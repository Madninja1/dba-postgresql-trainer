# Пользователи, группы и права Linux

## 1. Тема

Когда PostgreSQL получает `Permission denied`, проблема обычно находится не «в PostgreSQL вообще», а в конкретной цепочке Linux-доступа:

```text
какой пользователь выполняет процесс?
        ↓
кто владелец файла/каталога?
        ↓
какая группа назначена объекту?
        ↓
какие rwx-права действуют?
        ↓
можно ли пройти через все родительские каталоги?
```

Linux идентифицирует пользователей и группы числовыми UID/GID. Имена вроде `postgres` или `dba1` — удобное отображение этих идентификаторов.

---

## 2. Механизм

### Пользователь, UID и GID

Проверить текущую идентичность:

```bash
id
id postgres
```

Команда показывает UID, основной GID и supplementary groups.

Информацию из системных баз пользователей и групп удобно получать через `getent`:

```bash
getent passwd postgres
getent group dbadmins
```

### Пользователь PostgreSQL

Сервер PostgreSQL обычно работает от отдельного системного пользователя `postgres`. Поэтому доступ к файлам определяется правами **этого Linux-пользователя**, а не именем SQL-роли, от которой вы вошли в БД.

```text
SQL role
≠
Linux user процесса PostgreSQL
```

### Создание группы и пользователя

```bash
sudo groupadd dbadmins
sudo useradd -m dba1
```

`-m` у `useradd` создаёт домашний каталог.

Добавить пользователя в supplementary group:

```bash
sudo usermod -aG dbadmins dba1
```

Здесь важно сочетание:

```text
-G → задать supplementary groups
-a → append к текущему списку
```

`-G` без `-a` может заменить существующий список дополнительных групп. После изменения членства уже открытая пользовательская сессия может не увидеть новую группу до нового входа.

---

### Владелец, группа и `rwx`

Посмотреть права каталога:

```bash
ls -ld /srv/pgbackup
```

Типичный режим:

```text
drwxr-x---
│└─┬─┘└─┬─┘└─┬─┘
│  │    │    └ others
│  │    └ group
│  └ owner
└ directory
```

Биты:

```text
r → read
w → write
x → execute/traverse
```

Для обычного файла:

```text
r → читать
w → изменять
x → выполнять
```

Для каталога:

```text
r → читать список имён
w → создавать/удалять записи каталога
x → проходить через каталог и обращаться к объектам внутри
```

Именно `x` на каждом родительском каталоге критичен для доступа к вложенному файлу.

---

### Octal notation и `chmod`

```text
r = 4
w = 2
x = 1
```

Поэтому:

```text
7 = rwx
6 = rw-
5 = r-x
4 = r--
0 = ---
```

Команда:

```bash
chmod 750 /srv/pgbackup
```

даёт:

```text
owner  → rwx
group  → r-x
others → ---
```

---

### `chown` и `chgrp`

Изменить владельца:

```bash
sudo chown postgres /srv/pgbackup
```

Одновременно владельца и группу:

```bash
sudo chown postgres:dbadmins /srv/pgbackup
```

Только группу:

```bash
sudo chgrp dbadmins /srv/pgbackup
```

Синтаксис `owner:group` позволяет одной командой задать обе характеристики.

---

### Проверять права реальным действием

Простой просмотр `ls -l` не доказывает, что нужный пользователь реально может выполнить операцию.

Например:

```bash
sudo -u postgres touch /srv/pgbackup/postgres.txt
sudo -u dba1 touch /srv/pgbackup/dba1.txt
```

Это проверяет доступ именно от имени конкретного пользователя.

С shell redirect есть важный нюанс. Запись:

```bash
sudo -u dba1 echo test >> /srv/pgbackup/test.txt
```

может дать ложное впечатление, потому что `>>` обрабатывает исходный shell до запуска `sudo`.

Правильнее:

```bash
sudo -u dba1 sh -c 'echo test >> /srv/pgbackup/test.txt'
```

Теперь и команда, и перенаправление выполняются в контексте `dba1`.

---

### `umask`

`umask` не задаёт готовый режим, а убирает биты из базовых прав новых объектов.

Упрощённая модель лабораторной:

```text
файл    → база 666
каталог → база 777
```

При:

```bash
umask 022
```

обычно получаются:

```text
файл    → 644
каталог → 755
```

Более строгий вариант:

```bash
umask 0077
```

убирает права group/others у новых объектов. `umask` действует в контексте текущего shell и наследуется его дочерними процессами; это не глобальная настройка всей ОС.

## 3. Важные детали

### Почему корректные права самого файла могут не помочь

Пусть файл доступен `postgres`, но на одном из родительских каталогов нет `x`:

```text
/srv
  ↓ x?
/srv/dba-lab
  ↓ x?
/srv/dba-lab/data
  ↓ x?
report.txt
```

Тогда процесс не сможет пройти путь до файла.

Для диагностики:

```bash
namei -l /srv/dba-lab/data/report.txt
```

`namei -l` показывает каждый компонент пути вместе с владельцами и правами и помогает увидеть точку, где доступ ломается.

Полезны также:

```bash
ls -ld PATH
stat PATH
```

`stat` даёт подробные метаданные объекта.

### Least privilege

```bash
chmod -R 777 /srv/dba-lab
```

может временно скрыть проблему, но открывает доступ значительно шире необходимого. Правильный подход — найти конкретную причину и дать минимально достаточные права.

### Диагностическая цепочка `Permission denied`

```text
1. какой Linux-user выполняет процесс? → id / ps
2. кто owner/group?                    → ls -l / stat
3. какие rwx действуют?                → mode
4. есть ли нужная группа?              → id / getent
5. проходим ли весь путь?              → namei -l
6. работает ли реальная операция?      → sudo -u ...
```

## Что запомнить

```bash
id USER
getent passwd USER
getent group GROUP
```

→ пользователь, UID/GID и группы.

```text
файл:
r read, w write, x execute

каталог:
r list, w modify entries, x traverse
```

```text
chmod 750
→ owner rwx, group r-x, others ---
```

```bash
chown owner:group PATH
chgrp group PATH
```

→ владелец и группа.

```text
umask 022
→ обычно 644 для файлов и 755 для каталогов
```

```bash
namei -l /path/to/file
```

→ проверить весь путь при `Permission denied`.

Главный принцип: **права нужно проверять от имени того Linux-пользователя, который реально выполняет операцию**.
