# Процессы PostgreSQL и сигналы

## 1. Тема

Каждое клиентское соединение PostgreSQL обслуживается отдельным backend-процессом. Поэтому для DBA важно уметь связать три представления одной активности:

```text
клиентская сессия PostgreSQL
        ↓
backend PID
        ↓
Linux process
```

На этой связи строится диагностика зависших запросов, поиск процесса и безопасное завершение работы.

Основные инструменты:

```text
ps / pgrep / pstree
pg_backend_pid()
pg_stat_activity
kill
pg_cancel_backend()
pg_terminate_backend()
```

---

## 2. Механизм

### PID процесса

Процесс — выполняющийся экземпляр программы, которому ядро назначает PID.

PID текущего shell можно увидеть:

```bash
echo $$
```

`$$` — специальный параметр shell с PID самого shell-процесса.

---

### Просмотр процессов через `ps`

Классический вариант:

```bash
ps -ef
```

В этой форме:

```text
-e → все процессы
-f → full/расширенный формат
```

У `ps` исторически сосуществуют разные стили параметров. Поэтому часто встречается и запись:

```bash
ps aux
```

Она относится к BSD-style синтаксису и не должна удивлять отсутствием ведущего `-` у `aux`.

Найти PostgreSQL-процессы можно через pipeline:

```bash
ps -ef | grep postgres
```

Но такой вариант часто включает и сам `grep`. Более прямой инструмент:

```bash
pgrep -a postgres
```

`pgrep` ищет процессы по имени, а `-a` выводит PID вместе с полной командной строкой найденного процесса.

---

### Дерево процессов

PostgreSQL — не один изолированный PID. У серверного процесса есть дочерние процессы разных назначений.

Посмотреть иерархию:

```bash
pstree -p
```

`-p` добавляет PID. Это помогает увидеть родительско-дочернюю структуру и понять, как отдельный backend связан с основным сервером.

---

### PID текущей PostgreSQL-сессии

Внутри SQL:

```sql
SELECT pg_backend_pid();
```

Функция возвращает PID backend-процесса именно текущего соединения.

После этого PID можно найти на уровне Linux:

```bash
ps -fp <PID>
```

И в самой БД:

```sql
SELECT pid, usename, datname, state, query
FROM pg_stat_activity
WHERE pid = <PID>;
```

Получается связка:

```text
pg_backend_pid()
      ↓
pg_stat_activity.pid
      ↓
Linux PID
```

`pg_stat_activity` позволяет увидеть, кто подключён, к какой базе, в каком состоянии находится backend и какой запрос сейчас выполняется.

---

### Наблюдение за долгим запросом

Удобная учебная цель:

```sql
SELECT pg_sleep(300);
```

Запрос долго остаётся активным, поэтому его легко найти через `pg_stat_activity`, сопоставить с Linux-процессом и затем отменить.

---

### Сигналы Linux

Команда:

```bash
kill PID
```

не обязательно означает «убить процесс немедленно». `kill` отправляет процессу сигнал.

Список сигналов:

```bash
kill -l
```

В теме важны три сигнала:

```text
SIGINT  → прерывание текущей работы
SIGTERM → корректное завершение процесса
SIGKILL → принудительное завершение ядром
```

#### SIGINT

Для backend PostgreSQL во время активного запроса:

```bash
kill -INT <PID>
```

В лабораторной это используется для отмены текущего запроса. После ошибки отмены соединение обычно остаётся живым, и его можно проверить:

```sql
SELECT 1;
```

То есть модель:

```text
SIGINT
→ отменить текущую работу
→ backend/сессия остаётся
```

#### SIGTERM

```bash
kill -TERM <PID>
```

Для отдельного backend это означает завершение процесса и потерю соответствующего клиентского соединения.

```text
SIGTERM
→ завершить backend
→ соединение исчезает
```

#### SIGKILL

```bash
kill -KILL <PID>
# или
kill -9 <PID>
```

SIGKILL нельзя перехватить или обработать пользовательским процессом. Это аварийный механизм, а не штатный способ управления PostgreSQL. Для обычной DBA-работы сначала следует использовать средства самого PostgreSQL или корректные сигналы.

---

### То же самое через PostgreSQL

Для отмены текущей работы backend:

```sql
SELECT pg_cancel_backend(<PID>);
```

Для завершения сессии:

```sql
SELECT pg_terminate_backend(<PID>);
```

Различие принципиально:

```text
pg_cancel_backend
→ отменяет текущий запрос
→ соединение может продолжить работу

pg_terminate_backend
→ завершает backend
→ соединение теряется
```

Это SQL-аналоги двух разных административных намерений: «остановить запрос» и «закрыть сессию».

---

## 3. Важные детали

### Не путать query и session

Долгий или ошибочный запрос не всегда требует убивать соединение. Если проблема только в текущей работе, предпочтительнее cancel.

```text
плохой запрос
→ pg_cancel_backend()

нежелательная/зависшая сессия
→ pg_terminate_backend()
```

### PID нужно проверять перед действием

PID со временем переиспользуются ОС. Перед отправкой сигнала нужно убедиться, что PID всё ещё принадлежит нужному backend:

```bash
ps -fp <PID>
```

и сверить его с `pg_stat_activity`.

### Linux и PostgreSQL дают разные уровни контекста

Linux видит процесс и ресурсы. PostgreSQL видит пользователя БД, базу, состояние и SQL-запрос. Для хорошей диагностики используются оба уровня.

### `pgrep -a` удобнее голого `grep`

`ps | grep` полезен как универсальная техника, но `pgrep -a postgres` даёт более чистый список PID и командных строк без лишней строки `grep`.

## Что запомнить

```bash
echo $$
```

→ PID текущего shell.

```bash
ps -ef
ps aux
pgrep -a postgres
pstree -p
```

→ разные способы увидеть процессы и их иерархию.

```sql
SELECT pg_backend_pid();
SELECT pid, usename, datname, state, query
FROM pg_stat_activity;
```

→ связать PostgreSQL-сессию с Linux PID.

```text
SIGINT  → отменить текущую работу
SIGTERM → завершить backend
SIGKILL → жёсткое аварийное завершение
```

```text
pg_cancel_backend()    → cancel query
pg_terminate_backend() → terminate session
```

Главная модель:

```text
session → backend PID → Linux process
```
