# Strong — продвинутый PL/pgSQL

## 1. Тема

Тема посвящена PL/pgSQL — серверному процедурному языку PostgreSQL, который дополняет SQL переменными, блоками, управляющими конструкциями, обработкой ошибок и динамическим выполнением.

## 2. Механизм

Strong — безопасность dynamic SQL, диагностика ошибок, триггеры, транзакции и поведение планировщика PL/pgSQL.

### EXECUTE и планы

Динамический `EXECUTE` **не кеширует план**: команда планируется заново при каждом выполнении.

```sql
EXECUTE 'SELECT * FROM users WHERE id = $1'
INTO rec
USING p_id;
```

Это отличается от статических SQL-команд PL/pgSQL, для которых язык может кешировать и повторно использовать план.

Иногда повторное планирование — преимущество, если лучший план сильно зависит от текущего значения параметров.

### Безопасный dynamic SQL

Данные и идентификаторы нужно разделять.

```sql
EXECUTE format(
    'UPDATE %I SET %I = $1 WHERE id = $2',
    table_name,
    column_name
)
USING new_value, row_id;
```

- `%I` — SQL-идентификатор;
- `%L` — SQL-литерал;
- `$1`, `$2` в `EXECUTE ... USING` — значения данных.

Для строковой сборки также существуют `quote_ident`, `quote_literal`, `quote_nullable`.

### FOUND и EXECUTE

Обычный динамический `EXECUTE` сам по себе не меняет `FOUND`. Если нужно узнать число обработанных строк, используйте `GET DIAGNOSTICS ... ROW_COUNT`.

### GET STACKED DIAGNOSTICS

Внутри `EXCEPTION` можно получить сведения о пойманной ошибке:

```sql
EXCEPTION WHEN OTHERS THEN
    GET STACKED DIAGNOSTICS
        v_state = RETURNED_SQLSTATE,
        v_message = MESSAGE_TEXT,
        v_detail = PG_EXCEPTION_DETAIL,
        v_hint = PG_EXCEPTION_HINT,
        v_context = PG_EXCEPTION_CONTEXT;
```

Это используется именно для текущего обработанного исключения.

### Триггерные функции

В row-level trigger доступны специальные записи `NEW` и `OLD`.

- `INSERT`: обычно есть `NEW`;
- `DELETE`: обычно есть `OLD`;
- `UPDATE`: есть обе.

В `BEFORE` row trigger можно изменить `NEW` и вернуть его.

Чтобы пропустить операцию для текущей строки, `BEFORE` row trigger возвращает `NULL`.

Триггерная функция также получает сведения вроде `TG_OP`, `TG_NAME`, `TG_TABLE_NAME`, `TG_WHEN`, `TG_LEVEL`.

### Управление транзакциями

Функции не могут произвольно фиксировать транзакцию. Управление `COMMIT`/`ROLLBACK` доступно в процедурах и некоторых контекстах `CALL`/`DO`, где это разрешено.

```sql
COMMIT;
COMMIT AND CHAIN;
```

`COMMIT AND CHAIN` завершает текущую транзакцию и сразу начинает следующую с теми же характеристиками транзакции.

Блок с `EXCEPTION` создаёт под-транзакционную область; завершать транзакцию внутри такого активного блока нельзя.

### Конфликты имён

Если имя PL/pgSQL-переменной совпадает с именем столбца, возникает неоднозначность. По умолчанию PL/pgSQL сообщает ошибку.

Способы избежать конфликта:

- выбирать отличающиеся имена (`p_id`, `v_id`);
- квалифицировать столбцы псевдонимом таблицы;
- квалифицировать переменную меткой блока/именем функции;
- при необходимости использовать настройку `plpgsql.variable_conflict` или директиву `#variable_conflict`.

Лучший стиль — не создавать неоднозначность вообще.

### Кеширование статических команд

PL/pgSQL преобразует переменные статического SQL в параметры и может кешировать подготовленный план. PostgreSQL выбирает между custom и generic plan в зависимости от условий повторного выполнения.

Для dynamic `EXECUTE` плана между вызовами нет.

### Кавычки

Тело PL/pgSQL-функции обычно удобно заключать в dollar quoting:

```sql
CREATE FUNCTION f() RETURNS void
LANGUAGE plpgsql AS $$
BEGIN
    ...
END;
$$;
```

Это избавляет от многократного экранирования одинарных кавычек. Для динамического SQL всё равно используйте параметризацию и `%I/%L`, а не ручную конкатенацию пользовательских значений.

## 3. Важные детали и покрытие тестов

Ниже собраны детали, которые проверяются вопросами этой темы. Они сгруппированы по разделам исходной документации, чтобы их можно было связывать с механизмом, а не запоминать как отдельный список ответов.

### 43.5.4. Выполнение динамически формируемых команд

- **Планирование EXECUTE.** План строится заново при каждом выполнении. EXECUTE не кеширует план; это может быть полезно, когда оптимальный план сильно зависит от параметров.
- **format %I / %L.** `%I` эквивалентен quote_ident; `%L` эквивалентен quote_nullable.
- **Безопасное построение dynamic SQL.** Передавать data values через USING. Документация прямо предупреждает, что dollar quoting не подходит для заранее неизвестного динамического значения.
- **Параметры $1 и USING.** Они подставляют значения данных. Имена таблиц/столбцов требуется вставлять как текст, а data values лучше передавать USING.

### 43.5.5. Статус выполнения команды

- **EXECUTE и FOUND.** Нет. Документация статуса выполнения подчёркивает: EXECUTE меняет данные GET DIAGNOSTICS, но не FOUND.

### 43.6.8.1. Получение информации об ошибке

- **GET STACKED DIAGNOSTICS.** Получить информацию об ошибке внутри обработчика EXCEPTION. Раздел 43.6.8.1 описывает диагностику текущего перехваченного исключения.

### 43.10.1. Триггеры при изменении данных

- **NEW и OLD.** Запись новой строки для INSERT/UPDATE. Триггерные функции получают специальные переменные NEW/OLD в зависимости от события.
- **Возвращаемое значение BEFORE trigger.** Для BEFORE row trigger возврат NULL сообщает trigger manager пропустить оставшуюся операцию для строки.
- **Контекст trigger function.** Они получают специальные переменные о событии trigger. Раздел 43.10 описывает контекст trigger function и специальные переменные.

### 43.8. Управление транзакциями

- **COMMIT AND CHAIN.** Фиксирует текущую транзакцию и начинает новую с характеристиками предыдущей. Раздел управления транзакциями описывает COMMIT/ROLLBACK и варианты AND CHAIN.
- **COMMIT / ROLLBACK / AND CHAIN.** Процедуры, вызываемые через CALL, и DO могут в допустимом контексте выполнять COMMIT/ROLLBACK. Раздел 43.8 описывает ограничения и поведение transaction control в процедурах/DO.

### 43.11.1. Подстановка переменных

- **Неоднозначные имена.** Неоднозначная ссылка вызывает ошибку, если не изменена настройка разрешения конфликтов. Раздел подстановки переменных описывает конфликты имён и способы явной квалификации/настройки.
- **Конфликты имён.** Квалифицировать столбец именем таблицы/alias. Раздел реализации рассматривает неоднозначные ссылки и способы сделать намерение явным.

### 43.11.2. Кеширование плана

- **Кеширование планов.** Подготовленные планы выполнения, которые могут переиспользоваться. Раздел 43.11.2 посвящён кешированию планов для выражений и SQL в PL/pgSQL.
- **Статический план и EXECUTE.** Статические выражения/SQL могут использовать кешированный план. Разделы 43.5.4 и 43.11.2 противопоставляют dynamic planning и кеширование статических команд.

### 43.5.5 и 43.6.8.1

- **GET DIAGNOSTICS / GET STACKED DIAGNOSTICS.** ROW_COUNT через GET DIAGNOSTICS. Глава 43 описывает текущую и stacked diagnostics.

### 43.6.8. Обработка ошибок

- **Состояние после ошибки.** Блок EXCEPTION создаёт дополнительную стоимость входа/выхода. Раздел 43.6.8 описывает семантику и стоимость блока обработки ошибок.

### 43.12.1. Обработка кавычек

- **Dollar quoting и dynamic values.** Тело функции удобно заключать в dollar quotes. Документация отдельно различает dollar quoting тела функции и экранирование dynamic SQL.
