# Middle — уверенный PL/pgSQL

## 1. Тема

На базовом уровне PL/pgSQL достаточно переменных, `SELECT INTO`, условий и циклов. На практике быстро появляются более сложные вопросы:

- как не дублировать тип столбца в объявлении переменной;
- как хранить целую строку таблицы;
- что делать, если запрос вернул ноль или несколько строк;
- как строить SQL, когда имя таблицы или столбца известно только во время выполнения;
- как получить точное число обработанных строк;
- как перехватывать ошибки;
- как читать большой результат через курсор;
- как формировать диагностические сообщения.

Этот уровень посвящён именно этим механизмам.

---

## 2. Механизм

### 2.1. `%TYPE`: наследовать тип существующего значения

Вместо жёсткого повторения типа столбца:

```sql
DECLARE
    v_user_id bigint;
```

можно связать тип переменной с определением таблицы:

```sql
DECLARE
    v_user_id users.user_id%TYPE;
```

`%TYPE` берёт тип указанной переменной или столбца.

Преимущество — меньше дублирования. Если тип `users.user_id` позже изменится, объявление функции не содержит собственного отдельного знания о том, что это был `bigint`.

Пример:

```sql
DECLARE
    v_price products.price%TYPE;
    v_login users.login%TYPE;
```

`%TYPE` наследует **тип**, а не значение.

### 2.2. `%ROWTYPE`: переменная со структурой строки

Когда нужна целая строка таблицы или представления:

```sql
DECLARE
    v_user users%ROWTYPE;
BEGIN
    SELECT *
    INTO v_user
    FROM users
    WHERE id = p_id;

    RAISE NOTICE 'login = %', v_user.login;
END;
```

`users%ROWTYPE` имеет структуру строки `users`.

К полям обращаются через точку:

```sql
v_user.id
v_user.login
v_user.created_at
```

Это удобно, когда функция действительно работает со строкой как с единым объектом.

### 2.3. `RECORD`: строка без заранее фиксированной структуры

`RECORD` отличается от `%ROWTYPE`:

```sql
DECLARE
    rec record;
```

У него нет заранее определённого набора полей. Структура появляется после присваивания строки запросом или циклом:

```sql
SELECT id, login
INTO rec
FROM users
WHERE id = p_id;
```

После этого доступны:

```sql
rec.id
rec.login
```

Но до первого присваивания структура `record` неизвестна, и обращение к полю приведёт к ошибке времени выполнения.

Ментальная модель:

```text
%TYPE     → тип одного значения
%ROWTYPE  → заранее известная структура строки таблицы/представления
RECORD    → структура определяется полученной строкой во время выполнения
```

### 2.4. `SELECT ... INTO` без `STRICT`

Напомним базовое поведение:

```sql
SELECT id, login
INTO v_id, v_login
FROM users
WHERE email = p_email;
```

Без `STRICT`:

```text
0 строк   → цели получают NULL, FOUND = false
1 строка  → строка присваивается, FOUND = true
>1 строк  → присваивается первая строка
```

Если возможны несколько строк и выбор первой имеет значение, задавайте `ORDER BY`. Иначе «первая» строка не определена надёжно.

### 2.5. `INTO STRICT`: нужна ровно одна строка

Если запрос обязан вернуть ровно одну строку:

```sql
SELECT id, login
INTO STRICT v_id, v_login
FROM users
WHERE email = p_email;
```

`STRICT` меняет семантику:

```text
0 строк   → NO_DATA_FOUND
1 строка  → успех, FOUND = true
>1 строк  → TOO_MANY_ROWS
```

Ошибки можно обработать в `EXCEPTION`:

```sql
BEGIN
    SELECT *
    INTO STRICT v_user
    FROM users
    WHERE email = p_email;
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        RAISE EXCEPTION 'user not found';
    WHEN TOO_MANY_ROWS THEN
        RAISE EXCEPTION 'email is not unique';
END;
```

Для `INSERT/UPDATE/DELETE ... RETURNING ... INTO` PL/pgSQL не может просто выбрать произвольную из нескольких возвращённых строк: несколько строк приводят к ошибке даже без `STRICT`.

### 2.6. Когда нужен динамический `EXECUTE`

Обычный SQL внутри PL/pgSQL хорошо подходит, когда структура команды постоянна:

```sql
SELECT count(*)
INTO v_count
FROM users
WHERE status = p_status;
```

Но значение параметра и имя объекта — разные вещи.

Так можно передать **значение**:

```sql
WHERE status = p_status
```

Но нельзя обычным query parameter заменить имя таблицы:

```text
FROM <имя таблицы из переменной>
```

Если сам текст SQL должен меняться — например, выбирается другая таблица или другой столбец — используется PL/pgSQL `EXECUTE`:

```sql
EXECUTE command_text;
```

`command_text` — выражение, которое должно сформировать строку типа `text` с выполняемой командой. Полная форма:

```sql
EXECUTE command_text
    [ INTO [STRICT] target ]
    [ USING expression [, ...] ];
```

### 2.7. `EXECUTE ... USING`: значения отдельно от SQL-текста

Безопасный вариант для data values:

```sql
EXECUTE
    'SELECT count(*) FROM users WHERE status = $1 AND created_at >= $2'
INTO v_count
USING p_status, p_since;
```

Здесь `$1` и `$2` относятся к выражениям после `USING`.

Преимущества:

- значения не приходится вручную превращать в SQL-текст;
- сохраняются исходные типы данных;
- нет необходимости вручную экранировать кавычки внутри значений;
- существенно уменьшается риск SQL injection.

Но такие параметры заменяют **данные**, а не SQL-идентификаторы.

Так нельзя:

```sql
EXECUTE 'SELECT * FROM $1' USING table_name;
```

Имя таблицы нужно безопасно вставить в текст команды.

### 2.8. Динамические идентификаторы: `format('%I', ...)`

Для имени таблицы или столбца используйте `%I`:

```sql
EXECUTE format(
    'SELECT count(*) FROM %I WHERE status = $1',
    table_name
)
INTO v_count
USING p_status;
```

`%I` предназначен для SQL-идентификатора и эквивалентен безопасному quoting через `quote_ident`.

Для строкового представления значения существует `%L`, эквивалентный `quote_nullable`:

```sql
EXECUTE format(
    'SELECT * FROM %I WHERE category = %L',
    table_name,
    category_value
);
```

Но когда возможно, значения лучше всё равно передавать через `USING`:

```sql
EXECUTE format(
    'SELECT * FROM %I WHERE category = $1',
    table_name
)
USING category_value;
```

Это сохраняет тип значения и не требует превращать его в текст.

Полезное соответствие:

```text
%I              → identifier → quote_ident(...)
%L              → SQL literal → quote_nullable(...)
USING $1, $2...  → data values без текстовой вставки
```

### 2.9. Планирование dynamic `EXECUTE`

В отличие от обычного статического SQL в PL/pgSQL, команда внутри `EXECUTE` планируется заново при каждом выполнении.

На Middle-уровне достаточно понимать следствие:

```text
обычный статический SQL → может переиспользовать подготовленный/кешированный план
EXECUTE text            → строит план при каждом выполнении
```

На Strong-уровне это будет связано с выбором generic/custom plan и производительностью.

### 2.10. `EXECUTE ... INTO`

Динамический запрос может вернуть данные в переменную:

```sql
EXECUTE format('SELECT * FROM %I WHERE id = $1', table_name)
INTO rec
USING p_id;
```

Также поддерживается `STRICT`:

```sql
EXECUTE format('SELECT * FROM %I WHERE id = $1', table_name)
INTO STRICT rec
USING p_id;
```

Смысл `STRICT` тот же: нужна ровно одна строка.

### 2.11. `GET DIAGNOSTICS`: получить состояние выполнения

`FOUND` отвечает на boolean-вопрос: была ли строка/итерация/изменение.

Когда нужно точное количество строк, используйте диагностику:

```sql
DECLARE
    v_rows bigint;
BEGIN
    UPDATE jobs
    SET status = 'expired'
    WHERE expires_at < now();

    GET DIAGNOSTICS v_rows = ROW_COUNT;
END;
```

`ROW_COUNT` — число строк, обработанных последней SQL-командой.

Сравните:

```text
FOUND    → затронута ли хотя бы одна строка?
ROW_COUNT → сколько строк обработано?
```

`GET DIAGNOSTICS` также умеет получать другие элементы текущего состояния; `PG_CONTEXT` будет подробнее рассмотрен на следующем уровне.

### 2.12. Обработка ошибок: `EXCEPTION`

По умолчанию ошибка прерывает выполнение функции и текущую транзакцию. Внутри блока можно добавить обработчик:

```sql
BEGIN
    risky_operation();
EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'division by zero';
END;
```

Логика блока:

```text
BEGIN
    операторы
    ↓ ошибка
оставшиеся операторы блока пропускаются
    ↓
ищется первый подходящий WHEN
    ↓
выполняется обработчик
    ↓
выполнение продолжается после END блока
```

Можно объединять условия:

```sql
EXCEPTION
    WHEN unique_violation OR foreign_key_violation THEN
        ...
```

`OTHERS` ловит все ошибки, кроме `QUERY_CANCELED` и `ASSERT_FAILURE`. Использовать настолько широкий обработчик без необходимости обычно плохая идея.

### 2.13. Что откатывается при ошибке внутри `EXCEPTION`-блока

Это принципиальная особенность PL/pgSQL.

Если ошибка перехвачена обработчиком:

- изменения данных, выполненные **внутри ошибочной части блока**, откатываются;
- локальные переменные PL/pgSQL сохраняют значения, которые успели получить до ошибки;
- изменения, сделанные до входа в этот вложенный блок, не откатываются только из-за его обработчика.

Пример:

```sql
x := 10;

BEGIN
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    x := 20;
    y := 1 / 0;
EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'x = %', x;
END;
```

После обработки ошибки `x` остаётся `20`, но `UPDATE` внутри блока будет отменён.

Это делает `EXCEPTION` похожим по эффекту на внутреннюю точку отката, хотя писать ручной `SAVEPOINT` здесь не нужно.

### 2.14. `RETURN QUERY EXECUTE`

Set-returning function может добавлять строки динамического запроса:

```sql
RETURN QUERY EXECUTE
    format('SELECT * FROM %I WHERE active = $1', table_name)
USING true;
```

Как и обычный `RETURN QUERY`, эта команда **добавляет** строки к результату и не завершает функцию немедленно.

Она также влияет на `FOUND`: `true`, если запрос вернул хотя бы одну строку.

### 2.15. Курсоры и `refcursor`

Курсор позволяет работать с результатом запроса не как с одним полностью материализованным значением в переменной, а через состояние позиции в наборе строк.

Курсорная переменная имеет тип:

```sql
refcursor
```

Например:

```sql
DECLARE
    cur refcursor;
```

Или можно связать курсор с запросом при объявлении:

```sql
DECLARE
    cur CURSOR FOR
        SELECT id, login FROM users ORDER BY id;
```

### 2.16. `OPEN`, `FETCH`, `MOVE`, `CLOSE`

Основные операции:

```text
OPEN   → открыть курсор
FETCH  → получить строку и переместить позицию
MOVE   → переместить позицию без получения строки
CLOSE  → закрыть курсор и освободить портал
```

Пример:

```sql
OPEN cur FOR
    SELECT id, login FROM users ORDER BY id;

FETCH cur INTO v_id, v_login;
MOVE cur;
CLOSE cur;
```

После `FETCH` и `MOVE` можно проверять `FOUND`.

Курсор связан с серверным portal. Открытые portals существуют в рамках транзакции и автоматически закрываются в её конце.

### 2.17. Цикл по связанному курсору

Связанный курсор можно использовать непосредственно в `FOR`:

```sql
DECLARE
    cur CURSOR FOR SELECT id, login FROM users ORDER BY id;
BEGIN
    FOR rec IN cur LOOP
        RAISE NOTICE '%', rec.login;
    END LOOP;
END;
```

Такой `FOR` сам открывает курсор и закрывает его по завершении цикла.

Для обычного обхода результата `FOR rec IN SELECT ... LOOP` часто проще явного управления курсором. Курсор нужен, когда важна отдельная позиция, `FETCH/MOVE`, передача `refcursor` вызывающему коду или другая специальная семантика.

### 2.18. `RAISE`: сообщения и ошибки

`RAISE` используется и для диагностических сообщений, и для исключений.

Уровни:

```text
DEBUG
LOG
INFO
NOTICE
WARNING
EXCEPTION
```

`EXCEPTION` по умолчанию создаёт ошибку и прерывает обычный поток выполнения. Остальные уровни создают сообщения разной важности.

Пример:

```sql
RAISE NOTICE 'processing user %', p_user_id;
```

`%` подставляет следующий аргумент. Литеральный знак процента пишется как `%%`.

Можно добавить структурированную информацию:

```sql
RAISE EXCEPTION 'user % not found', p_user_id
    USING ERRCODE = 'P0002',
          DETAIL = 'lookup failed',
          HINT = 'check the identifier';
```

Поддерживаются, в частности:

- `MESSAGE`;
- `DETAIL`;
- `HINT`;
- `ERRCODE`;
- имена связанных объектов (`TABLE`, `COLUMN`, `CONSTRAINT`, ...).

`RAISE;` без аргументов внутри обработчика повторно выбрасывает текущую ошибку.

### 2.19. `ASSERT`: проверка предположений разработчика

Для отладочных инвариантов есть:

```sql
ASSERT condition [, message];
```

Если условие ложно или `NULL`, возникает `ASSERT_FAILURE`.

`ASSERT` предназначен для поиска ошибок в программе, а не для обычной бизнес-валидации. Для пользовательских ошибок используйте `RAISE`.

## 3. Как выбирать механизм

```text
Нужен тип конкретного столбца?          → %TYPE
Нужна строка конкретной таблицы?         → %ROWTYPE
Структура строки известна только позже?  → RECORD
Нужна максимум первая строка?            → INTO
Нужна строго одна строка?                → INTO STRICT
Меняется только значение в SQL?          → обычная переменная / parameter
Меняется имя таблицы/столбца?            → EXECUTE + format(%I)
Нужно передать data value в EXECUTE?      → USING
Нужно число затронутых строк?             → GET DIAGNOSTICS ... ROW_COUNT
Нужно обработать ошибку?                  → EXCEPTION ... WHEN
Нужна позиционная работа с набором строк? → cursor / refcursor
Нужно сообщение/ошибка?                   → RAISE
```

# Что запомнить

- `%TYPE` наследует тип столбца или переменной.
- `%ROWTYPE` задаёт заранее известную структуру строки таблицы/представления.
- `RECORD` получает структуру во время выполнения и до первого присваивания полей не имеет.
- `INTO` без `STRICT` берёт первую строку или даёт `NULL`, если строк нет.
- `INTO STRICT` требует ровно одну строку: `NO_DATA_FOUND` для нуля, `TOO_MANY_ROWS` для нескольких.
- `EXECUTE` нужен, когда меняется сам текст команды, особенно идентификаторы объектов.
- В dynamic SQL значения лучше передавать через `$1`, `$2`, ... и `USING`.
- Идентификаторы формируются через `format('%I', ...)`/`quote_ident`; `%L` соответствует quoting значения как SQL literal.
- Dynamic `EXECUTE` планируется при каждом выполнении.
- `GET DIAGNOSTICS ... ROW_COUNT` даёт точное число обработанных строк; `FOUND` — только boolean-состояние.
- `EXCEPTION ... WHEN` перехватывает ошибки; изменения данных внутри ошибочной части блока откатываются, локальные переменные сохраняют свои значения.
- Курсорная переменная имеет тип `refcursor`; основные операции — `OPEN`, `FETCH`, `MOVE`, `CLOSE`.
- `RETURN QUERY EXECUTE` добавляет результат динамического запроса в set-returning function.
- `RAISE` создаёт сообщения разных уровней, а `RAISE EXCEPTION` — ошибку.
