# 7. Буферный кеш и WAL

## 1. Тема

PostgreSQL не обязан немедленно записывать каждую изменённую страницу таблицы на диск. Сначала изменения попадают в буферный кеш, а долговечность транзакции обеспечивается WAL: журнальная запись должна быть надёжно записана раньше соответствующей страницы данных.

Главная модель:

```text
UPDATE
  ↓
shared_buffers: dirty page
  ↓
WAL record → WAL buffers → pg_wal
                   ↓ fsync при COMMIT

позже checkpoint/background writer
        ↓
     data files
```

# 2. Механизм

## Буферный кеш

Буферный кеш сглаживает разницу в скорости между оперативной памятью и диском. После загрузки страницы в кеш PostgreSQL может многократно обращаться к ней без повторного чтения через операционную систему. В лекции буферный кеш описан как массив буферов со страницами данных и служебной информацией. Обычный размер страницы — 8 Кбайт; изменить его можно при сборке PostgreSQL. Если данные страницы в буферном кеше были изменены, соответствующий буфер считается грязным и впоследствии должен быть записан на диск.

Лекция описывает LRU-подобный принцип: выбирается давно не использовавшаяся страница; грязная страница сначала записывается, после чего буфер может быть использован для другой страницы. Буферизация повышает производительность, но при сбое содержимое оперативной памяти может быть потеряно. WAL позволяет повторно воспроизвести необходимые изменения и восстановить согласованное состояние. Контрольная точка записывает соответствующие грязные буферы и создаёт опорную позицию, с которой можно начинать последующее восстановление.

Сам момент контрольной точки соответствует началу записи накопленных грязных буферов, но выполненной она считается только после завершения их записи. Лекция разделяет роли: walwriter обслуживает WAL, checkpointer выполняет контрольные точки, а background writer заранее очищает часть потенциально вытесняемых грязных буферов. Bgwriter старается заранее записывать буферы, которые с большой вероятностью скоро будут вытеснены, уменьшая задержку обслуживающих процессов.

## Правило WAL

В лекции указано, что журнал защищает таблицы, индексы, другие журналируемые объекты и статус транзакций. Изменения временных таблиц в WAL не попадают. Именно порядок «сначала WAL, затем изменённые данные» даёт возможность восстановить изменения после сбоя. Документация определяет это как основную идею WAL. В лекции WAL представлен как поток информации для повторного выполнения потерянных операций; файлы находятся в pg_wal. Временные и нежурналируемые таблицы исключены из обычной защиты WAL.

Нежурналируемые таблицы работают быстрее за счёт отсутствия защиты WAL, но после сбоя их содержимое не восстанавливается: таблицы очищаются. После аварийного завершения сервер восстанавливает согласованность, начиная с последней завершённой контрольной точки и воспроизводя нужные записи WAL. В лекции прямо указано: если запись о фиксации не успела попасть в журнал, такая транзакция после сбоя считается оборванной.

Документация подчёркивает последовательный характер записи WAL и меньшие затраты синхронизации по сравнению с записью множества изменённых файлов данных. Лекция объясняет использование fsync необходимостью не оставить журнальную запись только в кеше ОС и добиться её сохранения на энергонезависимом устройстве. Асинхронная запись позволяет не ждать немедленного fsync при каждой фиксации, но журнал всё равно используется для восстановления согласованности после сбоя.

Даже если журнальные записи ранее выводились асинхронно, перед записью соответствующей страницы данных PostgreSQL обязан обеспечить попадание необходимого WAL на диск. В материале перечислены уровни minimal, replica и logical с возрастающим объёмом информации в WAL и соответствующими дополнительными возможностями. На слайде об уровнях WAL значение replica указано как уровень по умолчанию.

Режим immediate завершает сервер без контрольной точки. На диске остаётся состояние, аналогичное сбою, и при следующем запуске PostgreSQL восстанавливает согласованность по WAL. Документация связывает WAL не только с REDO после сбоя, но также с физическим резервным копированием и восстановлением на момент времени. В лекции дополнительно подчёркивается использование WAL для репликации.

## Контрольные точки

В режиме fast сервер завершает соединения и выполняет контрольную точку. Выключение может занять больше времени, зато при следующем запуске восстановление после сбоя не требуется.

## Практический ориентир

```bash
SELECT pg_current_wal_lsn();
CHECKPOINT;
SELECT pg_current_wal_lsn();

-- параметры, влияющие на контрольные точки
SHOW checkpoint_timeout;
SHOW max_wal_size;
SHOW full_page_writes;
```

# Что запомнить

```text
• WAL должен попасть на надёжное хранилище раньше страницы данных, которую он описывает
• COMMIT не означает, что все изменённые страницы таблиц уже записаны; достаточно надёжного WAL
• checkpoint ограничивает объём WAL, который придётся воспроизводить после сбоя
• full-page image защищает от частично записанной страницы
• `pg_wal` — критическая часть кластера, а не обычный лог для чтения человеком
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
