# 11. Низкоуровневое хранение данных

## 1. Тема

Объект PostgreSQL, который хранит данные, на диске представлен не обязательно одним файлом. У отношения есть несколько **слоёв (forks)**, а большой слой разбивается на файловые сегменты.

Основная модель занятия:

```text
relation
├─ main   → основные данные
├─ fsm    → карта свободного пространства
├─ vm     → карта видимости
└─ init   → начальное состояние UNLOGGED-отношения

каждый слой
→ один или несколько файлов-сегментов
```

Отдельная задача — значения, которые делают версию строки слишком большой для одной страницы. Для них PostgreSQL использует TOAST.

---

# 2. Файлы отношений и сегменты

## Слой и его файлы

Для таблиц, индексов, последовательностей и материализованных представлений PostgreSQL хранит данные в отношениях. У отношения может быть несколько слоёв, каждый из которых содержит свой вид данных.

Сначала слой представлен одним файлом. Имя основного файла — числовой идентификатор отношения; дополнительные слои получают суффикс.

Когда файл слоя достигает предельного размера, PostgreSQL создаёт следующий сегмент:

```text
NNN
NNN.1
NNN.2
...
```

В стандартной сборке размер одного сегмента составляет 1 ГБ. Другой размер можно выбрать только при сборке PostgreSQL из исходного кода.

Размер отдельного слоя показывает:

```sql
SELECT pg_relation_size('имя_отношения');
```

Поэтому один объект базы данных физически может соответствовать нескольким файлам.

# 3. Слои отношения

## `main`

Основной слой содержит собственно данные объекта:

```text
таблица
→ версии строк

индекс
→ индексные записи
```

Основной слой существует у всех рассматриваемых объектов, которые физически хранят данные.

## `fsm`

Free space map — карта свободного пространства.

Файл имеет суффикс:

```text
_fsm
```

FSM хранит сведения о свободном месте и помогает находить страницы, подходящие для размещения новых данных. Такой слой может существовать и у таблиц, и у индексов.

## `vm`

Visibility map — карта видимости.

Файл имеет суффикс:

```text
_vm
```

В рамках занятия этот слой относится к таблицам. Смысл карты видимости уже разбирался в теме VACUUM: она хранит служебные признаки видимости страниц.

## `init`

Слой инициализации имеет суффикс:

```text
_init
```

Он существует только для нежурналируемых (`UNLOGGED`) таблиц и их индексов.

Изменения UNLOGGED-отношений не защищаются обычным WAL. После сбоя PostgreSQL не пытается восстанавливать их прежнее содержимое: основной слой заменяется копией слоя `init`, поэтому отношение возвращается к пустому начальному состоянию.

```text
UNLOGGED relation
      ↓
main — рабочие данные
init — пустое начальное состояние

сбой
      ↓
main восстанавливается из init
```

# 4. TOAST

## Зачем нужен TOAST

Версия строки PostgreSQL должна помещаться на одну страницу. Если отдельные значения делают строку слишком большой, PostgreSQL может:

```text
сжать значение
или
вынести значение из основной строки
или
сначала сжать, затем вынести
```

Этот механизм называется **TOAST — The Oversized-Attribute Storage Technique**.

## TOAST-таблица

Для основной таблицы при необходимости создаётся отдельная служебная TOAST-таблица и её индекс.

Обычная TOAST-таблица находится в схеме:

```text
pg_toast
```

Для временных таблиц используется соответствующая временная схема `pg_toast_temp_N`.

Длинное значение хранится в TOAST-таблице фрагментами, каждый из которых помещается на страницу. PostgreSQL собирает значение из этих фрагментов прозрачно для приложения.

```text
основная строка
      ↓ ссылка
TOAST-таблица
├─ fragment 1
├─ fragment 2
└─ fragment ...
```

TOAST-таблица читается только тогда, когда действительно требуется вынесенное длинное поле.

## Собственная версионность

TOAST-таблица имеет собственную версионность. Если `UPDATE` создаёт новую версию основной строки, но длинное поле не меняется, новая версия может продолжать ссылаться на прежнее TOAST-значение.

Это позволяет не копировать большой объект без необходимости.

# 5. Размеры отношений

Занятие различает несколько уровней измерения размера.

```text
pg_relation_size
→ размер отдельного слоя отношения

pg_table_size
→ таблица + её TOAST-часть
→ без обычных индексов основной таблицы

pg_indexes_size
→ суммарный размер обычных индексов таблицы

pg_total_relation_size
→ полный размер таблицы вместе с индексами
```

`pg_table_size` можно применять и к отдельному индексу, потому что таблицы и индексы являются отношениями.

# 6. Практика

Основная практика связывает логическую структуру отношения с реальными файлами:

```text
создать UNLOGGED-таблицу
      ↓
найти её слой init
      ↓
убедиться в наличии файла _init
```

Для TOAST предлагается:

```text
создать таблицу с text
      ↓
посмотреть стратегию хранения
      ↓
изменить её на external
      ↓
вставить короткое и длинное значения
      ↓
проверить содержимое TOAST-таблицы
```

В дополнительной практике также сравнивается размер базы с суммарным размером таблиц и исследуются доступные методы TOAST-сжатия (`pglz` и `lz4`).

# Что запомнить

```text
• отношение состоит из одного или нескольких слоёв
• большой слой разбивается на файлы-сегменты; стандартный сегмент — 1 ГБ
• main хранит данные объекта
• fsm хранит сведения о свободном пространстве
• vm хранит карту видимости таблицы
• init нужен UNLOGGED-отношениям для сброса к начальному состоянию после сбоя
• версия строки должна помещаться на страницу; большие значения обслуживает TOAST
• TOAST может сжимать и/или выносить значения в отдельную служебную таблицу
• pg_relation_size, pg_table_size, pg_indexes_size и pg_total_relation_size измеряют разные уровни физического объёма
```
