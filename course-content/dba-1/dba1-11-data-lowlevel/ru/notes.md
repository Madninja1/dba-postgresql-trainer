# 11. Низкоуровневое хранение данных

## 1. Тема

На диске отношение PostgreSQL представлено набором файлов и слоёв (forks), разбитых на страницы фиксированного размера. Табличная строка хранится как heap tuple, а вспомогательные карты FSM/VM и механизм TOAST помогают эффективно работать с пространством и крупными значениями.

Главная модель:

```text
relation
├─ main fork: данные
├─ fsm: свободное место
├─ vm: visibility/frozen bits
└─ init: только unlogged

main → segments → 8 KB pages → line pointers → tuples
```

# 2. Механизм

## Файлы отношений и сегменты

Для объектов, которые физически хранят данные, PostgreSQL использует отношения, представленные несколькими слоями, или forks. Основной слой содержит сами данные отношения. Он существует для любых объектов, физически хранящих данные. Один слой отношения при росте разбивается на физические сегменты. В занятии показаны файлы NNN, NNN.1, NNN.2 и размер сегмента 1 ГБ.

Init представляет исходное пустое состояние нежурналируемого отношения и используется после сбоя, поскольку содержимое UNLOGGED-таблицы нельзя восстановить по WAL. TOAST-таблица является вспомогательным отношением: содержит фрагменты длинных значений, обслуживается индексом и используется PostgreSQL прозрачно. Материал последовательно рассматривает размер отдельного слоя, таблицы с TOAST, индексов и полный размер отношения. `pg_database_size` измеряет размер базы данных, а не размер отношения или связанных с ним объектов из перечисленного набора.

Каждая из функций имеет свой уровень охвата: отдельный слой, индексы или полное отношение с зависимыми структурами. Практика предлагает создать нежурналируемую таблицу и непосредственно проверить наличие слоя init, файл которого имеет суффикс _init.

## Forks: main/FSM/VM/init

В материале рассматриваются основной слой, карта свободного пространства, карта видимости и слой инициализации. WAL не является слоем (fork) отношения из перечисленного набора. Файлы карты свободного пространства имеют суффикс _fsm. FSM — карта свободного пространства. В конспекте отдельно подчёркивается, что такой слой применяется и для таблиц, и для индексов.

Файлы карты видимости имеют суффикс _vm. VM хранит служебную информацию о видимости страниц и является отдельным слоем таблицы, а не основным хранилищем строк. Слой инициализации имеет суффикс _init и существует у UNLOGGED-отношений.

## Страницы

TOAST решает проблему больших значений при условии, что версия строки должна физически помещаться на одну страницу.

## Практический ориентир

```bash
SELECT pg_relation_filepath('public.orders');
SELECT pg_relation_size('public.orders');
SELECT pg_total_relation_size('public.orders');

-- ctid показывает физическое положение версии строки
SELECT ctid, * FROM public.orders LIMIT 5;
```

# 3. Важные детали

## Heap tuples и MVCC-поля

В материале перечислены сжатие, вынос и сочетание этих способов для уменьшения размера основной версии строки. TOAST имеет собственную версионность. Если длинное значение не изменилось, новая версия основной строки может продолжать ссылаться на существующее значение, экономя место.

## TOAST

Для основной таблицы при необходимости создаётся служебная TOAST-таблица в схеме pg_toast. Pg_table_size включает саму таблицу и её TOAST-часть с индексом TOAST, но не обычные индексы основной таблицы. Практика связывает настройку стратегии хранения с наблюдением того, какие значения фактически попадают в TOAST-таблицу. Перезапуск сервера не входит в перечисленные шаги практического задания.

# Что запомнить

```text
• обычная страница PostgreSQL — 8 КБ
• большие relations делятся на файловые сегменты
• FSM ищет свободное место, VM хранит признаки all-visible/all-frozen
• `ctid` — физический адрес версии строки и не является стабильным бизнес-идентификатором
• TOAST позволяет хранить значения, которые не помещаются удобно в строку страницы
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
