# 6. Очистка и обслуживание

## 1. Тема

MVCC оставляет после изменений старые версии строк. Пока они нужны снимкам транзакций, удалять их нельзя; позднее они становятся мёртвыми. Если их не обслуживать, таблицы и индексы будут разрастаться, статистика устареет, а старые идентификаторы транзакций создадут риск wraparound.

Поэтому VACUUM — не одна операция, а часть набора периодических задач:

```text
удаление мёртвых версий
        +
visibility map
        +
free space map
        +
ANALYZE
        +
freeze старых XID
```

# 2. Механизм

## Обычный `VACUUM`

Очистка удаляет мёртвые версии строк из таблиц и ненужные индексные записи. Без списка таблиц команда обрабатывает все таблицы текущей базы, которые пользователь имеет право вакуумировать; при необходимости можно указать конкретные таблицы. Освободившееся место становится доступным для повторного использования, но файл таблицы обычно **не уменьшается физически**. Обычный VACUUM может работать параллельно с обычным чтением и записью, однако `VACUUM` нельзя выполнять внутри блока транзакции.

```sql
VACUUM table_name;
```

Для регулярного обслуживания это нормальное поведение: цель — сделать внутреннее пространство снова пригодным для новых версий строк, а не постоянно переписывать файл.

## Карта видимости

Visibility map отмечает страницы таблицы, на которых все версии строк видимы во всех снимках.

Она используется для двух важных оптимизаций:

```text
VACUUM
→ может не заходить в заведомо полностью видимые страницы

index-only scan
→ может не читать страницу таблицы для проверки видимости,
  если нужная страница отмечена all-visible
```

Карта видимости существует для таблиц, а не для индексов.

## Карта свободного пространства

Free space map хранит сведения о свободном месте внутри страниц. При вставке новой версии строки PostgreSQL может быстро найти страницу, куда она поместится.

```text
очистка
→ свободного места больше
→ FSM обновляется
→ следующая вставка быстрее находит подходящую страницу
```

FSM существует и для таблиц, и для индексов.

## `ANALYZE`

Планировщику нужна статистика о данных: числе строк и распределении значений. `ANALYZE` собирает её по выборке строк и обновляет статистику для планировщика.

```sql
ANALYZE table_name;
VACUUM ANALYZE table_name;
```

`VACUUM ANALYZE` сначала выполняет очистку, а затем `ANALYZE`. Статистика планировщика хранится в системном каталоге `pg_statistic`; `ANALYZE` можно ограничить конкретными таблицами и даже отдельными столбцами.

## Заморозка XID

Обычный XID PostgreSQL имеет 32-битный диапазон и циклически переполняется. Очень старые версии строк нужно **замораживать**, чтобы их видимость больше не зависела от исходного номера транзакции и они считались видимыми во всех подходящих снимках, не превращаясь после wraparound в версии «из будущего».

VACUUM выполняет freeze старых версий; карта видимости также позволяет отмечать страницы как all-frozen и не просматривать их без необходимости при последующей заморозке.

Если заморозку слишком долго не выполнять, PostgreSQL в конечном счёте вынужден ограничить работу, чтобы не допустить потери корректности данных.

## Autovacuum

Обычное регулярное обслуживание выполняет подсистема autovacuum.

```text
autovacuum launcher
→ выбирает базы для обслуживания

        ↓

autovacuum worker
→ обслуживает конкретную базу / объекты
```

Autovacuum реагирует на объём изменений и запускает VACUUM/ANALYZE автоматически. Для его работы важны параметры `autovacuum` и `track_counts`; отключение любого из них отключает обычный механизм автоочистки.

Ручные команды всё равно остаются полезны:

```sql
VACUUM;
ANALYZE;
VACUUM ANALYZE;
```

# 3. Разрастание

## Почему появляется bloat

Разрастание — это ситуация, когда физический объём таблицы или индекса существенно больше пространства, занятого полезными актуальными данными.

Типичные причины из занятия:

```text
неподходящая настройка autovacuum
массовые изменения данных
долгие транзакции
```

Последствия:

```text
лишнее дисковое пространство
больше резервных копий
медленнее последовательное чтение
хуже эффективность индексного доступа
```

Обычный VACUUM освобождает место **внутри** файла, поэтому размер файла ОС обычно не уменьшается. В материалах приведён запрос из PostgreSQL Wiki для приблизительной оценки bloat, а расширение `pgstattuple` позволяет измерять физическое состояние отношения непосредственно. `pgstattuple` возвращает, в частности, длину отношения, число и долю живых и мёртвых версий, а также объём и долю свободного пространства; для диагностики полезны поля `dead_tuple_count`, `dead_tuple_percent`, `free_space` и `free_percent`. Вариант `pgstattuple_approx` избегает полного сканирования всей таблицы и часть показателей получает приблизительно.

## `VACUUM FULL`

Чтобы физически уплотнить разросшуюся таблицу, можно использовать:

```sql
VACUUM FULL table_name;
```

Он переписывает таблицу и требует эксклюзивной блокировки, поэтому значительно тяжелее обычного VACUUM и применяется как специальная операция, а не как ежедневное обслуживание. На время переписывания нужна дополнительная дисковая ёмкость.

## Индексы: `REINDEX`

Индекс может потребовать перестроения после разрастания, повреждения или изменения некоторых параметров хранения:

```sql
REINDEX INDEX index_name;
REINDEX TABLE table_name;
```

`REINDEX TABLE` перестраивает все индексы указанной таблицы. Обычный `REINDEX` блокирует использование перестраиваемого индекса и может задерживать изменения таблицы. В PostgreSQL есть вариант `REINDEX ... CONCURRENTLY`, который позволяет продолжать обычные изменения ценой более долгой и сложной операции; материал отдельно отмечает его ограничения и возможность неуспеха.

`pg_repack` — стороннее расширение для перестроения таблиц и индексов с минимизацией длительных эксклюзивных блокировок; в занятии оно приведено как практическая альтернатива тяжёлой блокирующей переупаковке.

Для оценки размера объектов в практике используются функции вроде:

```sql
pg_table_size(...)
pg_indexes_size(...)
```

# Что запомнить

```text
• VACUUM удаляет мёртвые версии и делает место повторно используемым
• обычный VACUUM обычно не уменьшает файл на уровне ОС
• visibility map ускоряет VACUUM и index-only scan
• free space map помогает находить место для новых версий строк
• ANALYZE обновляет статистику планировщика
• freeze защищает от wraparound XID
• autovacuum launcher запускает worker-процессы и должен работать постоянно
• VACUUM FULL физически переписывает таблицу и сильно блокирует её
• REINDEX обслуживает разросшиеся индексы
```
