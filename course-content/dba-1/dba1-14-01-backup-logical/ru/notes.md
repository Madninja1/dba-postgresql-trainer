# 17. Логическое резервное копирование

## 1. Тема

Логическая резервная копия сохраняет не файлы `PGDATA`, а логическое описание объектов и данных. В простейшем случае это SQL-команды, которые можно выполнить на другом сервере и заново создать нужное состояние.

Главная модель:

```text
database objects/data
       ↓
COPY / pg_dump / pg_dumpall
       ↓
SQL script or archive
       ↓
psql / pg_restore
       ↓
restored objects
```

Логический подход гибкий: можно копировать отдельные объекты или базы, переносить данные на другую архитектуру и обычно восстанавливать дамп на более новой основной версии PostgreSQL. Цена этой гибкости — сравнительно невысокая скорость на больших объёмах и отсутствие произвольной точки восстановления: дамп отражает состояние на момент его создания.

# 2. Механизм

## `COPY` и `\copy`

`COPY` предназначен для быстрого обмена содержимым таблицы с файлом, потоком стандартного ввода-вывода или программой. Он умеет:

- выгружать таблицу;
- выгружать результат запроса;
- загружать строки в уже существующую таблицу;
- работать с текстовым, CSV и двоичным форматами.

При загрузке `COPY FROM` существующие строки не удаляются — новые строки добавляются в таблицу.

Ключевое различие между двумя вариантами:

```text
SQL COPY       → файл открывает сервер PostgreSQL
psql \copy     → файл открывает клиент psql
```

Поэтому для серверного `COPY` файл должен быть доступен пользователю ОС, под которым работает PostgreSQL, а для `\copy` — пользователю на клиентской машине, запустившему `psql`.

## `pg_dump`

`pg_dump` — основной инструмент логического резервирования одной базы данных. Он работает как обычный клиент PostgreSQL и создаёт согласованный снимок базы на момент начала выгрузки, не блокируя обычную работу с данными.

Основные варианты результата:

- обычный SQL-скрипт;
- архив в custom- или directory-формате;
- выборочный дамп отдельных схем, таблиц, только DDL или только данных.

SQL-дамп восстанавливается через `psql`, а архивные форматы — через `pg_restore`. Формат с оглавлением удобен тем, что набор объектов можно выбирать уже при восстановлении и для подходящих форматов использовать параллельную работу.

## Восстановление дампа

Для восстановления полного дампа отдельной базы целевую БД обычно создают из `template0`, чтобы изменения локального `template1` не дублировались с объектами из дампа.

До восстановления должны существовать кластерные зависимости, которые `pg_dump` одной базы не сохраняет, прежде всего:

- роли-владельцы и роли, которым выданы права;
- необходимые табличные пространства.

Текстовый дамп удобно выполнять через `psql -X`, исключая влияние пользовательского `.psqlrc`. Для контролируемого восстановления полезно прекращать выполнение после первой ошибки (`ON_ERROR_STOP`) или выполнять весь дамп одной транзакцией, если такой режим подходит задаче.

После большого восстановления имеет смысл выполнить `ANALYZE`, чтобы оптимизатор получил актуальную статистику.

## `pg_dumpall`

`pg_dumpall` предназначен для логической копии всего кластера. Он последовательно вызывает `pg_dump` для баз и дополнительно сохраняет глобальные объекты уровня кластера:

- роли;
- табличные пространства;
- права на параметры конфигурации.

Результат `pg_dumpall` — только SQL-скрипт, поэтому параллельное восстановление архивного формата здесь недоступно. Для больших кластеров часто удобнее разделить задачу:

```bash
pg_dumpall --globals-only > globals.sql
pg_dump -Fc -f appdb.dump appdb
```

`pg_dumpall` должен иметь доступ ко всем сохраняемым объектам; для полной копии его обычно запускают с правами суперпользователя. При восстановлении глобальных объектов такие права также требуются.

# 3. Практический ориентир

```bash
# SQL-дамп одной базы
pg_dump appdb > appdb.sql
createdb -T template0 appdb_restore
psql -X --set ON_ERROR_STOP=on -d appdb_restore -f appdb.sql

# custom archive
pg_dump -Fc -f appdb.dump appdb
pg_restore -d appdb_restore -j 4 appdb.dump

# только глобальные объекты кластера
pg_dumpall --globals-only > globals.sql
```

# Что запомнить

```text
• логическая копия переносима и может быть выборочной, но обычно медленнее физической
• `COPY` открывает файл на сервере, `\copy` — на стороне клиента psql
• `pg_dump` сохраняет одну БД и создаёт согласованный снимок без остановки обычной работы
• SQL-дамп восстанавливается через psql, архивные форматы — через pg_restore
• целевую БД для полного восстановления обычно создают из template0
• роли и tablespaces — глобальные объекты; их резервируют отдельно или через pg_dumpall
• pg_dumpall выдаёт SQL-скрипт и не даёт параллельного архивного восстановления
```

Перед тестом важно понимать не только команды, но и **уровень копирования, переносимость, ограничения и требования к восстановлению**.
