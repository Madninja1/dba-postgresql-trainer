# 15. Роли и аутентификация

## 1. Тема

В PostgreSQL нет отдельного типа «пользователь» вне системы ролей: роль с атрибутом `LOGIN` может подключаться к серверу. Сам факт подключения определяется не только ролью и паролем, но и первым подходящим правилом `pg_hba.conf`.

Главная модель:

```text
client connection
 host / db / user / address
          ↓
pg_hba.conf: first matching rule
          ↓
auth method
          ↓
role with LOGIN
          ↓
session
```

# 2. Механизм

## Роли и атрибуты

Роль рассматривается и как пользователь, способный подключаться к СУБД, и как элемент иерархии ролей, удобной для управления доступом. Слайд перечисляет LOGIN, SUPERUSER, CREATEDB и CREATEROLE; CREATEROLE относится к управлению ролями, а не к табличным пространствам. LOGIN непосредственно обозначает возможность роли входить в сеанс PostgreSQL.

CREATE ROLE создаёт роль и позволяет определить её свойства. SUPERUSER не выдаётся автоматически.

## `pg_hba.conf`

Конспект определяет pg_hba.conf как файл host-based authentication, содержащий правила подключения. Строка pg_hba.conf сопоставляется с параметрами подключения, включая тип, базу, пользователя и при сетевом подключении адрес. Порядок записей принципиален: выбирается первая строка, соответствующая параметрам подключения.

После выбора первой строки выполняются соответствующие проверки, а следующие строки уже не рассматриваются. На схеме pg_hba.conf тип local сопоставлен локальному сокету, а host — TCP/IP. Правила pg_hba.conf образуют явный список допуска. Если подходящей записи нет, подключение не разрешается.

Подключение определяется сразу несколькими проверками: правилом pg_hba.conf, методом аутентификации и полномочиями роли. Практическая часть строится вокруг создания ролей, изменения pg_hba.conf и проверки поведения различных правил аутентификации.

## Практический ориентир

```bash
CREATE ROLE app LOGIN PASSWORD 'secret';
CREATE ROLE dba NOLOGIN;
GRANT dba TO app;

# pg_hba.conf
# TYPE  DATABASE  USER  ADDRESS       METHOD
host    appdb     app   10.0.0.0/24   scram-sha-256
```

# 3. Важные детали

## Методы аутентификации

Слайд прямо сопоставляет trust с разрешением, reject с отказом, peer с проверкой через ОС, а scram-sha-256 и md5 — с парольной аутентификацией. В материале peer описан как метод, который получает имя пользователя от операционной системы. На слайде scram-sha-256 и md5 объединены как методы, при которых у клиента запрашивается пароль.

Практика предлагает сначала убедиться, что вход через peer невозможен без нужного отображения пользователя ОС.

# Что запомнить

```text
• роль с `LOGIN` может устанавливать сеанс; роль без LOGIN удобна как групповая
• `pg_hba.conf` проверяется сверху вниз и применяется первое совпавшее правило
• `trust` не проверяет пароль и требует очень ограниченного применения
• для паролей современный выбор — SCRAM-SHA-256
• аутентификация отвечает «кто подключается», а привилегии — «что он может делать после подключения»
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
