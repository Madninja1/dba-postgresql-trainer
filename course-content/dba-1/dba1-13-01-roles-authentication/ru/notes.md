# 15. Роли и аутентификация

## 1. Тема

В PostgreSQL «пользователь» — это роль с возможностью входа (`LOGIN`). Роли существуют на уровне всего кластера, а не отдельной базы данных, и концептуально не обязаны совпадать с пользователями операционной системы.

Успешное подключение — это цепочка нескольких проверок:

```text
client
  ↓
server listens on this interface?
  ↓
first matching pg_hba.conf rule
  ↓
authentication method
  ↓
role has LOGIN
  ↓
role has CONNECT to database
  ↓
session
```

Аутентификация отвечает на вопрос «кто подключается», а объектные привилегии следующей темы — «что эта роль сможет делать после входа».

---

# 2. Роли и атрибуты

Роль используется в двух основных качествах:

1. как пользователь СУБД;
2. как контейнер прав/группа, в которую включаются другие роли.

При `initdb` создаётся начальная роль-суперпользователь с `LOGIN`; обычно она называется `postgres`.

Основные атрибуты занятия:

| Атрибут | Назначение |
|---|---|
| `LOGIN` / `NOLOGIN` | возможность устанавливать сеанс |
| `SUPERUSER` | обход обычных проверок доступа |
| `CREATEDB` | создание баз данных |
| `CREATEROLE` | управление ролями в разрешённых пределах |

Связанная документация также показывает другие важные свойства: `INHERIT`, `REPLICATION`, `BYPASSRLS`, `CONNECTION LIMIT`, пароль и срок его действия.

```sql
CREATE ROLE app LOGIN PASSWORD 'secret';
CREATE ROLE readers NOLOGIN;
```

`CREATE ROLE` без явного `LOGIN` создаёт роль, которая не может входить в систему как обычный пользователь.

# 3. Подключение и `pg_hba.conf`

## Выбор правила

`pg_hba.conf` просматривается **сверху вниз**. Сервер выбирает первую запись, соответствующую параметрам подключения:

```text
TYPE
DATABASE
USER
ADDRESS   (для сетевых подключений)
METHOD
```

После выбора первой строки следующие записи уже не рассматриваются — даже если аутентификация по выбранному правилу завершилась ошибкой. Если ни одно правило не подошло, подключение отклоняется.

Основные типы:

```text
local → Unix-domain socket
host  → TCP/IP
```

Пример:

```conf
# TYPE  DATABASE  USER  ADDRESS       METHOD
local   all       postgres            peer
local   all       all                 peer
host    all       all   127.0.0.1/32  scram-sha-256
host    all       all   ::1/128       scram-sha-256
```

Изменения `pg_hba.conf` должны быть перечитаны сервером:

```sql
SELECT pg_reload_conf();
```

или эквивалентным `reload` через утилиту управления сервером.

`listen_addresses` решает другую задачу: на каких сетевых интерфейсах сервер вообще принимает TCP-соединения. `pg_hba.conf` затем решает, какие из пришедших подключений разрешать и как их аутентифицировать.

# 4. Методы аутентификации

Основные методы из занятия:

```text
trust          → разрешить без проверки пароля
reject         → безусловно отклонить
scram-sha-256  → парольная аутентификация SCRAM
md5            → старый парольный метод
peer           → получить имя локального пользователя от ОС
```

Для `peer` имена пользователя ОС и роли PostgreSQL могут совпадать напрямую либо сопоставляться через карту в `pg_ident.conf`.

В PostgreSQL 16 SCRAM-SHA-256 является современным вариантом парольной аутентификации; MD5 сохранён для совместимости, но считается устаревающим подходом.

---

# 5. Пароли ролей и клиентское хранение

Если выбран парольный метод, у роли должен быть задан пароль. Сервер хранит не открытый пароль, а его verifier/хеш в системном каталоге `pg_authid`, доступ к которому ограничен.

Клиент может получить пароль тремя показанными в занятии способами:

```text
ввод вручную
PGPASSWORD
~/.pgpass
```

Формат строки `.pgpass`:

```text
host:port:database:user:password
```

На Unix файл должен быть доступен только владельцу (`0600`); при слишком широких правах PostgreSQL игнорирует его.

`PGPASSWORD` удобен для кратких сценариев, но материал не рекомендует его как безопасное постоянное хранилище секрета.

# 6. Практика с `peer`

Практическое задание показывает важное различие:

```text
pg_hba.conf выбирает метод peer
        ≠
имя роли автоматически совпадёт с пользователем ОС
```

Для сопоставления можно использовать `pg_ident.conf`, например:

```conf
# MAPNAME  SYSTEM-USERNAME  PG-USERNAME
stmap      student          alice
stmap      student          bob
```

и указать карту в соответствующем правиле `pg_hba.conf`.

---

# Что запомнить

```text
• роли глобальны для кластера и не обязаны совпадать с пользователями ОС
• `LOGIN` делает роль способной устанавливать сеанс
• `pg_hba.conf` читается сверху вниз; работает только первое совпавшее правило
• изменения `pg_hba.conf` требуют reload, а `listen_addresses` отвечает за сетевое прослушивание
• `trust`, `reject`, `peer`, SCRAM и MD5 решают разные задачи аутентификации
• пароль можно вводить вручную, передавать через PGPASSWORD или хранить в `.pgpass`
• `.pgpass` в Unix должен иметь права `0600`
• успешная аутентификация ещё не означает наличие прав на объекты
```
