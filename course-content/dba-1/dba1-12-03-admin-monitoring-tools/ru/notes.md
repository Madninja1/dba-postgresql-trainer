# 14. Средства мониторинга и статистика запросов

## 1. Тема

Внешний мониторинг собирает метрики во времени и строит алерты, а `pg_stat_statements` агрегирует статистику SQL внутри PostgreSQL. Это дополняющие инструменты: один показывает состояние системы, другой помогает найти запросы, создающие основную нагрузку.

Главная модель:

```text
PostgreSQL
├─ exporters/agents → monitoring system → dashboards/alerts
└─ pg_stat_statements → normalized query stats
```

# 2. Механизм

## Внешние системы мониторинга

Материал подчёркивает необходимость системы, которая собирает разнообразные метрики, сохраняет их историю и отображает результаты в удобной форме. Zabbix, Munin и Cacti приведены как примеры универсальных систем мониторинга. В блоке специализированных систем PostgreSQL перечислены pg_profile, pgpro_pwr, PGObserver, PoWA и OPM.

Все четыре названия присутствуют на слайде специализированных систем мониторинга PostgreSQL. `pg_dump` не относится к перечисленным в лекции системам мониторинга PostgreSQL. Представление позволяет анализировать накопленные характеристики выполнения запросов, а не только текущую активность. На слайде подчёркивается именно история метрик и их визуализация, что позволяет анализировать изменения во времени.

Лекция описывает практический мониторинг как сбор разных метрик с PostgreSQL и ОС с последующим хранением истории и визуализацией. Pgpro_pwr включён в конспект среди специализированных решений мониторинга и сопровождается ссылкой на документацию Postgres Pro Enterprise. Слайд разделяет универсальные, облачные и специализированные PostgreSQL-средства.

Финальный блок занятия подчёркивает систематический мониторинг: сбор разных классов показателей, историю и удобное представление информации.

## Подключение `pg_stat_statements`

Pg_stat_statements предназначено для накопления статистики планирования и выполнения SQL-операторов. Именно такая последовательность составляет дополнительную практику занятия. Удаление расширения не входит в указанную последовательность практической работы. Конспект прямо указывает на необходимость добавить расширение в shared_preload_libraries перед CREATE EXTENSION.

В практическом комментарии прямо сказано изменить shared_preload_libraries с последующей перезагрузкой сервера. Pg_stat_statements собирает агрегированные показатели выполнения запросов, позволяющие искать часто выполняемые и дорогостоящие операции. Pg_stat_statements накапливает статистику по множеству выполнений запросов, поэтому подходит для анализа совокупной нагрузки, а не только текущего состояния.

## Нормализация и `queryid`

## Практический ориентир

```bash
# postgresql.conf / ALTER SYSTEM
shared_preload_libraries = 'pg_stat_statements'

CREATE EXTENSION pg_stat_statements;

SELECT queryid, calls, total_exec_time, mean_exec_time, rows, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

# Что запомнить

```text
• внешний мониторинг нужен для истории, графиков и алертов
• `pg_stat_statements` агрегирует похожие запросы и показывает их совокупную стоимость
• для загрузки модуля требуется `shared_preload_libraries`, а объект расширения создаётся отдельно в БД
• смотреть только на среднее время недостаточно: важны calls, total time, I/O и rows
• статистику можно сбрасывать, поэтому период наблюдения всегда имеет значение
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
