# 1. Инструменты и установка

## 1. Тема

Первый блок DBA1 связывает установку PostgreSQL с устройством экземпляра сервера. Важно различать программу сервера, каталог данных и кластер баз данных, а затем понимать, какими инструментами кластер создаётся, запускается, останавливается и проверяется.

Главная модель:

```text
PostgreSQL binaries
        ↓
initdb
        ↓
кластер баз данных (PGDATA)
        ↓
pg_ctl / systemd
        ↓
работающий экземпляр сервера
```

# 2. Механизм

## Сборка из исходного кода

Традиционный способ сборки PostgreSQL из исходного кода основан на GNU Make и Autoconf. Начиная с PostgreSQL 16 можно использовать систему сборки Meson. Readline предоставляет редактирование командной строки, историю команд и автодополнение.

По умолчанию Meson использует Ninja. После настройки каталога сборки компиляция выполняется командой ninja. Краткая процедура традиционной сборки включает конфигурирование через ./configure, сборку командой make и установку через make install. --no-sync отключает ожидание надёжной записи файлов. Он полезен главным образом при тестировании и в режиме --check не оказывает влияния.

Материал подчёркивает пользу понимания сборки из исходников для нестандартных параметров, специфичных архитектур и общего понимания процесса установки. Git даёт доступ к любому коммиту, но требует дополнительных инструментов; в архиве часть генерируемых файлов уже подготовлена. В материале к обязательному ПО отнесены tar, gzip/bzip2, GNU make и компилятор C.

Zlib, lz4 и zstd используются для сжатия. Readline нужна прежде всего для удобства интерактивной командной строки; материал отмечает, что без запуска psql в консоли она может быть не нужна. Perl, Python и Tcl нужны для использования процедурных языков PL/Perl, PL/Python и PL/Tcl.

В блоке дополнительного ПО материал связывает Kerberos, OpenSSL, OpenLDAP и PAM с аутентификацией и шифрованием. ICU указана как библиотека для кроссплатформенной поддержки Unicode. После сборки и до установки полезно выполнить `make check`; регрессионные тесты запускаются обычным пользователем, не `root`.

Make world включает дополнительные модули и документацию, а make world-bin — дополнительные модули без документации. Параметр --prefix задаёт префикс дерева установки вместо значения по умолчанию /usr/local/pgsql. Параметры `--with-python`, `--with-lz4` и `--with-zstd` включают соответствующие возможности при конфигурировании сборки.

--without-readline запрещает использование Readline/libedit, поэтому в psql пропадают редактирование командной строки и история. Meson setup создаёт и настраивает каталог сборки; аргумент builddir для этой команды обязателен. После первоначального meson setup настройки каталога сборки изменяют командой meson configure.

Для Meson регрессионные тесты после сборки и до установки запускаются через `meson test`; их также выполняют обычным пользователем. Команды `ninja install`, `ninja clean` и `ninja uninstall` используются соответственно для установки, очистки результатов сборки и удаления установленного набора. Глава runtime оговаривает, что готовый продукт обычно интегрирован производителем с системными механизмами установки и запуска, поэтому детали могут отличаться от «чистой» сборки.

--no-sync может ускорить изменяющие операции ценой риска при сбое и не рекомендуется в production; для --check он не влияет.

## Создание кластера: `initdb`

Initdb создаёт новый кластер баз данных PostgreSQL. Initdb выполняют от имени владельца будущего серверного процесса; запуск от системного суперпользователя не допускается. Каталог хранения данных задаётся параметром -D/--pgdata либо переменной окружения PGDATA.

По умолчанию initdb использует провайдер локалей libc. --no-sync отключает ожидание надёжной записи файлов на диск. Это может ускорить initdb, но повышает риск повреждения данных при сбое и не рекомендуется для production. -U/--username задаёт имя начального суперпользователя; по умолчанию используется имя пользователя ОС, запускающего initdb.

-X/--waldir задаёт каталог, в котором будет храниться журнал предзаписи WAL. --pwfile заставляет initdb прочитать пароль начального суперпользователя из первой строки указанного файла. --sync-only синхронизирует файлы базы с диском и завершает работу, не выполняя остальные операции initdb.

Размер WAL-сегмента задаётся при initdb; по умолчанию это 16 МБ, а изменить его позднее этим параметром нельзя.

## Управление сервером: `pg_ctl`

Pg_ctl предназначен для инициализации и управления сервером: запуска, остановки, restart, reload, status, promote и других операций. Pg_ctl stop поддерживает режимы smart, fast и immediate. Если -m не указан, pg_ctl использует режим fast.

Smart shutdown запрещает новые подключения и ожидает, пока существующие клиенты отключатся. Immediate shutdown немедленно прерывает серверные процессы без штатной остановки, поэтому при следующем запуске потребуется crash recovery. Reload посылает серверу SIGHUP, после чего PostgreSQL перечитывает postgresql.conf, pg_hba.conf и другие конфигурационные файлы.

Для работающего сервера pg_ctl status выводит PID и параметры командной строки, с которыми он был запущен. Restart представляет собой остановку и последующий запуск сервера и может применяться для изменений, требующих полного перезапуска. Promote выводит сервер из режима резерва и переводит его к обычным операциям чтения/записи.

При запуске сервера pg_ctl параметр -l позволяет направить вывод сервера в указанный файл журнала.

## Практический ориентир

```bash
# традиционная сборка
./configure --prefix=/usr/local/pgsql
make
make check
make install

# Meson/Ninja
meson setup builddir
ninja -C builddir
meson test -C builddir
ninja -C builddir install

# новый кластер
initdb -D /srv/postgresql/data -k

# управление
pg_ctl -D /srv/postgresql/data -l server.log start
pg_ctl -D /srv/postgresql/data reload
pg_ctl -D /srv/postgresql/data stop -m fast
```

# 3. Важные детали

## Контрольные суммы: `pg_checksums`

-k/--data-checksums включает контрольные суммы страниц данных; при включении они применяются ко всем объектам во всех базах данных кластера. Перед запуском pg_checksums сервер PostgreSQL должен быть остановлен в штатном режиме. Pg_checksums позволяет проверить, включить или отключить контрольные суммы данных кластера.

При включении pg_checksums рассчитывает контрольную сумму каждого блока отношений и перезаписывает блоки; при отключении изменяется только pg_control. Практический порядок: остановить сервер, проверить состояние контрольных сумм, включить их и затем запустить сервер. --check является режимом по умолчанию; код завершения показывает, обнаружены ли ошибки контрольных сумм.

Операции включения и отключения checksums могут быть длительными; сервер должен оставаться остановленным. При физической репликации режим checksums на узлах должен быть согласован. Если pg_checksums прерван при включении или отключении, состояние настройки checksums остаётся прежним и операцию можно повторить.

## Пакетная установка, Ubuntu и облако

Пакетная установка обычно проще в сопровождении и обновлении; для получения актуальных версий PostgreSQL часто используют репозиторий PGDG. В Ubuntu pg_createcluster оборачивает initdb; пакет создаёт кластер main, checksums по умолчанию выключены, а запуск/останов интегрирован с ОС. `pg_createcluster` и `pg_dropcluster` специфичны для Debian/Ubuntu; в других системах используют `initdb` и соответствующие средства ОС.

Для Ubuntu в пакетном дистрибутиве используется обёртка pg_ctlcluster; в других системах pg_ctl может использоваться непосредственно. В VM администратор получает полный контроль над ОС ценой больших накладных расходов; в DBaaS часть доступа ограничена, а больше эксплуатационной ответственности берёт на себя провайдер.

## Кластер и сервер — разные сущности

Один экземпляр PostgreSQL одновременно работает с несколькими базами данных; этот набор баз данных называется кластером баз данных. Кластер — это данные в файлах, а сервер или экземпляр сервера — программа, управляющая этим кластером.

# Что запомнить

```text
• кластер БД — это набор данных в PGDATA; сервер — процесс, который этим кластером управляет
• `initdb` создаёт кластер и не запускается от root
• `pg_ctl` управляет жизненным циклом сервера; штатный default shutdown — `fast`
• checksums включаются на весь кластер и `pg_checksums` запускается на чисто остановленном сервере
• сборка из исходников нужна не всегда, но полезна для понимания возможностей и нестандартных конфигураций
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
