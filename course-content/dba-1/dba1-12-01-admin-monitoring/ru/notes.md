# 12. Мониторинг PostgreSQL

## 1. Тема

Мониторинг PostgreSQL начинается с двух уровней наблюдения:

- операционная система показывает процессы, CPU, память, ввод-вывод и свободное место;
- сам PostgreSQL показывает текущие сеансы, ожидания, накопительные счётчики и прогресс длительных операций.

Главная модель:

```text
OS tools
ps / pgrep / top / iostat / vmstat / sar / df / du
                    ↕ PID
PostgreSQL
pg_stat_activity
pg_stat_* counters
pg_stat_progress_*
```

Один источник не заменяет другой. Высокая загрузка диска видна снаружи, а конкретный backend, запрос или ожидание — изнутри PostgreSQL.

# 2. Механизм

## Процессы и ресурсы ОС

Для просмотра процессов в материале используются `ps` и `pgrep`. PostgreSQL умеет менять заголовок процесса: при включённом `update_process_title` в выводе `ps` можно видеть назначение и текущее состояние серверного процесса. Параметр `cluster_name` помогает отличать экземпляры PostgreSQL друг от друга.

Для ресурсов ОС материал приводит:

```text
CPU / I/O / память: iostat, vmstat, sar, top
занятое место:      du
свободное место:    df
квоты ОС:           quota
```

PostgreSQL не предоставляет дисковые квоты для отдельных ролей: серверные процессы обычно работают от одного пользователя ОС, поэтому свободное место и квоты надо контролировать на уровне ОС и файловой системы.

## Настройки сбора статистики

Количество собираемой информации регулируется параметрами сервера:

| Параметр | Что включает |
|---|---|
| `track_activities` | текущие команды и активности серверных процессов |
| `track_counts` | накопительную статистику обращений к таблицам и индексам |
| `track_functions` | статистику вызовов пользовательских функций |
| `track_io_timing` | измерение времени операций ввода-вывода блоков |
| `track_wal_io_timing` | измерение времени операций ввода-вывода WAL |

`track_functions`, `track_io_timing` и `track_wal_io_timing` в материале отмечены как выключенные по умолчанию: дополнительная статистика имеет собственную цену.

## `pg_stat_activity`

`pg_stat_activity` показывает обслуживающие и фоновые процессы и их текущую активность. Для диагностики особенно полезны:

```sql
SELECT pid,
       usename,
       datname,
       state,
       wait_event_type,
       wait_event,
       query_start,
       xact_start,
       query
FROM pg_stat_activity;
```

Это текущая активность, а не накопительные счётчики. Информация о текущем запросе, собираемая при `track_activities`, отличается от обычной накопительной статистики тем, что должна отражать текущее состояние процесса.

## Накопительная статистика

Серверные процессы передают накопленную статистику в разделяемую память не после каждого отдельного события. В PostgreSQL 16 передача выполняется перед переходом процесса в ожидание и не чаще интервала `PGSTAT_MIN_INTERVAL` — обычно около одной секунды.

При штатной остановке накопительная статистика сохраняется в `PGDATA/pg_stat/` и загружается при следующем старте. При аварийном завершении такие счётчики могут быть потеряны.

Для таблиц можно анализировать, например:

```text
n_tup_ins   — вставленные строки
n_tup_del   — удалённые строки
n_live_tup  — оценка живых строк
n_dead_tup  — оценка мёртвых версий
```

Именно эти показатели используются в практической работе занятия: выполнить `INSERT`, `DELETE`, затем `VACUUM` и сравнить статистику.

## Согласованность снимка статистики

`stats_fetch_consistency` определяет кеширование накопительной статистики в текущей транзакции:

```text
none      → не кешировать уже полученные значения
cache     → кешировать данные по отдельным запрошенным объектам
snapshot  → использовать единый снимок статистики текущей БД
```

По умолчанию используется `cache`. Закешированные значения живут до конца транзакции. Функция:

```sql
SELECT pg_stat_clear_snapshot();
```

сбрасывает текущий статистический снимок/кеш, поэтому следующее обращение получает свежие данные согласно выбранному режиму.

# 3. Прогресс длительных операций

Для ряда потенциально долгих команд PostgreSQL предоставляет отдельные `pg_stat_progress_*` представления:

| Операция | Представление |
|---|---|
| `ANALYZE` | `pg_stat_progress_analyze` |
| `CREATE INDEX`, `REINDEX` | `pg_stat_progress_create_index` |
| `VACUUM` / autovacuum | `pg_stat_progress_vacuum` |
| `CLUSTER`, `VACUUM FULL` | `pg_stat_progress_cluster` |
| базовая резервная копия | `pg_stat_progress_basebackup` |
| `COPY` | `pg_stat_progress_copy` |

Обычный долгий `SELECT` не получает автоматически отдельного `pg_stat_progress_*` представления.

## Дополнительная статистика

Сам модуль DBA1 также показывает расширения, дополняющие встроенные представления:

```text
pg_stat_statements → статистика SQL-запросов
pgstattuple         → статистика по версиям строк
pg_buffercache      → содержимое буферного кеша
pg_wait_sampling    → статистика ожиданий
pg_stat_kcache      → CPU и I/O
pg_qualstats        → статистика предикатов
```

`pg_stat_statements` подробно рассматривается далее в отдельном блоке темы.

# 4. Практический ориентир

```sql
-- текущая активность
SELECT pid, usename, datname, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid();

-- статистика базы
SELECT *
FROM pg_stat_database
WHERE datname = current_database();

-- статистика таблицы
SELECT relname, n_tup_ins, n_tup_del, n_live_tup, n_dead_tup
FROM pg_stat_user_tables;

-- прогресс VACUUM
SELECT * FROM pg_stat_progress_vacuum;
```

# Что запомнить

```text
• мониторинг PostgreSQL всегда сочетает уровень ОС и внутренние представления СУБД
• `track_*` определяют, какую статистику сервер вообще собирает
• `pg_stat_activity` показывает текущую активность и ожидания
• накопительная статистика обновляется с задержкой и может кешироваться в транзакции
• `pg_stat_clear_snapshot()` позволяет отбросить текущий кеш статистики
• `pg_stat_progress_*` существует только для поддерживаемого набора длительных операций
• статистику важно сравнивать во времени, а не воспринимать один снимок как полную картину
```
