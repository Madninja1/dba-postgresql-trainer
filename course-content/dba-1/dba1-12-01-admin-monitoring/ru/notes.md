# 12. Мониторинг PostgreSQL

## 1. Тема

Мониторинг начинается с разделения двух уровней: операционная система показывает процессы и ресурсы, а PostgreSQL — текущую активность и накопительную статистику. DBA должен уметь связать серверный backend с SQL-сеансом и понять, является ли проблема CPU, I/O, блокировкой или конкретным запросом.

Главная модель:

```text
OS tools
ps / top / iostat / vmstat / df
        ↕ PID
PostgreSQL
pg_stat_activity
pg_stat_* counters
pg_stat_progress_*
```

# 2. Механизм

## Процессы и ресурсы ОС

Для наблюдения за процессами PostgreSQL материал приводит системные команды ps и pgrep. Именно iostat, vmstat, sar и top перечислены как средства наблюдения за использованием ресурсов ОС. `pg_dump` предназначен для логического резервного копирования, а не для наблюдения за использованием ресурсов ОС. Параметр update_process_title связан с информацией о процессах, видимой средствами операционной системы.

В блоке о дисковом пространстве перечислены df, du и quota; системные представления PostgreSQL не заменяют контроль файловой системы. Эти соответствия непосредственно приведены в таблице представлений для отслеживания длительных команд. В блоке средств ОС cluster_name приводится вместе с update_process_title как параметр, помогающий идентифицировать процессы PostgreSQL.

Материал рассматривает оба уровня как взаимодополняющие: ОС показывает ресурсы и процессы, а PostgreSQL — внутреннее состояние сервера.

## `pg_stat_activity`

Pg_stat_activity относится к динамической статистике и показывает сведения о серверных процессах и их текущей активности. Pg_stat_activity предназначено для анализа процессов и сеансов, включая их состояние и выполняемую работу, а не содержимого страниц данных.

## Накопительная статистика

Конспект показывает передачу накопительной статистики в разделяемую память; обновления выполняются не непрерывно после каждого события.

## Практический ориентир

```bash
SELECT pid, usename, datname, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid();

SELECT * FROM pg_stat_database WHERE datname = current_database();
SELECT * FROM pg_stat_progress_vacuum;
```

# 3. Важные детали

## Прогресс операций

Для VACUUM, включая работу процессов автоочистки, материал указывает pg_stat_progress_vacuum. Для COPY в материале указано представление pg_stat_progress_copy. Список progress-представлений охватывает лишь определённые потенциально длительные операции, а не произвольный SELECT.

Созданию базовой резервной копии соответствует pg_stat_progress_basebackup.

## Снимок статистики

На схеме подсистемы статистики явно перечислены режимы none, cache и snapshot. Конспект специально показывает задержку обновления накопительной статистики и режимы none, cache и snapshot для её чтения.

# Что запомнить

```text
• сначала определяй: проблема на уровне ОС или внутри PostgreSQL
• `pg_stat_activity` показывает текущие сеансы и их состояние
• `pg_stat_*` содержит накопительные счётчики, которые надо интерпретировать в динамике
• `pg_stat_progress_*` показывает прогресс поддерживаемых длительных операций
• PID помогает связать backend PostgreSQL с процессом в ОС
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
