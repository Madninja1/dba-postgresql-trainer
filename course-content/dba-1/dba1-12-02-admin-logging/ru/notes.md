# 13. Журналирование и анализ журнала

## 1. Тема

Журнал сообщений — второй основной источник информации о работе PostgreSQL после статистических представлений. Он нужен для расследования ошибок, подключений, блокировок, медленных запросов, контрольных точек и других событий.

Главная модель:

```text
server processes
      ↓
what to log
      ↓
log_destination
stderr / csvlog / jsonlog / syslog / eventlog
      ↓
logging_collector   (для файлов stderr/csvlog/jsonlog)
      ↓
log_directory / log_filename
      ↓
rotation
      ↓
grep / awk / pgBadger
```

---

# 2. Куда попадают сообщения

## `log_destination`

`log_destination` принимает один или несколько приёмников, разделённых запятыми:

```text
stderr   — стандартный поток ошибок, значение по умолчанию
csvlog   — структурированный CSV
jsonlog  — структурированный JSON
syslog   — системный syslog Unix
 eventlog — журнал событий Windows
```

`csvlog` и `jsonlog` предназначены для работы с включённым коллектором сообщений.

## `logging_collector`

`logging_collector = on` запускает отдельный процесс, который собирает сообщения серверных процессов и записывает `stderr`, `csvlog` и `jsonlog` в файлы.

Ключевые свойства из материала:

- сообщения не должны теряться;
- поэтому при очень большой нагрузке коллектор сам может стать ограничивающим звеном;
- файлы создаются в `log_directory` с именами по `log_filename`.

`syslog` и `eventlog` являются отдельными направлениями и не требуют записи через коллектор в PostgreSQL-файлы.

---

# 3. Что журналировать

Материал подчёркивает, что «писать всё» дорого: журнал занимает место и создаёт I/O. Нужные события выбираются осознанно.

Основные параметры занятия:

| Параметр | Назначение |
|---|---|
| `log_min_messages` | минимальный уровень сообщений сервера |
| `log_min_duration_statement` | журналировать длительность команд не короче заданного времени |
| `log_duration` | писать длительность выполненных команд |
| `log_checkpoints` | события контрольных точек |
| `log_connections`, `log_disconnections` | подключения и отключения |
| `log_lock_waits` | длительные ожидания блокировок |
| `log_statement` | выбранные категории SQL-команд |
| `log_temp_files` | использование временных файлов |

`log_statement` поддерживает уровни `none`, `ddl`, `mod`, `all`. Для поиска медленных запросов обычно полезнее целевой `log_min_duration_statement`, чем безусловное логирование каждого SQL-оператора.

## Контекст строки журнала

`log_line_prefix` добавляет контекст: время, PID/идентификатор сеанса, пользователя, базу, приложение и другие поля. Например:

```conf
log_line_prefix = '%m [%p] %q%u@%d/%a '
```

PID или идентификатор сеанса особенно полезен для связывания записи журнала с `pg_stat_activity` и соседними сообщениями того же backend.

# 4. Файлы и ротация

`log_directory` задаёт каталог, а `log_filename` — имя или маску имени файла. Для встроенной ротации используются:

```text
log_filename
log_rotation_age
log_rotation_size
log_truncate_on_rotation
```

Примеры из занятия:

```text
postgresql-%H.log + 1h → 24 имени файлов по часам
postgresql-%a.log + 1d → 7 имён файлов по дням недели
```

`log_truncate_on_rotation = on` позволяет перезаписывать уже существующий файл при ротации по времени и повторном появлении того же имени.

Альтернатива встроенной ротации — системный `logrotate`. В пакетной установке Ubuntu материал указывает `/etc/logrotate.d/postgresql-common`.

Журнал нельзя рассматривать как безобидный технический файл: он может содержать SQL-текст, параметры и другие чувствительные данные, поэтому права доступа и политика хранения являются частью эксплуатации.

---

# 5. Анализ журнала

Базовые средства:

```text
grep
awk
```

Для специализированного анализа материал использует **pgBadger**. Он строит отчёты по PostgreSQL-журналам, но качество результата зависит от конфигурации логирования.

В исходном занятии отдельно отмечено, что сообщения для pgBadger должны быть на английском. Документация pgBadger также требует распознаваемый `log_line_prefix`; для stderr в нём должны присутствовать как минимум время и идентификатор процесса/сеанса. Для полезного отчёта обычно включают нужные события (`log_checkpoints`, подключения, ожидания блокировок, временные файлы и т. п.).

Не следует одновременно бездумно включать максимальное логирование всеми параметрами: это раздувает журнал и может исказить анализ.

---

# 6. Практический ориентир

```sql
SHOW log_destination;
SHOW logging_collector;
SHOW log_directory;
SHOW log_filename;
SHOW log_line_prefix;
SHOW log_min_duration_statement;

ALTER SYSTEM SET log_min_duration_statement = '500ms';
SELECT pg_reload_conf();
```

Для лабораторной диагностики полезно создать контролируемый deadlock и посмотреть, какие сообщения сервер записывает в журнал.

---

# Что запомнить

```text
• `log_destination` выбирает направления сообщений
• `logging_collector` собирает stderr/csvlog/jsonlog в управляемые файлы
• параметры `log_*` определяют не только место, но и состав журнала
• `log_line_prefix` даёт контекст, необходимый для корреляции событий
• ротация ограничивает рост файлов; внешний вариант — logrotate
• журнал может содержать чувствительные данные и должен быть защищён
• pgBadger требует подходящего формата журнала и английских сообщений
```
