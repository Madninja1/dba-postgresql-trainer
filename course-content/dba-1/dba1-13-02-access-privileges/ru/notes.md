# 16. Привилегии и управление доступом

## 1. Тема

После успешной аутентификации PostgreSQL проверяет права роли на конкретные объекты. Система доступа складывается из:

```text
role attributes
+ role membership
+ ownership
+ object privileges
+ PUBLIC/default privileges
```

Роль может иметь право войти в БД, но не иметь права читать конкретную таблицу; и наоборот, выданный `SELECT` бесполезен, если роль не может подключиться к базе или использовать нужную схему.

---

# 2. Владение и объектные привилегии

Объект получает владельца при создании. Владелец изначально получает применимые права и сохраняет неотъемлемые возможности управления объектом: например, может удалить его или снова выдать себе отозванную обычную привилегию.

Материал выделяет три категории:

```text
SUPERUSER → обычные проверки разграничения доступа не выполняются
owner     → владеет объектом и управляет его правами
others    → работают только в рамках выданных привилегий
```

## Таблицы и представления

Основные права:

```text
SELECT      чтение
INSERT      вставка
UPDATE      изменение
DELETE      удаление
TRUNCATE    опустошение таблицы
REFERENCES  создание внешних ключей
TRIGGER     создание триггеров
```

`SELECT`, `INSERT`, `UPDATE`, `REFERENCES` могут в подходящих случаях назначаться на уровне отдельных столбцов.

## Другие типы объектов

В DBA1 отдельно рассматриваются:

```text
sequence:
  SELECT → currval
  UPDATE → nextval, setval
  USAGE  → currval, nextval

tablespace:
  CREATE

database:
  CONNECT
  CREATE
  TEMPORARY

schema:
  USAGE
  CREATE

function/procedure:
  EXECUTE
```

`CONNECT` к БД не означает `SELECT` таблиц. `USAGE` схемы позволяет обращаться к находящимся в ней объектам, но права на сами объекты проверяются отдельно.

---

# 3. `GRANT`, `REVOKE` и проверка прав

```sql
GRANT SELECT ON app.orders TO reader;
REVOKE UPDATE ON app.orders FROM reader;
```

`GRANT` и `REVOKE` используются и для объектных привилегий, и для членства в ролях.

Документация позволяет выдавать права сразу на набор объектов, например `ALL TABLES IN SCHEMA`, а также передавать право дальнейшей выдачи через `WITH GRANT OPTION`.

Для программной проверки доступны функции семейства `has_*_privilege`, например:

```sql
SELECT has_table_privilege('reader', 'app.orders', 'SELECT');
```

---

# 4. Групповые роли и членство

Отдельного типа «группа» в PostgreSQL нет: групповая роль — обычная роль, обычно с `NOLOGIN`, в которую включаются другие роли.

```sql
CREATE ROLE readers NOLOGIN;
GRANT readers TO alice;
REVOKE readers FROM alice;
```

Роль может входить в несколько других ролей, но циклическое членство запрещено.

Права включающей роли могут использоваться через наследование и/или `SET ROLE` в зависимости от параметров членства. Атрибуты вроде `LOGIN`, `SUPERUSER`, `CREATEDB`, `CREATEROLE` не наследуются как обычные объектные права.

## `PUBLIC`

`PUBLIC` — псевдороль, в которую неявно входят все роли, включая будущие. Право, выданное `PUBLIC`, фактически доступно всем.

PostgreSQL создаёт некоторые права `PUBLIC` автоматически. Для PostgreSQL 16 документация, в частности, указывает:

```text
database            → CONNECT, TEMPORARY
function/procedure  → EXECUTE
language/type       → USAGE
```

У таблиц, схем и последовательностей объектных прав `PUBLIC` по умолчанию нет.

# 5. Предопределённые роли

PostgreSQL предоставляет административные роли, позволяющие делегировать часть возможностей без выдачи `SUPERUSER`, например:

```text
pg_read_all_settings
pg_read_all_stats
pg_stat_scan_tables
pg_read_all_data
pg_write_all_data
pg_read_server_files
pg_write_server_files
pg_execute_server_program
pg_monitor
```

Полный список ролей, включая системные, можно посмотреть в psql:

```text
\duS
```

Конкретные разрешения предопределённых ролей могут меняться между версиями PostgreSQL, поэтому их следует сверять с документацией используемой версии.

# 6. Привилегии по умолчанию

`ALTER DEFAULT PRIVILEGES` меняет права **будущих** объектов. Уже существующие объекты команда не переписывает.

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE writer
IN SCHEMA public
GRANT SELECT ON TABLES TO reader;
```

Важно: учитываются default privileges роли, которая непосредственно создаёт объект. Они не «подтягиваются» автоматически из всех ролей, членом которых является создатель.

Права по умолчанию можно настраивать для таблиц, последовательностей, функций/процедур, типов и схем в пределах возможностей команды.

# 7. Подпрограммы и контекст безопасности

Для функций и процедур основная объектная привилегия — `EXECUTE`.

```text
SECURITY INVOKER  → выполняется с правами вызывающей роли (по умолчанию)
SECURITY DEFINER  → выполняется с правами владельца подпрограммы
```

`SECURITY DEFINER` позволяет предоставить контролируемую операцию над объектами, к которым у вызывающего нет прямого доступа, но увеличивает риск повышения привилегий.

Для безопасной `SECURITY DEFINER` функции нельзя оставлять в `search_path` доступные на запись недоверенным пользователям схемы; `pg_temp` следует помещать в конец безопасного пути. Часто также требуется отозвать автоматически выданный `PUBLIC EXECUTE` и дать `EXECUTE` только нужным ролям.

# 8. Практический ориентир

```sql
CREATE ROLE writer NOLOGIN;
CREATE ROLE reader NOLOGIN;

REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO writer;
GRANT USAGE ON SCHEMA public TO reader;

ALTER DEFAULT PRIVILEGES FOR ROLE writer IN SCHEMA public
GRANT SELECT ON TABLES TO reader;

GRANT writer TO w1;
GRANT reader TO r1;
```

Эта схема отделяет «кто входит» от «какие действия доступны после входа» и позволяет централизованно управлять правами через групповые роли.

---

# Что запомнить

```text
• права зависят от типа объекта: у БД, схемы, последовательности и таблицы разные наборы привилегий
• владелец имеет особые неотъемлемые возможности, SUPERUSER обходит обычные проверки
• `GRANT`/`REVOKE` управляют и объектными правами, и членством ролей
• `PUBLIC` означает все роли; часть прав выдаётся PUBLIC автоматически
• групповые роли уменьшают количество индивидуальных GRANT
• `ALTER DEFAULT PRIVILEGES` действует только на будущие объекты конкретной роли-создателя
• `SECURITY DEFINER` требует защищённого `search_path` и аккуратной выдачи EXECUTE
```
