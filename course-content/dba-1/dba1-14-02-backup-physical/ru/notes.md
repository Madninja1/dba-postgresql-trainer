# 18. Физическое резервное копирование и восстановление

## 1. Тема

Физическая резервная копия сохраняет файлы всего кластера. Она восстанавливается быстро и в сочетании с архивом WAL позволяет получить состояние кластера на нужный момент времени, но не умеет восстанавливать одну отдельную базу и требует совместимой основной версии и архитектуры PostgreSQL.

Главная модель:

```text
primary cluster
   ├─ pg_basebackup → base backup
   └─ WAL → file archive / pg_receivewal

restore:
base backup + WAL
       ↓
recovery
       ↓
consistent cluster
```

# 2. Механизм

## Холодная и горячая копия

Физическое резервирование копирует файлы кластера.

**Холодная копия** создаётся при остановленном сервере. После корректного останова файлы уже согласованы и отдельный набор WAL для приведения копии к согласованному состоянию не нужен. Если снимок получен после аварийного состояния, должны сохраниться WAL, необходимые для crash recovery.

**Горячая копия** создаётся на работающем сервере. Простого `cp` недостаточно: пока разные файлы копируются, сервер продолжает их изменять. Поэтому необходим специальный механизм, который гарантирует наличие WAL за всё время создания копии.

## `pg_basebackup`

`pg_basebackup` создаёт базовую физическую копию работающего кластера целиком. Копировать отдельную базу или отдельную таблицу этим инструментом нельзя.

Утилита подключается через протокол репликации. Для подключения нужны:

- суперпользователь или роль с атрибутом `REPLICATION`;
- разрешение репликационного подключения в `pg_hba.conf`;
- `wal_level = replica` или выше;
- достаточное значение `max_wal_senders`.

В автономной копии необходимые WAL можно получать одновременно с файлами кластера, чтобы после развёртывания копии сервер сам восстановил согласованность.

## Протокол репликации и слот

Протокол репликации используется не только собственно репликами, но и `pg_basebackup`/`pg_receivewal`. Репликационное подключение обслуживает процесс `wal sender`.

Слот репликации хранит позицию, до которой клиент гарантированно получил WAL. Пока нужные записи не подтверждены через слот, сервер не должен удалить соответствующий WAL. Это защищает клиента от разрыва в последовательности журнала, но забытый или остановленный слот способен удерживать большой объём WAL на основном сервере.

## Файловый архив WAL

Непрерывное архивирование сохраняет завершённые сегменты WAL отдельно от кластера.

```conf
wal_level = replica
archive_mode = on
archive_command = 'cp %p /archive/%f'
```

`archive_command` вызывается для завершённого сегмента. Нулевой код возврата означает успешное архивирование; при ошибке PostgreSQL сохраняет сегмент и повторяет попытку позднее. Поэтому неисправный архив способен заполнить `pg_wal`, если проблему долго не устранять.

Файловое архивирование неизбежно имеет задержку: текущий незавершённый WAL-сегмент ещё не передан в архив.

## Потоковый архив: `pg_receivewal`

`pg_receivewal` получает WAL по протоколу потоковой репликации и пишет его в отдельный каталог, не ожидая переключения сегмента. Обычно для надёжности используют слот репликации.

Незаполненный файл имеет суффикс `.partial`; после завершения сегмента он получает обычное имя. При восстановлении последний доступный `.partial` может содержать записи, которых ещё нет в завершённом архивном сегменте.

Каждый `pg_receivewal` занимает `wal sender`, поэтому его нужно учитывать при выборе `max_wal_senders`.

# 3. Восстановление

## Базовая копия + архив

При непрерывном архивировании базовая копия служит стартовой точкой, а последующие WAL доводят её до требуемого состояния.

Типовой порядок:

1. Развернуть базовую копию.
2. Настроить `restore_command` для получения WAL из архива.
3. При необходимости задать целевую точку восстановления.
4. Создать `recovery.signal`.
5. Запустить сервер.

```conf
restore_command = 'cp /archive/%f %p'
```

При recovery сервер сначала использует доступные WAL в `pg_wal`, а отсутствующие сегменты запрашивает через `restore_command`. Если целевая точка не задана, применяются все доступные записи. PITR позволяет остановить воспроизведение на выбранном времени или другой поддерживаемой цели.

После завершения управляемого восстановления сервер переходит к обычной работе и может стать новым основным сервером.

## Практический ориентир

```bash
# базовая копия
pg_basebackup -h primary -D /backup/base -Fp -Xs -P

# потоковый архив
pg_receivewal -h primary -D /archive -S archive_slot

# восстановление
# развернуть /backup/base
# задать restore_command
touch recovery.signal
```

# Что запомнить

```text
• физическая копия относится ко всему кластеру и зависит от совместимости сервера
• горячая базовая копия требует WAL за время копирования
• pg_basebackup и pg_receivewal используют протокол репликации и процессы wal sender
• слот не даёт удалить WAL, который ещё нужен клиенту
• archive_command отправляет завершённые WAL в архив и при ошибке должен быть повторён
• pg_receivewal уменьшает задержку и пишет текущий сегмент как .partial
• restore_command получает WAL при recovery, а recovery.signal включает управляемое восстановление
• base backup + непрерывный WAL позволяют PITR
```

Перед тестом важно уметь восстановить в голове полный путь: **базовая копия → сохранение WAL → recovery → целевая точка**.
