# 9. System Catalog

## 1. Topic

PostgreSQL describes its own structure through system catalogs. Tables in `pg_catalog` store metadata about objects, OIDs link rows across catalogs, and convenient views and psql meta-commands hide part of the internal complexity.

Main model:

```text
SQL object
   ↓ metadata
pg_catalog tables
   ↓ OID references
other catalog rows
   ↓
system views / psql \d*
```

---

# 2. Mechanism

## `pg_catalog` and system tables

The system catalog stores metadata: information about tables, columns, and other PostgreSQL objects. The catalog is accessible through SQL. Clients, including psql and graphical tools, can read it and present the retrieved information in a more convenient form. PostgreSQL's main system catalog is located in the `pg_catalog` schema.

Names of system catalog tables and views begin with `pg_`. For this reason, the material recommends not using that prefix for application objects. Catalog columns commonly use a three-letter prefix, usually related to the catalog name. The material separately notes exceptions such as `oid`. The presentation uses `pg_database.datname` as an example of the convention: the column prefix usually corresponds to the name of the system catalog.

The course practice directly asks students to explore `pg_class`, `pg_tables`, and the full schema list using catalog-inspection tools. Although system catalogs are tables, the documentation explicitly warns that they normally should not be modified manually. SQL commands are intended for changing objects. The system catalog is an active working part of PostgreSQL, not merely a report. SQL commands that create or alter objects cause corresponding metadata changes in the catalog.

## OID and `reg*` types

An OID is a numeric object identifier. PostgreSQL 16 documentation describes `oid` as a four-byte (32-bit) unsigned integer used in many system catalogs as an internal primary key for object rows. Its range is not large enough to guarantee uniqueness across an entire large database or even a very large individual table. PostgreSQL provides several `reg*` types that are aliases of `oid` for specific categories of system objects. For example, `regclass` corresponds to relations from `pg_class`, `regtype` to types from `pg_type`, and `regnamespace` to namespaces from `pg_namespace`. There is no standard `regdatabase` type in this list.

`reg*` types allow an object to be supplied by symbolic name and displayed by symbolic name on output; for objects in namespaces, name resolution follows schema-search rules. `regclass`, for example, allows a relation name to be used instead of manually looking up its numeric OID.

## Shared and local catalogs

Most catalog data belongs to a particular database. At the same time, some catalog objects are shared across the whole cluster and are visible identically from different databases. The presentation uses the database list as an obvious example of metadata shared across the cluster.

## Practical orientation

```bash
SELECT oid, datname FROM pg_database;
SELECT 'public.orders'::regclass::oid;
SELECT oid, relname, relkind FROM pg_class WHERE relname = 'orders';

\dt
\d+ public.orders
\dn
\l
```

# 3. Important details

## Views and `information_schema`

The material describes `information_schema` as a standardized and more portable representation that does not expose every PostgreSQL-specific detail.

## psql meta-commands

The `\d` command family is intended for describing objects. For a relation, `\d` shows columns, their types, and additional properties including associated indexes and constraints. The `+` suffix is used by many psql meta-commands for extended output. For `\d+`, the documentation lists additional information about tables and views, including details such as the table access method and view definition when applicable. For a number of `\d` commands, the `S` modifier includes system objects in the output.

Psql uses its own object-search patterns. In these patterns, `*` matches any sequence of characters and `?` matches a single character. Without a pattern, visible objects are normally shown, while `*.*` can cover objects in all schemas of the current database. The `\dn` meta-command lists schemas. It also supports a pattern, `S`, and the extended `+` variant. The `\d` family contains specialized forms for different object types: `\dt` shows tables, `\dv` views, and `\di` indexes. `\dn` applies to schemas, not functions.

The `-E` option corresponds to enabling `ECHO_HIDDEN`. In this mode, psql displays the queries generated by its meta-commands. This directly supports the practical exercise with `\d+ pg_views`.

# What to remember

```text
• system catalogs are ordinary relations, but they almost never should be modified directly
• OID is an internal object identifier; `regclass` and other `reg*` types make references more readable
• some catalogs are shared cluster-wide, while others belong to a particular database
• `information_schema` is more portable; `pg_catalog` exposes PostgreSQL-specific details
• psql meta-commands are built largely on top of the system catalogs
```

Before the test, it is useful not only to recognize command names, but to be able to explain **what problem a mechanism solves, at what level it works, and what limitations it has**.
