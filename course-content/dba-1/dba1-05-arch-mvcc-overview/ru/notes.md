# 5. Многоверсионность и изоляция

## 1. Тема

MVCC позволяет нескольким транзакциям одновременно работать с данными, видя подходящие версии строк вместо глобальной блокировки чтения и записи. Снимок данных и правила видимости определяют, какие версии доступны конкретному оператору или транзакции.

Главная модель:

```text
UPDATE строки
    ↓
старая версия + новая версия
    ↓             ↓
видимость определяется snapshot
    ↓
VACUUM позже удаляет версии,
которые уже никому не нужны
```

# 2. Механизм

## Версии строк и снимки

В материале многоверсионность определяется как наличие нескольких версий одной и той же строки. Курс связывает время действия версии строки с идентификаторами транзакций, которые выдаются по возрастанию. Снимок представляет согласованный срез данных, определяющий, какие версии строк видит транзакция.

Уровни изоляции в том числе отличаются моментом и временем жизни снимка данных. На Read Committed новый снимок строится для каждого оператора SQL. Поскольку снимок строится в начале каждого оператора, следующий запрос может увидеть уже другие зафиксированные данные.

В материале это описано как создание снимка в начале транзакции, точнее — при выполнении её первого оператора. Repeatable Read сохраняет один снимок на протяжении транзакции, поэтому подходит, например, для многошаговых отчётов. MVCC оставляет исторические версии строк; когда они уже не могут понадобиться ни одной транзакции, их следует очищать.

Старая транзакция всё ещё может нуждаться в старых версиях, поэтому горизонт очистки не может продвинуться дальше неё. Накопление ненужных версий увеличивает объём таблиц и индексов и ухудшает работу с актуальными версиями. Одно из преимуществ многоверсионности — снижение необходимости в блокировках, что повышает параллелизм работы.

Обычное чтение благодаря MVCC не требует блокировать строки от чтения или изменения. Именно эта формулировка вынесена в итоговый слайд темы как одно из ключевых следствий MVCC.

## Уровни изоляции

Read Uncommitted как отдельная семантика в PostgreSQL не поддерживается и ведёт себя как Read Committed. Курс прямо указывает Read Committed как уровень изоляции PostgreSQL по умолчанию. Serializable обеспечивает наиболее строгую изоляцию, но цена этого — возможность прерывания транзакций, которые приложение должно повторять.

## Практический ориентир

```bash
-- Сеанс A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM accounts WHERE id = 1;

-- Сеанс B меняет и фиксирует строку
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
COMMIT;

-- Сеанс A продолжает видеть данные своего snapshot
SELECT * FROM accounts WHERE id = 1;
```

# 3. Важные детали

## Конкурирующие изменения

Изменение строки конфликтует с другими изменениями этой строки, но не мешает её обычному чтению. Конфликт возникает между конкурирующими изменениями одной строки: второй писатель должен дождаться разрешения ситуации с первым. Помимо блокировок строк существуют блокировки более высокого уровня, необходимые для согласования операций со структурой и физическим состоянием таблиц.

Материал связывает основное время жизни блокировок с транзакцией; при откате к точке сохранения блокировки, взятые после неё, также могут быть освобождены.

## Связь с VACUUM

Материал указывает как автоматическую фоновую очистку, так и возможность выполнить её вручную с помощью VACUUM.

# Что запомнить

```text
• UPDATE обычно создаёт новую версию строки, а не переписывает её «на месте» как единственную версию
• snapshot определяет видимость версий
• `READ COMMITTED` получает новый snapshot для каждого оператора; `REPEATABLE READ` держит согласованный снимок транзакции
• конкурирующие изменения одной строки всё равно требуют блокировок
• долгие транзакции могут удерживать старые версии и мешать очистке
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
