# 4. Общая архитектура PostgreSQL

## 1. Тема

Общая архитектура PostgreSQL соединяет клиент-серверный протокол, транзакции, обработку SQL, процессы, память и хранение данных. Для DBA важно видеть не отдельные команды, а путь запроса от клиента до изменённых страниц и WAL.

Главная модель:

```text
клиент
  ↓ protocol
backend process
  ↓
parser → rewriter → planner → executor
  ↓                 ↘
shared buffers       WAL
  ↓                   ↓
data files          pg_wal
```

# 2. Механизм

## Клиент и сервер

Клиент и сервер должны использовать один протокол взаимодействия. Обычно клиент работает через драйвер, который реализует протокол PostgreSQL; драйвер может использовать libpq или реализовывать протокол самостоятельно. Протокол позволяет клиенту подключиться к базе данных кластера; сервер выполняет аутентификацию, затем принимает SQL-запросы, выполняет их и возвращает результат. Клиент не изменяет файлы данных напрямую. ACID включает атомарность, согласованность, изоляцию и долговечность. Резервное копирование само по себе не является буквой ACID.

Как правило, именно клиентское приложение определяет команды, входящие в транзакцию, и выполняет фиксацию или отмену. На стороне сервера транзакциями также могут управлять хранимые процедуры. Системный каталог содержит метаинформацию о базе данных, необходимую, например, чтобы определить, существуют ли таблицы и другие объекты, на которые ссылается запрос. После подготовки запроса конкретные значения параметров задаются на этапе привязки.

Пул соединений рекомендуется рассматривать при большом числе клиентов или при частом установлении и разрыве соединений. Менеджер пула принимает клиентские соединения и переиспользует ограниченный набор открытых соединений с PostgreSQL. Файлы логически делятся на страницы (блоки), обычный размер страницы — 8 Кбайт. Другой размер можно задать лишь при сборке сервера.

Страница имеет внутреннюю разметку, содержит заголовок и данные, а при неполном заполнении — свободное пространство. Размер страницы задаётся для собранного сервера, а не выбирается для каждого запроса.

## Транзакции

Атомарность означает принцип «всё или ничего»: изменения транзакции либо фиксируются целиком, либо не фиксируются. В материале BEGIN отмечает начало транзакции, COMMIT — фиксацию изменений, а ROLLBACK — отмену изменений. В материале многоверсионность названа основным механизмом, обеспечивающим первые три свойства транзакций: атомарность, согласованность и изоляцию.

## Путь SQL-запроса

Материал выделяет стадии разбора, переписывания, планирования и выполнения запроса. SQL является декларативным языком: запрос описывает требуемые данные, а планировщик определяет способ выполнения, например целесообразность использования индексов. Для планирования нужна статистика, содержащая сведения о размерах таблиц и распределении данных. Пароль пользователя к выбору плана не относится.

Подготовленный оператор позволяет заранее выполнить разбор и переписывание и сохранить дерево разбора; конкретные параметры привязываются при выполнении. Материал отмечает возможность повторного использования плана в некоторых случаях и защиту от внедрения SQL-кода. Повторное планирование не исключается безусловно.

## Практический ориентир

```bash
BEGIN;
SAVEPOINT before_change;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
ROLLBACK TO SAVEPOINT before_change;
COMMIT;

PREPARE q(int) AS SELECT * FROM accounts WHERE id = $1;
EXECUTE q(1);
```

# 3. Важные детали

## Prepared statements и курсоры

Курсор позволяет не получать весь набор результата сразу, а работать с ним итеративно, получая строки по мере необходимости. Курсор позволяет итеративно получать данные; открытый курсор представлен порталом, а использованный в нём запрос неявно подготавливается.

## Процессы и память

При старте сервера запускается postmaster: он создаёт остальные процессы, следит за ними и слушает входящие соединения. Локальная память backend используется для состояния конкретного обслуживаемого соединения и выполнения его запросов. В ней могут находиться разобранные запросы и их планы, состояние открытых курсоров, кеш системного каталога, а также рабочая память для сортировок и соединений. Общий буферный кеш расположен в общей памяти. Для каждого нового клиента postmaster порождает обслуживающий процесс backend; этот процесс также выполняет аутентификацию.

Для общей памяти применяются короткие блокировки. Для табличных данных PostgreSQL опирается на MVCC и снимки, стараясь блокировать только конфликтующие изменения. При пуле несколько клиентов могут разделять один backend во времени, а backend хранит локальное состояние. Поэтому это состояние необходимо учитывать при проектировании приложения. Буферный кеш PostgreSQL находится в общей памяти, чтобы разные серверные процессы могли использовать кешированные страницы.

При сбое содержимое оперативной памяти может пропасть вместе с ещё не записанными страницами. Журнал позволяет восстановить потерянные изменения и вернуть данные в согласованное состояние.

## Диск, WAL и расширяемость

Помимо общего буферного кеша PostgreSQL существует кеш ОС. Изменённые страницы могут быть записаны на диск позже, поэтому долговечность требует дополнительного механизма. Архитектура PostgreSQL допускает расширения, добавляющие типы и операторы, методы индексации, фоновые задачи, работу с внешними источниками и другие возможности. Конспект подчёркивает расширяемость PostgreSQL и отмечает, что большинство расширений можно устанавливать без перезапуска сервера.

# Что запомнить

```text
• каждое обычное клиентское соединение обслуживается отдельным backend-процессом
• SQL проходит стадии разбора, переписывания, планирования и выполнения
• транзакция задаёт атомарную единицу работы; savepoint создаёт промежуточную точку отката
• изменённые страницы сначала могут жить в памяти, а долговечность обеспечивает WAL
• PostgreSQL расширяем: типы, функции, индексы, языки и extensions можно добавлять
```

Перед тестом полезно не просто узнавать названия команд, а уметь объяснить, **какую задачу решает механизм, на каком уровне он работает и какие ограничения у него есть**.
