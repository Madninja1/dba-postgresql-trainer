# 20. Логическая репликация

## 1. Тема

Логическая репликация декодирует WAL в изменения строк и передаёт выбранные данные от публикации к подписке. В отличие от физической, она не копирует весь кластер, не требует двоичной совместимости и позволяет строить выборочные и разнонаправленные схемы.

Главная модель:

```text
PUBLISHER
WAL → logical decoding → wal sender
                      ===== protocol =====>
SUBSCRIBER
logical replication worker → apply row changes
```

---

# 2. Механизм

## `wal_level = logical`

Обычного уровня `replica` достаточно для физической репликации, но логическое декодирование требует `wal_level = logical` на публикующем сервере. Этот уровень добавляет в WAL информацию, необходимую для восстановления логического смысла изменений строк и структуры отношений.

## Публикации

Публикация существует в одной базе и описывает набор изменений, которые сервер готов отправлять подписчикам.

Она может определять:

- таблицы;
- набор операций `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`;
- публикуемые столбцы;
- фильтры строк.

Одна таблица может входить в несколько публикаций. Публикация не является схемой и сама по себе не меняет права доступа к таблицам.

## Подписки

Подписка подключается к одной или нескольким публикациям и обычно создаёт на publisher слот логической репликации. Изменения одной подписки поступают через её слот, а при начальной синхронизации могут временно потребоваться дополнительные слоты.

При создании подписки существующие данные по умолчанию копируются (`copy_data = true`), после чего новые изменения передаются потоком. Таблицы-приёмники и необходимая схема должны существовать заранее: DDL автоматически не переносится.

## Что передаётся

Реплицируются изменения строк, а не исходный SQL-текст и не физические страницы. Subscriber применяет полученные операции к своим таблицам.

Обычная встроенная логическая репликация не переносит автоматически:

- DDL и изменения схемы;
- значения последовательностей;
- большие объекты `lo`;
- изменения представлений, materialized views и foreign tables.

Непосредственно реплицируются обычные и секционированные таблицы.

# 3. Replica identity и конфликты

## Replica identity

Для `UPDATE` и `DELETE` подписчик должен определить, какую строку менять. Для этого используется `REPLICA IDENTITY`:

- `DEFAULT` — первичный ключ;
- `USING INDEX` — подходящий уникальный, непарциальный, неотложенный индекс на `NOT NULL` столбцах;
- `FULL` — старые значения всех столбцов;
- `NOTHING` — не сохранять идентификатор.

Если публикация передаёт `UPDATE`/`DELETE`, а подходящей replica identity нет, соответствующие изменения нельзя корректно публиковать.

## Конфликты

Subscriber — обычная база PostgreSQL, поэтому локальные изменения могут конфликтовать с входящими. Если применение входящей операции нарушает ограничение или необходимые права отсутствуют, рабочий процесс логической репликации останавливается с ошибкой до ручного устранения причины.

Универсального автоматического разрешения конфликтов встроенная логическая репликация не предоставляет.

Последовательности реплицируются отдельно от таблиц и их текущие значения автоматически не синхронизируются. В двунаправленных схемах это особенно важно: разные серверы должны использовать непересекающиеся диапазоны либо глобально уникальные идентификаторы, например UUID.

# 4. Эксплуатационные ограничения

## Слоты и разрыв соединения

Слот гарантирует, что publisher удерживает WAL, ещё необходимый subscriber. Если подписка надолго становится неактивной, слот способен удерживать WAL и горизонт очистки, поэтому потерянную связь нельзя игнорировать бесконечно.

## `TRUNCATE` и внешние ключи

Для корректной репликации `TRUNCATE` все таблицы, связанные внешними ключами с опустошаемой таблицей и требующие совместного `TRUNCATE`, должны быть включены в совместимую репликационную схему. Иначе применение операции на subscriber может завершиться ошибкой.

## Длинные транзакции и `streaming`

Без streaming изменения долгой транзакции полностью декодируются на publisher и передаются после её фиксации. Параметр подписки `streaming` позволяет передавать изменения выполняющейся транзакции раньше; subscriber может временно сохранять их или применять параллельным рабочим процессом в поддерживаемом режиме.

# 5. Сценарии

## Консолидация

Несколько филиалов могут публиковать выбранные таблицы, а центральный сервер — подписываться на них и объединять данные.

## Обновление основной версии

Логическая репликация не требует двоичной совместимости основных версий. Поэтому можно подготовить новый сервер, синхронизировать данные и затем переключить клиентов, сокращая окно недоступности.

## Двунаправленная репликация

PostgreSQL 16 позволяет строить двунаправленные схемы, но приложение должно избегать конфликтов и самостоятельно обеспечивать корректную генерацию идентификаторов. Встроенный механизм не даёт глобальных распределённых транзакций и автоматического управления кластером.

Для практической подписки между двумя серверами занятия используются:

```text
copy_data = false
origin = none
```

`origin = none` просит не пересылать изменения, уже имеющие replication origin, что помогает избежать немедленного обратного распространения полученных изменений.

## Подписка внутри того же кластера

При подписке на публикацию в том же кластере обычный `CREATE SUBSCRIPTION`, который одновременно пытается создать удалённый слот, может зависнуть. Практический обход: заранее создать логический слот отдельно и затем создать подписку с `create_slot = false`.

# 6. Практический ориентир

```sql
-- publisher
CREATE PUBLICATION app_pub FOR TABLE app.orders;

-- subscriber: таблица app.orders должна существовать
CREATE SUBSCRIPTION app_sub
CONNECTION 'host=publisher dbname=appdb user=repl'
PUBLICATION app_pub;

-- если нет подходящего PK/unique identity
ALTER TABLE app.orders REPLICA IDENTITY FULL;
```

# Что запомнить

```text
• publisher для встроенной логической репликации использует wal_level = logical
• публикация выбирает таблицы/операции и может ограничивать строки и столбцы
• подписка обычно создаёт логический replication slot и может выполнить initial copy
• DDL, sequences и large objects автоматически не синхронизируются
• для UPDATE/DELETE нужна replica identity
• неактивный слот удерживает необходимые WAL и требует наблюдения
• streaming помогает с длинными транзакциями
• двунаправленная схема требует явного проектирования конфликтов и уникальности ключей
• подписка внутри того же кластера требует отдельного создания слота и create_slot = false
```

Перед тестом важно видеть логическую репликацию как **поток изменений выбранных таблиц с явными ограничениями по схеме, идентификации строк и конфликтам**.
