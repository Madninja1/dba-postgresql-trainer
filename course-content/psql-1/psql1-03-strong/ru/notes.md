# Strong — продвинутый psql

## 1. Тема

На Strong-уровне psql рассматривается как инструмент **надёжной автоматизации**: скрипт должен правильно завершаться при ошибке, возвращать понятный exit code, не фиксировать половину изменений и безопасно подставлять значения.

Главная модель:

```text
shell / CI
    ↓
psql process
    ├─ параметры запуска
    ├─ psql-переменные
    ├─ обработка ошибок
    ├─ query buffer
    └─ метакоманды
          ↓
      PostgreSQL
          ↓
 SQLSTATE / результат / транзакция
          ↓
      exit code psql
          ↓
       shell / CI
```

Здесь важно понимать не отдельные команды, а то, **где проходит граница между psql и сервером** и что происходит при ошибке.

# 2. Механизм

## По умолчанию psql не останавливает скрипт на каждой SQL-ошибке

Это принципиальная особенность автоматизации.

Если в psql-скрипте SQL-команда завершилась ошибкой, обычное поведение клиента — продолжить обработку следующих команд.

Для интерактивной работы это часто удобно. Для миграции или deployment-скрипта — опасно.

### `ON_ERROR_STOP`

```text
\set ON_ERROR_STOP on
```

или при запуске:

```bash
psql -v ON_ERROR_STOP=1 -f deploy.sql
```

меняет поведение: при ошибке psql прекращает обработку команд.

В интерактивном сеансе клиент возвращается к приглашению. В неинтерактивном режиме psql завершает работу с отдельным кодом возврата.

Модель:

```text
ON_ERROR_STOP off (default)
ошибка
  ↓
psql обычно продолжает скрипт

ON_ERROR_STOP on
ошибка
  ↓
psql прекращает обработку
```

Это **клиентская** настройка psql. Она не останавливает сам PostgreSQL server.

---

## Exit codes psql

Для shell, cron и CI важен не текст в терминале, а код завершения процесса.

Документация psql определяет:

```text
0   нормальное завершение
1   критическая ошибка самого psql
2   неудачное соединение с сервером в неинтерактивном сеансе
3   ошибка в скрипте при включённом ON_ERROR_STOP
```

Пример shell-проверки:

```bash
psql -v ON_ERROR_STOP=1 -f deploy.sql
status=$?

if [ "$status" -ne 0 ]; then
    echo "psql failed: $status" >&2
    exit "$status"
fi
```

Особенно важно различать `1`, `2` и `3`: это разные классы проблем.

## `-1` / `--single-transaction`

Для нескольких `-c`/`-f` psql умеет обернуть всю обработку в одну транзакцию:

```bash
psql -1 -v ON_ERROR_STOP=1 -f migration.sql
```

`-1` можно использовать только вместе с одним или несколькими `-c` и/или `-f`.

Механизм:

```text
psql
  ↓
BEGIN
  ↓
первый -c/-f
  ↓
следующий -c/-f
  ↓
...
  ↓
COMMIT
```

Если одна из команд завершается ошибкой **и** `ON_ERROR_STOP` включён, вместо финального `COMMIT` psql отправляет `ROLLBACK`.

То есть распространённая связка:

```bash
psql -1 -v ON_ERROR_STOP=1 -f migration.sql
```

даёт модель:

```text
всё успешно → COMMIT
ошибка       → остановка + ROLLBACK
```

### Ограничения `-1`

`-1` не является магией поверх любого скрипта.

Если внутри самих `-c`/`-f` есть явные:

```sql
BEGIN;
COMMIT;
ROLLBACK;
```

они могут разрушить ожидаемую семантику `--single-transaction`.

Также вся транзакция завершится ошибкой, если скрипт содержит команду, которую нельзя выполнять внутри transaction block.

Поэтому `-1` хорошо подходит для скриптов, которые **сами не управляют границами транзакции**.

---

## Транзакционная особенность одного `-c`

Рассмотрим:

```bash
psql -c 'INSERT INTO a VALUES (1); INSERT INTO b VALUES (2);'
```

Одна строка SQL, переданная через один `-c`, отправляется серверу как **один запрос**.

Если внутри нет явных `BEGIN`/`COMMIT`, разделяющих команды, сервер выполняет несколько SQL-команд такой строки в одной транзакции.

Это отличается от:

```bash
psql \
  -c 'INSERT INTO a VALUES (1);' \
  -c 'INSERT INTO b VALUES (2);'
```

Здесь psql отправляет два отдельных запроса.

Следовательно, точка с запятой внутри одного аргумента `-c` **не создаёт отдельное соединение и не означает автоматически отдельную клиентскую транзакцию для каждой команды**.

Если нужно не объединять несколько SQL-команд в одну строку запроса, используйте несколько `-c` или подавайте команды через стандартный ввод отдельно.

## `AUTOCOMMIT`

`AUTOCOMMIT` — специальная переменная psql.

По умолчанию:

```text
AUTOCOMMIT = on
```

### При `on`

После каждой успешно выполненной команды изменения обычно фиксируются автоматически, если вы сами не начали явный transaction block:

```sql
BEGIN;
...
COMMIT;
```

### При `off`

```text
\set AUTOCOMMIT off
```

psql не фиксирует изменения, пока явно не выполнен:

```sql
COMMIT;
```

или:

```sql
END;
```

Перед подходящей командой psql может неявно выполнить `BEGIN`, если транзакция ещё не начата.

Упрощённо:

```text
AUTOCOMMIT on
SQL успешно
  ↓
обычно сразу commit

AUTOCOMMIT off
SQL
  ↓
неявный BEGIN при необходимости
  ↓
изменения остаются незакоммиченными
  ↓
явный COMMIT / END
```

Если выйти из сеанса с незафиксированными изменениями, они **теряются**, а не сохраняются автоматически.

После ошибки при выключенном autocommit неуспешную транзакцию нужно явно откатить через `ROLLBACK`/`ABORT`.

---

## `ON_ERROR_ROLLBACK`: не то же самое, что `ON_ERROR_STOP`

Ещё одна специальная переменная:

```text
ON_ERROR_ROLLBACK
```

При `on` psql внутри transaction block создаёт неявный `SAVEPOINT` перед каждой командой и при ошибке откатывается к нему, позволяя транзакции продолжиться.

Сравнение:

```text
ON_ERROR_STOP       что делать psql со скриптом после ошибки
ON_ERROR_ROLLBACK   как psql помогает продолжить transaction block после ошибки
```

Это разные механизмы. Для migration/deployment обычно важнее связка `ON_ERROR_STOP + -1`.

## Безопасная интерполяция переменных

psql поддерживает четыре важные формы:

```text
:name       буквальная подстановка значения
:'name'     значение как SQL-литерал
:"name"     значение как SQL-идентификатор
:{?name}    TRUE/FALSE: определена ли переменная
```

### Обычная `:name`

```text
\set condition 'id > 10'
SELECT * FROM users WHERE :condition;
```

psql копирует значение буквально.

Это мощно, но опасно, если значение является внешними данными: оно может содержать кавычки или другой SQL.

### SQL-литерал — `:'name'`

Для значения данных:

```text
\set login 'Alice'
```

используйте:

```sql
SELECT *
FROM users
WHERE name = :'login';
```

psql корректно оформляет значение как SQL literal, включая необходимые кавычки.

### SQL-идентификатор — `:"name"`

Для имени таблицы или столбца:

```text
\set table_name 'User Data'
```

используйте:

```sql
SELECT * FROM :"table_name";
```

psql корректно оформляет значение как SQL identifier.

### Проверка существования — `:{?name}`

```text
\if :{?table_name}
    \echo 'table_name is set'
\endif
```

конструкция заменяется на `TRUE` или `FALSE` в зависимости от наличия переменной.

Правило:

```text
данные                  → :'name'
имена таблиц/столбцов   → :"name"
готовый SQL-фрагмент     → :name, только если вы точно контролируете содержимое
```

## `\gset`: строгий контракт одной строки

На Middle-уровне мы использовали `\gset` как мост от SQL к переменным. Здесь важны все детали контракта.

```sql
SELECT current_database() AS db,
       current_user AS usr
\gset session_
```

Требования и поведение:

- запрос должен вернуть **ровно одну строку**;
- каждый столбец становится отдельной psql-переменной;
- необязательный префикс добавляется к имени каждого столбца;
- если значение столбца `NULL`, соответствующая переменная удаляется;
- если запрос завершился ошибкой или вернул не одну строку, переменные не меняются.

То есть psql не выбирает «последнюю строку» при множественном результате.

---

## `\gexec`: результат запроса становится SQL

`\gexec` сначала выполняет текущий query buffer, а затем каждое непустое поле результата рассматривает как SQL-команду и отправляет серверу.

Пример:

```sql
SELECT format(
    'ANALYZE %I.%I;',
    schemaname,
    tablename
)
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY tablename
\gexec
```

Модель:

```text
SELECT генерирует строки SQL
          ↓
        \gexec
          ↓
каждое непустое поле
          ↓
отдельный SQL-запрос серверу
```

### Порядок

Сгенерированные запросы выполняются:

```text
по строкам результата сверху вниз
и внутри строки — слева направо по столбцам
```

### `NULL`

Поля со значением `NULL` игнорируются.

### Ошибка одной из сгенерированных команд

По умолчанию `\gexec` продолжает выполнение остальных команд после ошибки.

Если включён:

```text
ON_ERROR_STOP
```

обработка прекращается.

### Что именно выполняется

Значения результата передаются серверу буквально как SQL. Они **не интерпретируются как psql-метакоманды** и не получают новую интерполяцию psql-переменных.

Поэтому при генерации SQL особенно важно использовать безопасное форматирование, например `%I` для SQL-идентификаторов и `%L` для литералов в `format()`.

---

## `\bind`: параметры следующего запроса

`\bind` задаёт значения параметров `$1`, `$2`, ... для **следующего** выполнения запроса.

Пример:

```text
INSERT INTO audit_log(message, severity)
VALUES ($1, $2)
\bind 'started' 'INFO'
\g
```

Ключевая особенность: psql использует для такого выполнения **extended query protocol**, а не обычный simple query protocol.

`\bind` действует только на следующее выполнение. Последующие запросы снова используют обычное поведение, если `\bind` не задан заново.

Это не создаёт «вечный» server-side prepared statement и не имеет отношения к привязке роли к пользователю.

---

## `\gexec`, `\gset` и `\bind`: три разных направления данных

Их легко перепутать, поэтому полезна одна схема:

```text
\gset
SQL result → psql variables

\gexec
SQL result → новый SQL → server

\bind
psql values → параметры $1, $2 → следующий query execution
```

---

## `\errverbose`

После серверной ошибки:

```text
\errverbose
```

повторяет **последнее серверное сообщение об ошибке** с максимальной детализацией — как при `VERBOSITY=verbose` и `SHOW_CONTEXT=always`.

Это удобно, если обычное сообщение уже было показано кратко, но теперь нужны детали диагностики.

Команда не запускает `EXPLAIN`, не показывает всю history и не меняет client encoding.

---

## Переменные состояния ошибки

psql также поддерживает специальные переменные:

```text
ERROR               true/false для последнего SQL-запроса
SQLSTATE            SQLSTATE последнего запроса, либо 00000 при успехе
LAST_ERROR_MESSAGE  текст последней ошибки
LAST_ERROR_SQLSTATE SQLSTATE последней ошибки
ROW_COUNT           число строк последней команды, когда оно известно
```

Они полезны в автоматизации вместе с `\if`.

---

## `ECHO_HIDDEN`: увидеть SQL за метакомандой

Многие команды psql вроде `\d` сами обращаются к системным каталогам.

```text
\set ECHO_HIDDEN on
```

заставляет psql перед такой метакомандой показать нижележащий SQL-запрос.

Это полезно для:

- изучения системных каталогов;
- понимания реализации `\d*`;
- построения собственных запросов диагностики.

Есть также значение:

```text
ECHO_HIDDEN = noexec
```

при котором psql показывает такие запросы, но не отправляет их серверу.

Но обычное `on` **не отключает выполнение** — оно лишь дополнительно показывает SQL.

---

## `FETCH_COUNT`: большие результаты порциями

По умолчанию psql обычно получает полный результирующий набор перед отображением.

Если установить положительное целое значение:

```text
\set FETCH_COUNT 500
```

результаты `SELECT` извлекаются из базы и отображаются группами по заданному числу строк.

Смысл:

```text
большой SELECT
     ↓
FETCH_COUNT = 500
     ↓
показывать результат порциями по 500 строк
     ↓
ограничить потребление памяти клиентом
```

Важно:

- `FETCH_COUNT` не добавляет `LIMIT` в ваш SQL;
- он не означает, что запрос в целом вернёт максимум `FETCH_COUNT` строк;
- это механизм psql для порционной обработки результата.

При таком режиме запрос может завершиться ошибкой уже после того, как часть строк была показана.

---

## `\watch`: interval и count

Форма PostgreSQL 16:

```text
\watch [interval=seconds] [count=number]
```

или совместимая короткая форма с числом секунд.

Например:

```sql
SELECT now(), count(*) FROM pg_stat_activity;
\watch interval=1 count=20
```

Поведение:

- выполняет текущий query buffer как `\g`;
- если буфер пуст, повторяет последний переданный запрос;
- интервал по умолчанию — **2 секунды**;
- `count` ограничивает количество выполнений;
- без ограничения повторение продолжается до прерывания или ошибки.

## Продвинутые шаблоны `\d*`

Шаблоны psql — это не просто `*` и `?`.

### Схема и объект

```text
\dt foo*.*bar*
```

часть до точки — шаблон схемы, часть после — шаблон имени объекта.

Поэтому утверждение «точка никогда не относится к схеме» неверно: наоборот, именно точка разделяет эти компоненты.

### Все схемы

```text
\dt *.*
```

позволяет находить объекты независимо от их видимости через текущий `search_path`.

### Элементы регулярных выражений

Опытные пользователи могут применять элементы regexp, например классы символов:

```text
\dt log_[0-9]
```

При этом psql имеет собственные правила шаблонов: `*` интерпретируется как любое количество символов, `?` — как один символ, а совпадение относится ко всему имени.

### Кавычки

Внутри двойных кавычек специальные символы шаблона теряют специальное значение и соответствуют самим себе.

# 3. Важные детали

## Надёжный migration script — это несколько механизмов вместе

Одна только настройка не решает всё.

Практическая комбинация:

```bash
psql \
  -1 \
  -v ON_ERROR_STOP=1 \
  -f migration.sql
```

даёт:

```text
ON_ERROR_STOP   остановиться на ошибке
-1              единая внешняя транзакция
exit code       сообщить shell результат
```

Но только если сам скрипт совместим с transaction block и не ломает внешнее управление своими `BEGIN/COMMIT/ROLLBACK`.

---

## Не путайте клиентскую ошибку и SQLSTATE

```text
exit code psql   результат процесса для ОС
SQLSTATE         состояние выполнения SQL на стороне PostgreSQL
```

Например, код процесса `3` означает ошибку скрипта при `ON_ERROR_STOP`, а конкретную причину серверной ошибки описывает SQLSTATE.

---

## Интерполяция psql — до разбора SQL сервером

psql сначала подставляет переменные, и только затем готовый текст получает PostgreSQL.

Поэтому:

```text
:name
```

нельзя считать параметром prepared statement. Это текстовая интерполяция клиента.

Если нужны параметры `$1`, `$2` следующего выполнения через extended protocol — для этого существует `\bind`.

# Что запомнить

Ошибки и автоматизация:

```text
ON_ERROR_STOP off   после ошибки psql обычно продолжает
ON_ERROR_STOP on    прекратить обработку

exit 0              normal
exit 1              fatal psql error
exit 2              connection failure in noninteractive session
exit 3              script error with ON_ERROR_STOP
```

Одна транзакция для `-c`/`-f`:

```text
-1 / --single-transaction
        ↓
BEGIN
        ↓
все -c / -f
        ↓
COMMIT

ошибка + ON_ERROR_STOP
        ↓
ROLLBACK
```

Но явные `BEGIN/COMMIT/ROLLBACK` внутри скрипта могут нарушить ожидаемую семантику.

Переменные:

```text
:name       raw substitution
:'name'     SQL literal
:"name"     SQL identifier
:{?name}    variable exists? → TRUE/FALSE
```

Продвинутые команды:

```text
\gset     одна строка SQL → psql variables
\gexec    поля результата → SQL commands
\bind     values → $1/$2 следующего execution
\errverbose  последняя серверная ошибка подробно
```

`\gset`:

```text
ровно 1 строка
столбец → переменная
prefix  → префикс имени
NULL    → удалить переменную
```

`\gexec`:

```text
NULL                игнорируется
порядок              строки сверху вниз, столбцы слева направо
ошибка               обычно продолжить
ON_ERROR_STOP        прекратить
psql-метакоманды     не выполняются из результата
```

Состояние клиента:

```text
AUTOCOMMIT = on       по умолчанию
AUTOCOMMIT = off      нужен явный COMMIT/END
ECHO_HIDDEN = on      показать SQL за \d-подобными командами
FETCH_COUNT = N       показывать SELECT порциями по N строк
```

Мониторинг и шаблоны:

```text
\watch                повторять query buffer
default interval       2 seconds
count=N                ограничить число выполнений

schema.object          схема + объект
*.*                    объекты независимо от search_path visibility
[0-9]                  пример regexp-класса в шаблоне
```

И отдельное правило для `-c`:

```text
один -c с несколькими SQL-командами
        ↓
один запрос серверу
        ↓
обычно одна транзакция,
если внутри нет явных BEGIN/COMMIT, разделяющих её
```
