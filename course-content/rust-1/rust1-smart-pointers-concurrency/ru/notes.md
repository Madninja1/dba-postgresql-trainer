# Шаг 14. Указатели и многопоточность

## 1. Тема

В этом шаге соединяются две большие темы:

```text
умные указатели
→ управляют владением и доступом к данным

многопоточность
→ позволяет нескольким потокам
  выполнять код одновременно
```

Обычная ссылка:

```rust
&T
```

только заимствует значение.

Умный указатель — структура, которая ведёт себя как указатель, но дополнительно может владеть данными, хранить метаданные и предоставлять особое поведение. Для умных указателей особенно важны traits `Deref` и `Drop`. `String` и `Vec<T>` тоже относятся к этой общей идее. Язык программирования Rust(2)

Главные типы шага:

```text
Box<T>
→ один владелец
→ данные в heap

Rc<T>
→ несколько владельцев
→ один поток

RefCell<T>
→ borrowing проверяется runtime
→ interior mutability

Weak<T>
→ ссылка без владения
→ разрыв Rc-циклов

Mutex<T>
→ защищённый изменяемый доступ

Arc<T>
→ многопоточное множественное владение
```

А для связи потоков используются:

```text
thread::spawn
JoinHandle
channels
Mutex<T>
Arc<T>
Send
Sync
```

---

# 2. Механизм

## `Box<T>`

`Box<T>` хранит само значение в куче, а в месте расположения `Box` остаётся указатель на него.

```rust
let b = Box::new(5);
```

Модель:

```text
stack                   heap

b ────────────────────→ 5
```

При выходе `Box` из области видимости освобождается и сам указатель, и данные в куче.

Один из главных случаев применения — тип, чей размер невозможно определить непосредственно из рекурсивного определения. Язык программирования Rust(2)

---

## Рекурсивные типы

Такое определение невозможно:

```rust
enum List {
    Cons(i32, List),
    Nil,
}
```

Причина:

```text
List содержит List
     содержит List
          содержит List
               ...
```

Компилятор не может вычислить конечный размер `List`.

`Box<T>` имеет известный размер независимо от размера `T`, поэтому рекурсию можно разорвать:

```rust
enum List {
    Cons(i32, Box<List>),
    Nil,
}
```

Теперь:

```text
List
├─ i32
└─ Box<List>
      ↓
   следующий List в heap
```

Сам `List` имеет вычислимый размер, поскольку содержит указатель фиксированного размера, а не следующий `List` напрямую.

---

# `Deref`

Умный указатель может вести себя подобно обычной ссылке благодаря trait:

```rust
Deref
```

Например:

```rust
let x = 5;
let y = Box::new(x);

assert_eq!(5, *y);
```

Оператор:

```rust
*
```

получает значение, на которое указывает `Box`.

Для собственного типа концепция выглядит так:

```rust
impl<T> Deref for MyBox<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &self.0
    }
}
```

При `*value` Rust фактически использует `Deref::deref`, чтобы получить обычную ссылку, которую уже умеет разыменовывать. Язык программирования Rust(2)

---

## Deref coercion

Rust умеет автоматически преобразовывать ссылку на умный указатель в ссылку на внутренний тип.

Например, если функция принимает:

```rust
fn hello(name: &str) {
    ...
}
```

можно передать:

```rust
let name = Box::new(String::from("Rust"));

hello(&name);
```

Rust может провести цепочку:

```text
&Box<String>
     ↓ Deref
&String
     ↓ Deref
&str
```

Это называется **deref coercion**. Преобразования определяются во время компиляции и не требуют ручных цепочек `*` и `&`. Язык программирования Rust(2)

Для изменяемых ссылок существует аналогичный `DerefMut`.

---

# `Drop`

`Drop` задаёт код автоматической очистки значения.

```rust
impl Drop for MyType {
    fn drop(&mut self) {
        ...
    }
}
```

Rust вызывает `drop` автоматически, когда значение выходит из области видимости.

Это используется для освобождения ресурсов:

```text
heap memory
files
network connections
locks
...
```

Например, `Box<T>` через этот механизм освобождает данные в куче. Язык программирования Rust(2)

Модель:

```text
value выходит из scope
        ↓
Drop::drop(...)
        ↓
очистка ресурса
```

То есть RAII-модель ownership распространяется не только на память.

---

# `Rc<T>` — несколько владельцев

Обычный ownership предполагает одного владельца.

Но иногда одни данные должны принадлежать нескольким частям структуры одновременно.

Для однопоточного случая:

```rust
Rc<T>
```

`Rc` означает **reference counted**.

Пример:

```rust
let a = Rc::new(value);

let b = Rc::clone(&a);
let c = Rc::clone(&a);
```

Модель:

```text
a ─┐
b ─┼──→ DATA
c ─┘
```

Внутри хранится счётчик сильных ссылок:

```text
Rc::new
→ strong_count = 1

Rc::clone
→ +1

Rc удалён
→ -1

strong_count == 0
→ DATA уничтожаются
```

`Rc::clone` не выполняет глубокое копирование данных — он увеличивает счётчик ссылок. Язык программирования Rust(2)

---

## Что даёт `Rc<T>`

Главное:

```text
Rc<T>
→ shared ownership
```

Но обычный `Rc<T>` предоставляет совместный доступ в основном для чтения.

Несколько владельцев не должны автоматически означать несколько произвольных изменяемых ссылок, иначе нарушились бы правила borrowing. Язык программирования Rust(2)

`Rc<T>` предназначен для **однопоточного** использования.

---

# `RefCell<T>`

`RefCell<T>` переносит проверку borrowing:

```text
обычные & / &mut
→ compile time

RefCell<T>
→ runtime
```

Получить неизменяемое заимствование:

```rust
value.borrow()
```

Результат:

```text
Ref<T>
```

Изменяемое:

```rust
value.borrow_mut()
```

Результат:

```text
RefMut<T>
```

Оба типа реализуют `Deref`, поэтому с ними можно работать подобно ссылкам. Язык программирования Rust(2)

---

## Правила не меняются

`RefCell<T>` разрешает:

```text
несколько Ref<T>

ИЛИ

один RefMut<T>
```

То есть старое правило:

```text
many readers
OR
one writer
```

остаётся.

Изменяется только момент проверки.

При обычных ссылках нарушение:

```text
→ compiler error
```

При `RefCell<T>`:

```text
→ код компилируется
→ нарушение обнаруживается runtime
→ panic
```

Например, два активных `borrow_mut()` приводят к `BorrowMutError`. Язык программирования Rust(2)

---

# Interior mutability

`RefCell<T>` позволяет изменить внутреннее значение даже через API, который внешне использует неизменяемую ссылку.

Это называют:

```text
interior mutability
```

Практическая комбинация:

```text
Rc<RefCell<T>>
```

означает:

```text
Rc
→ несколько владельцев

RefCell
→ внутреннее изменение
```

Получается:

```text
несколько частей программы
        ↓
совместно владеют данными
        ↓
могут изменять внутреннее значение
        ↓
правила borrowing проверяются runtime
```

Книга показывает эту комбинацию на общей части нескольких списков. Язык программирования Rust(2)

---

# Циклы `Rc<T>`

Reference counting имеет важный риск.

Если:

```text
A owns Rc<B>
B owns Rc<A>
```

получается:

```text
A ──strong──→ B
↑             │
└──strong─────┘
```

Даже если внешние владельцы исчезнут:

```text
A strong_count > 0
B strong_count > 0
```

ни один объект не будет удалён.

Результат:

```text
memory leak
```

Ownership и borrow checker не гарантируют отсутствие таких логических циклов.

---

# `Weak<T>`

Для ссылки, которая **не должна владеть объектом**, используется:

```rust
Weak<T>
```

Создание из `Rc<T>`:

```rust
let weak = Rc::downgrade(&strong);
```

Это:

```text
не увеличивает strong_count
увеличивает weak_count
```

Поэтому `Weak<T>` не удерживает объект живым. Язык программирования Rust(2)

Получить объект обратно:

```rust
weak.upgrade()
```

возвращает:

```text
Option<Rc<T>>
```

Почему `Option`?

Потому что объект уже мог быть уничтожен:

```text
ещё существует
→ Some(Rc<T>)

уже удалён
→ None
```

---

## Типичный пример `Weak`

Для дерева:

```text
parent
  │
  └── strong Rc ──→ child

child
  │
  └── Weak ───────→ parent
```

Родитель владеет ребёнком.

Ребёнок только знает о родителе, но **не владеет им**.

Это разрывает цикл и позволяет корректно удалять структуру. Язык программирования Rust(2)

---

# Переход к потокам

Поток — отдельная последовательность выполнения внутри процесса.

Rust рассматривает несколько моделей многопоточности:

```text
threads
→ параллельное выполнение

message passing
→ передача значений между потоками

shared state
→ общий доступ к данным

Send / Sync
→ гарантии типов
```

Язык программирования Rust(2)

---

# `thread::spawn`

Новый поток:

```rust
use std::thread;

let handle = thread::spawn(|| {
    // код нового потока
});
```

`spawn` получает замыкание.

Порядок выполнения потоков заранее не гарантирован:

```text
main thread ────────┐
                    │ concurrent
spawned thread ─────┘
```

Главный поток может завершиться раньше дочернего, поэтому сам по себе `spawn` не гарантирует, что дочерний поток успеет закончить работу.

---

# `JoinHandle` и `join`

`thread::spawn` возвращает:

```text
JoinHandle
```

Можно вызвать:

```rust
handle.join().unwrap();
```

`join` блокирует текущий поток до завершения соответствующего потока. Язык программирования Rust(2)

Модель:

```text
spawn
  ↓
JoinHandle
  ↓
join()
  ↓
wait until thread finished
```

Где расположен `join`, важно.

Если сначала `join`, а потом работа `main`, настоящего чередования выполнения этих участков уже не получится.

---

# `move` в потоках

Новый поток может жить дольше области, в которой был создан.

Поэтому такой код опасен концептуально:

```rust
let v = vec![1, 2, 3];

thread::spawn(|| {
    println!("{v:?}");
});
```

Поток мог бы сохранить ссылку на `v`, а `v` уже быть уничтожен.

Используется:

```rust
thread::spawn(move || {
    println!("{v:?}");
});
```

`move` передаёт ownership нужных значений замыканию нового потока. Язык программирования Rust(2)

---

# Каналы

Вместо совместного изменения данных потоки могут **передавать сообщения**.

Создание:

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();
```

Где:

```text
tx
→ transmitter
→ sender

rx
→ receiver
```

Пример:

```rust
thread::spawn(move || {
    let msg = String::from("hi");

    tx.send(msg).unwrap();
});

let received = rx.recv().unwrap();
```

Язык программирования Rust(2)

---

## `send` передаёт ownership

```rust
tx.send(value)
```

для non-`Copy` значения перемещает ownership в канал.

После:

```rust
tx.send(val).unwrap();
```

использовать:

```rust
val
```

у отправителя уже нельзя.

Модель:

```text
producer owns value
        ↓ send
channel owns/transfers value
        ↓ receive
consumer owns value
```

Это важная гарантия: отправитель не может одновременно продолжать менять объект, который уже передал другому потоку. Язык программирования Rust(2)

---

## `recv` и `try_recv`

```rust
rx.recv()
```

блокирует поток:

```text
нет сообщения
→ ждать

сообщение пришло
→ Ok(value)

канал закрыт
→ Err(...)
```

`try_recv()`:

```text
не блокирует
→ сразу возвращает Result
```

Он полезен, если поток должен параллельно выполнять другую работу и лишь периодически проверять канал. Язык программирования Rust(2)

`rx` также можно использовать как итератор, получая сообщения до закрытия канала.

---

# `Mutex<T>`

При shared-state подходе несколько потоков работают с одними данными.

Для контролируемого изменяемого доступа:

```rust
Mutex<T>
```

Пример:

```rust
let m = Mutex::new(5);

{
    let mut value = m.lock().unwrap();
    *value = 6;
}
```

`lock()`:

```text
пытается получить блокировку
        ↓
если занята
→ текущий поток ждёт

если получена
→ доступ к данным
```

`lock()` возвращает `MutexGuard`, обёрнутый в `LockResult`. `MutexGuard` реализует `Deref`, поэтому ведёт себя подобно ссылке на внутреннее значение. Язык программирования Rust(2)

---

## Автоматическое снятие блокировки

`MutexGuard` также реализует:

```text
Drop
```

Когда guard выходит из области видимости:

```text
MutexGuard dropped
      ↓
mutex unlocked
```

Не нужно вручную помнить о разблокировке. Язык программирования Rust(2)

Это связь с первой половиной шага:

```text
Drop
→ автоматическое управление ресурсом

здесь ресурс
→ mutex lock
```

---

# Почему одного `Mutex<T>` недостаточно

Если нужно передать один `Mutex<T>` нескольким потокам, возникает вопрос shared ownership.

Можно подумать о:

```text
Rc<Mutex<T>>
```

Но `Rc<T>` не потокобезопасен.

Его reference counter не предназначен для одновременного изменения из разных потоков. Поэтому `Rc<T>` не реализует `Send`, и компилятор не позволяет передать его между потоками. Язык программирования Rust(2)

---

# `Arc<T>`

Многопоточный аналог `Rc<T>`:

```rust
Arc<T>
```

`A` означает:

```text
atomic
```

Использование:

```rust
let counter =
    Arc::new(Mutex::new(0));
```

Для каждого потока:

```rust
let counter =
    Arc::clone(&counter);

let handle =
    thread::spawn(move || {
        let mut num =
            counter.lock().unwrap();

        *num += 1;
    });
```

Получается:

```text
Arc
→ shared ownership between threads

Mutex
→ exclusive mutable access
```

То есть классическая комбинация:

```text
Arc<Mutex<T>>
```

Язык программирования Rust(2)

---

# Связь `Rc<RefCell<T>>` и `Arc<Mutex<T>>`

Очень полезная модель:

```text
ОДИН ПОТОК

Rc<T>
→ multiple ownership

RefCell<T>
→ interior mutability

Rc<RefCell<T>>
→ shared mutable data
```

А в многопоточном случае:

```text
НЕСКОЛЬКО ПОТОКОВ

Arc<T>
→ thread-safe multiple ownership

Mutex<T>
→ synchronized interior mutability

Arc<Mutex<T>>
→ shared mutable state
```

Книга напрямую сопоставляет эти две пары. Язык программирования Rust(2)

---

# `Send`

`Send` — marker trait.

Он означает:

```text
ownership значения этого типа
можно безопасно передать
из одного потока в другой
```

Большинство типов Rust — `Send`.

Но, например:

```text
Rc<T>
→ не Send
```

поскольку его счётчик ссылок не потокобезопасен.

Если тип полностью состоит из `Send`-типов, он обычно автоматически получает `Send`. Язык программирования Rust(2)

---

# `Sync`

`Sync` означает:

```text
&T
можно безопасно использовать
из нескольких потоков
```

Книга формулирует связь так:

```text
T: Sync
если
&T: Send
```

Примеры:

```text
Rc<T>
→ не Sync

RefCell<T>
→ не Sync

Mutex<T>
→ Sync
```

`RefCell<T>` не подходит для многопоточного shared access, потому что его runtime-проверка borrowing не является потокобезопасной. Язык программирования Rust(2)

---

# 3. Важные детали

## `Box`, `Rc`, `RefCell` решают разные задачи

Не воспринимать их как взаимозаменяемые контейнеры.

```text
Box<T>
→ один владелец
→ heap
→ фиксированный размер указателя

Rc<T>
→ несколько владельцев
→ single-thread

RefCell<T>
→ один владелец напрямую,
  но borrowing проверяется runtime
```

Комбинация:

```text
Rc<RefCell<T>>
```

нужна, когда требуются одновременно:

```text
shared ownership
+
mutation
```

в однопоточном коде.

---

## Compile-time vs runtime borrowing

Обычные ссылки:

```text
ошибка borrowing
→ программа не компилируется
```

`RefCell<T>`:

```text
ошибка borrowing
→ программа компилируется
→ panic во время выполнения
```

Поэтому `RefCell<T>` расширяет набор выражаемых моделей, но переносит часть ошибок на runtime. Язык программирования Rust(2)

---

## `Rc` может создавать memory leaks

Rust гарантирует memory safety, но reference cycle через `Rc<T>` может логически удерживать данные навсегда.

Для связей, которые не являются владением:

```text
Rc<T>
→ strong ownership

Weak<T>
→ non-owning relation
```

Именно `Weak<T>` используется для разрыва таких циклов.

---

## Потоки не гарантируют порядок выполнения

После `spawn` нельзя полагаться на конкретное чередование инструкций между потоками.

Для гарантии завершения:

```rust
handle.join()
```

Но `join` блокирует текущий поток, поэтому его расположение влияет на степень параллельного выполнения. Язык программирования Rust(2)

---

## Message passing и shared state — разные модели

Через channel:

```text
передать ownership данных
→ другому потоку
```

Через:

```text
Arc<Mutex<T>>
```

несколько потоков продолжают работать с одним общим объектом.

Обе модели сохраняют фундаментальные правила ownership.

---

## `Mutex<T>` не устраняет все ошибки

Он помогает предотвращать несинхронизированный доступ к данным, но возможны логические ошибки вроде **deadlock**:

```text
thread A
owns lock 1
waits for lock 2

thread B
owns lock 2
waits for lock 1

→ оба ждут бесконечно
```

Rust не может автоматически исключить все такие сценарии. Язык программирования Rust(2)

---

## `Arc` не нужно использовать вместо `Rc` всегда

`Arc` использует атомарный reference counting, необходимый для потокобезопасности, но это имеет дополнительную стоимость.

Поэтому:

```text
single thread
→ Rc<T>

multiple threads
→ Arc<T>
```

если требуется именно reference-counted shared ownership. Язык программирования Rust(2)

---

# 4. Что запомнить

Основная карта smart pointers:

```text
Box<T>
→ heap
→ one owner
→ recursive types

Rc<T>
→ many owners
→ one thread

RefCell<T>
→ borrowing at runtime
→ interior mutability

Weak<T>
→ non-owning Rc reference
→ breaks reference cycles
```

---

Traits:

```text
Deref
→ smart pointer behaves like reference

Drop
→ automatic cleanup on scope exit
```

Deref coercion:

```text
&Box<String>
→ &String
→ &str
```

может выполняться автоматически.

---

Запомнить комбинацию:

```text
Rc<RefCell<T>>
```

как:

```text
multiple ownership
+
mutable inner value
+
single thread
```

---

Потоки:

```rust
let handle = thread::spawn(move || {
    ...
});

handle.join().unwrap();
```

Читать:

```text
spawn
→ создать поток

move
→ передать необходимые значения
  во владение closure

join
→ дождаться завершения
```

---

Каналы:

```rust
let (tx, rx) = mpsc::channel();

tx.send(value);
rx.recv();
```

Модель:

```text
producer
  │
  │ move value
  ▼
channel
  │
  ▼
consumer
```

`recv` ждёт.

`try_recv` не ждёт.

---

Общий изменяемый state:

```rust
Arc<Mutex<T>>
```

Читать:

```text
Arc
→ несколько потоков владеют

Mutex
→ один поток за раз
  получает изменяемый доступ
```

Основной паттерн:

```rust
let data =
    Arc::new(Mutex::new(value));

let data =
    Arc::clone(&data);

thread::spawn(move || {
    let mut value =
        data.lock().unwrap();

    // modify *value
});
```

---

Маркерные traits:

```text
Send
→ ownership можно передать
  между потоками

Sync
→ ссылки на значение можно
  безопасно использовать
  из нескольких потоков
```

Практически:

```text
Rc<T>
→ single-thread sharing

Arc<T>
→ multi-thread sharing

RefCell<T>
→ single-thread interior mutability

Mutex<T>
→ multi-thread synchronized mutability
```

---

Самая важная итоговая схема шага:

```text
                    OWNERSHIP
                        │
        ┌───────────────┴───────────────┐
        │                               │
     one owner                     many owners
        │                               │
     Box<T>                      Rc<T> / Arc<T>
                                        │
                         ┌──────────────┴─────────────┐
                         │                            │
                     one thread                 many threads
                         │                            │
                     Rc<T>                        Arc<T>


                    MUTABILITY
                        │
             ┌──────────┴──────────┐
             │                     │
          one thread           many threads
             │                     │
         RefCell<T>             Mutex<T>
```

И две комбинации, которые стоит запомнить буквально:

```text
Rc<RefCell<T>>
→ shared mutable state
→ single-thread

Arc<Mutex<T>>
→ shared mutable state
→ multi-thread
```

Главная идея обеих глав одна и та же: **Rust не отменяет ownership при переходе к сложным структурам данных или потокам. `Box`, `Rc`, `RefCell`, `Arc`, `Mutex`, каналы, `Send` и `Sync` лишь дают разные способы выразить владение и доступ так, чтобы система типов могла сохранить гарантии безопасности.**

**Объём конспекта:** примерно **13–15 тыс. символов** с кодом и схемами.

**Время переноса в тетрадь:** примерно **75–90 минут**. Это один из двух самых плотных шагов курса; при сокращении первым можно убрать реализацию собственного `Deref` и подробности `Weak::strong_count/weak_count`, но стоит сохранить `Box`, `Rc<RefCell<T>>`, циклы `Rc`, `spawn/join`, channels, `Arc<Mutex<T>>`, `Send` и `Sync`.
