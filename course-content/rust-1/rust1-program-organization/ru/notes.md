# Шаг 6. Организация программы

## 1. Тема

Модульная система Rust решает четыре задачи:

```text
package → объединяет один или несколько crates
crate   → единица компиляции
module  → организует код внутри crate
path    → указывает, где находится элемент
```

Кроме этого:

```text
pub     → управляет доступностью
use     → вводит путь в текущую область видимости
```

Книга разделяет систему организации программы именно на пакеты, крейты, модули и пути. Язык программирования Rust(2)

Главная иерархия:

```text
PACKAGE
│
├── CRATE
│    │
│    └── MODULE TREE
│         ├── module
│         │    ├── function
│         │    ├── struct
│         │    └── submodule
│         └── module
│
└── CRATE
```

---

# 2. Механизм

## Package и crate

### Crate

**Crate** — минимальный объём кода, который компилятор Rust рассматривает за один раз.

Даже если выполнить:

```bash
rustc main.rs
```

один переданный файл рассматривается как crate.

Есть два вида:

```text
binary crate
library crate
```

### Binary crate

Компилируется в исполняемый файл.

Должен иметь:

```rust
fn main()
```

Примеры назначения из книги: программа командной строки, сервер.

### Library crate

Не содержит `main` и не создаёт самостоятельный исполняемый файл.

Его задача — предоставить функциональность другому коду. Язык программирования Rust(2)

---

## Package

**Package** — один или несколько crates, объединённых общей функциональностью и описанных через:

```text
Cargo.toml
```

Ограничения пакета:

```text
может содержать:
→ сколько угодно binary crates

может содержать:
→ максимум один library crate

обязан содержать:
→ хотя бы один crate
```

Язык программирования Rust(2)

---

## Как Cargo определяет crates

Если есть:

```text
src/main.rs
```

Cargo считает его корнем binary crate с именем пакета.

Если есть:

```text
src/lib.rs
```

это корень library crate с тем же именем.

Если присутствуют оба:

```text
src/
├── main.rs
└── lib.rs
```

пакет содержит:

```text
1 binary crate
+
1 library crate
```

Дополнительные бинарные crates можно размещать:

```text
src/bin/
```

где каждый файл соответствует отдельному binary crate. Язык программирования Rust(2)

---

# Модули

## `mod`

Модули группируют связанные элементы внутри crate.

```rust
mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
    }

    mod serving {
        fn take_order() {}
    }
}
```

Модуль может содержать:

```text
functions
struct
enum
constants
traits
другие modules
```

Основная задача — организовать код и одновременно контролировать его видимость. Язык программирования Rust(2)

---

## Дерево модулей

Предыдущий код формирует дерево:

```text
crate
└── front_of_house
    ├── hosting
    │   └── add_to_waitlist
    └── serving
        └── take_order
```

Корнем является неявный модуль:

```text
crate
```

`src/main.rs` и `src/lib.rs` являются корневыми модулями соответствующих crates. Язык программирования Rust(2)

Связи между модулями:

```text
parent
│
├── child
└── child

два child одного parent
→ siblings
```

---

# Пути

Чтобы обратиться к элементу дерева модулей, используется **path**.

Элементы пути разделяются:

```rust
::
```

Есть два вида путей.

---

## Абсолютный путь

Начинается от корня crate.

Для текущего crate:

```rust
crate::front_of_house::hosting::add_to_waitlist()
```

То есть:

```text
crate
  ↓
front_of_house
  ↓
hosting
  ↓
add_to_waitlist
```

Для элемента внешнего crate абсолютный путь начинается с имени этого crate. Язык программирования Rust(2)

---

## Относительный путь

Начинается относительно текущего модуля.

Например:

```rust
front_of_house::hosting::add_to_waitlist()
```

Также могут использоваться:

```text
self
super
```

Книга отмечает, что выбор между абсолютным и относительным путём зависит от того, как код может перемещаться при реорганизации; в приведённом примере авторы предпочитают абсолютные пути, поскольку определения и использующий их код проще перемещать независимо. Язык программирования Rust(2)

---

## `super`

`super` означает переход к родительскому модулю.

```rust
fn deliver_order() {}

mod back_of_house {
    fn fix_incorrect_order() {
        super::deliver_order();
    }
}
```

Схема:

```text
crate
├── deliver_order
│
└── back_of_house
     └── fix_incorrect_order
             │
             └─ super::deliver_order
```

По смыслу `super` похож на:

```text
..
```

в пути файловой системы. Язык программирования Rust(2)

---

# 3. Важные детали

## Приватность по умолчанию

В Rust элементы по умолчанию приватны относительно родительских модулей.

Это относится к:

```text
modules
functions
structs
enums
methods
constants
```

Например:

```rust
mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {}
    }
}
```

из родительского кода `hosting` недоступен.

Главная идея:

```text
private by default
        ↓
внутренние детали скрыты
        ↓
наружу открывается только нужный API
```

При этом дочерние модули могут обращаться к элементам своих модулей-предков. Язык программирования Rust(2)

---

## `pub`

Чтобы сделать элемент доступным:

```rust
pub
```

Например:

```rust
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
    }
}
```

Важно: открыть только модуль недостаточно.

```rust
pub mod hosting {
    fn add_to_waitlist() {}
}
```

Здесь:

```text
hosting
→ public

add_to_waitlist
→ всё ещё private
```

`pub` у контейнера не делает автоматически публичным его содержимое. Язык программирования Rust(2)

---

# `pub struct` и поля

Для структуры:

```rust
pub struct Breakfast {
    pub toast: String,
    seasonal_fruit: String,
}
```

сама структура доступна снаружи, но поля по-прежнему независимо подчиняются правилам приватности.

Здесь:

```text
Breakfast       public
toast           public
seasonal_fruit  private
```

Если структура содержит private-поля, внешний код не сможет самостоятельно заполнить их при создании экземпляра. В примере книги структура предоставляет для этого публичную ассоциированную функцию. Язык программирования Rust(2)

Это позволяет скрывать внутреннее состояние за публичным API.

---

# `pub enum`

Для enum правило отличается:

```rust
pub enum Appetizer {
    Soup,
    Salad,
}
```

Если сам `enum` public, его варианты автоматически public:

```text
Appetizer::Soup
Appetizer::Salad
```

То есть:

```text
pub struct
→ поля всё ещё private по умолчанию

pub enum
→ варианты доступны
```

Язык программирования Rust(2)

---

# `use`

Длинные пути неудобно постоянно повторять:

```rust
crate::front_of_house::hosting::add_to_waitlist();
```

`use` позволяет ввести путь в область видимости:

```rust
use crate::front_of_house::hosting;

hosting::add_to_waitlist();
```

`use` не меняет расположение элемента в дереве модулей — он создаёт удобное имя в текущей области видимости. Язык программирования Rust(2)

---

## `use` действует только в своей области

```rust
use crate::front_of_house::hosting;
```

имя `hosting` доступно только в той области видимости, где находится этот `use`.

Если перейти в дочерний модуль, это имя автоматически туда не переносится. Язык программирования Rust(2)

То есть:

```text
use
↓
локальный импорт имени
↓
не глобальный для всего crate
```

---

# Идиоматический `use`

Книга различает распространённый стиль импорта функций и типов.

Для функции обычно импортируется её родительский модуль:

```rust
use crate::front_of_house::hosting;

hosting::add_to_waitlist();
```

а не:

```rust
use crate::front_of_house::hosting::add_to_waitlist;

add_to_waitlist();
```

Так из вызова видно, что функция определена не локально.

Для структур, enum и других типов обычно импортируется сам тип:

```rust
use std::collections::HashMap;

let map = HashMap::new();
```

Это соглашение Rust-кода, а не техническое ограничение языка. Язык программирования Rust(2)

---

# Конфликт одинаковых имён и `as`

Нельзя напрямую импортировать в одну область два типа с одинаковым именем:

```text
std::fmt::Result
std::io::Result
```

Один вариант — импортировать родительские модули:

```rust
use std::fmt;
use std::io;

fn f1() -> fmt::Result { ... }
fn f2() -> io::Result<()> { ... }
```

Другой — использовать псевдоним:

```rust
use std::fmt::Result;
use std::io::Result as IoResult;
```

Теперь:

```text
Result
IoResult
```

не конфликтуют. Язык программирования Rust(2)

---

# `pub use` — реэкспорт

Обычный:

```rust
use ...
```

создаёт приватное имя в текущей области.

Но:

```rust
pub use ...
```

делает это имя частью публичного API.

Пример:

```rust
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
    }
}

pub use crate::front_of_house::hosting;
```

Без реэкспорта внешний путь мог бы быть:

```text
restaurant::front_of_house::hosting::add_to_waitlist
```

После:

```rust
pub use ...
```

можно предоставить более удобный путь:

```text
restaurant::hosting::add_to_waitlist
```

Это позволяет отделить:

```text
внутреннюю организацию библиотеки
           от
её внешнего публичного API
```

Язык программирования Rust(2)

---

# Внешние packages

Для внешнего пакета механизм уже знаком из Cargo.

Сначала зависимость указывается:

```toml
[dependencies]
...
```

После этого Cargo делает crate доступным проекту, а нужные элементы можно вводить в область видимости через `use`.

Стандартная библиотека:

```text
std
```

тоже является crate, но добавлять её в `Cargo.toml` не требуется, поскольку она поставляется вместе с Rust. Язык программирования Rust(2)

---

# Группировка `use`

Вместо:

```rust
use std::cmp::Ordering;
use std::io;
```

можно:

```rust
use std::{cmp::Ordering, io};
```

Если один путь является частью другого:

```rust
use std::io;
use std::io::Write;
```

можно:

```rust
use std::io::{self, Write};
```

`self` здесь означает сам `std::io`, а `Write` — элемент внутри него. Язык программирования Rust(2)

---

## Glob `*`

Можно импортировать все публичные элементы:

```rust
use std::collections::*;
```

Но книга рекомендует осторожность: после такого импорта труднее понять, какие имена находятся в области видимости и откуда они пришли.

В книге `*` отмечается как часто применяемый в тестах и иногда в prelude-паттерне. Язык программирования Rust(2)

---

# Разделение модулей по файлам

Модульное дерево и файловая структура связаны, но **модуль определяется через `mod`**, а не просто существованием файла.

Например:

```rust
mod front_of_house;
```

в:

```text
src/lib.rs
```

сообщает компилятору, что содержимое модуля нужно найти во внешнем файле.

Основной вариант:

```text
src/front_of_house.rs
```

Книга также указывает поддерживаемый старый вариант:

```text
src/front_of_house/mod.rs
```

Язык программирования Rust(2)

---

## Подмодули в отдельных файлах

Допустим:

```text
front_of_house
└── hosting
```

Файловая структура:

```text
src/
├── lib.rs
├── front_of_house.rs
└── front_of_house/
    └── hosting.rs
```

`src/lib.rs`:

```rust
mod front_of_house;
```

`src/front_of_house.rs`:

```rust
pub mod hosting;
```

`src/front_of_house/hosting.rs`:

```rust
pub fn add_to_waitlist() {}
```

Модуль `hosting` — дочерний для `front_of_house`, поэтому файл располагается в каталоге, соответствующем родительскому модулю. Язык программирования Rust(2)

---

## `mod` — не текстовый include

Важная деталь книги:

```rust
mod front_of_house;
```

не означает «вставить содержимое файла сюда».

Он объявляет модуль в определённой точке **дерева модулей**.

После того как файл один раз включён в дерево через `mod`, остальной код обращается к его элементам по путям.

То есть:

```text
файлы
→ физическое размещение кода

modules
→ логическая структура кода
```

Язык программирования Rust(2)

---

# Binary + library в одном package

Книга отдельно рекомендует полезную структуру, когда пакет содержит:

```text
src/main.rs
src/lib.rs
```

Большую часть функциональности размещают в library crate, а binary crate содержит достаточно кода, чтобы запустить приложение и вызвать библиотечную часть.

Тогда:

```text
lib.rs
→ основная переиспользуемая логика

main.rs
→ запуск программы
```

Binary crate использует public API library crate подобно внешнему пользователю библиотеки. Это помогает одновременно делать функциональность переиспользуемой и проверять качество публичного API. Язык программирования Rust(2)

---

# 4. Что запомнить

Главная иерархия:

```text
PACKAGE
→ Cargo.toml
→ содержит crates

CRATE
→ единица компиляции

MODULE
→ организация кода внутри crate

PATH
→ адрес элемента в дереве модулей
```

---

Корни crates:

```text
src/main.rs
→ binary crate root

src/lib.rs
→ library crate root

src/bin/*.rs
→ дополнительные binary crates
```

Пакет:

```text
не более 1 library crate
любое число binary crates
минимум 1 crate
```

---

Модули:

```rust
mod module_name {
    ...
}
```

или:

```rust
mod module_name;
```

если код вынесен в файл.

Дерево:

```text
crate
└── module
    └── submodule
```

---

Пути:

```rust
crate::module::item
```

→ абсолютный путь внутри текущего crate.

```rust
module::item
```

→ относительный путь.

```rust
super::item
```

→ элемент родительского модуля.

---

Приватность:

```text
по умолчанию
→ private
```

Открыть:

```rust
pub mod ...
pub fn ...
pub struct ...
pub enum ...
```

Но помнить:

```text
pub module
≠ всё внутри public
```

Для структур:

```text
pub struct
→ поля всё равно private,
  пока не указано pub
```

Для enum:

```text
pub enum
→ его варианты public
```

---

`use`:

```rust
use crate::some::module;
```

→ короткое имя в текущей области.

`as`:

```rust
use std::io::Result as IoResult;
```

→ переименование для устранения конфликта.

`pub use`:

```rust
pub use crate::internal::item;
```

→ реэкспорт и часть внешнего API.

---

Минимальная модель организации реального проекта:

```text
Cargo.toml
│
└── src/
    ├── lib.rs
    │     ↓
    │   module tree
    │     ↓
    │   основная логика/API
    │
    ├── main.rs
    │     ↓
    │   запуск приложения
    │
    └── modules...
```

И три правила, которые особенно важно не путать:

```text
1. Файл сам по себе не становится модулем.
   Модуль должен быть объявлен через mod.

2. pub открывает только тот элемент,
   перед которым написан.

3. use не перемещает и не открывает элемент.
   Он только вводит удобное имя
   в конкретную область видимости.
```

Итоговая цепочка:

```text
Cargo.toml
   ↓
package
   ↓
crate root
   ↓
module tree
   ↓
paths
   ↓
pub определяет доступность
   ↓
use упрощает обращение
```

**Объём конспекта:** примерно **9–11 тыс. символов** с кодом и схемами.

**Время переноса в тетрадь:** примерно **50–65 минут**. Самое важное для повторения через несколько месяцев — различать `package / crate / module`, понимать `crate::` и `super::`, правила `pub`, назначение `use`/`pub use` и связь `mod` с файловой структурой.
