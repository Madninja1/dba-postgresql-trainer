# Шаг 11. Тестирование + архитектура приложения

## 1. Тема

Компилятор Rust проверяет типы, ownership, borrowing и lifetimes, но не может доказать, что программа выполняет именно ту бизнес-логику, которую задумал программист. Для этого используются автоматические тесты. Язык программирования Rust(2)

Базовая модель теста:

```text
подготовить данные
      ↓
выполнить код
      ↓
проверить результат
```

Вторая часть шага — организация обычного приложения. На примере `minigrep` книга постепенно разделяет программу на:

```text
main.rs
→ запуск
→ ввод/вывод
→ обработка ошибок верхнего уровня

lib.rs
→ основная логика
→ Config
→ run
→ функции, которые удобно тестировать
```

Такое разделение особенно важно, потому что код библиотеки можно вызывать напрямую из тестов, не запуская каждый раз готовый бинарный файл. Язык программирования Rust(2)

---

# 2. Механизм

## Базовый тест

Тест в Rust — обычная функция с атрибутом:

```rust
#[test]
fn it_works() {
    let result = 2 + 2;

    assert_eq!(result, 4);
}
```

Запуск:

```bash
cargo test
```

`#[test]` сообщает тестовому runner, что функцию нужно выполнить как тест. Cargo компилирует тестовый бинарный файл, запускает отмеченные функции и сообщает результат. Язык программирования Rust(2)

---

## `assert!`

Проверяет логическое выражение:

```rust
assert!(condition);
```

Тест проходит, если:

```text
condition == true
```

Например:

```rust
assert!(larger.can_hold(&smaller));
```

Обратная проверка:

```rust
assert!(!smaller.can_hold(&larger));
```

Если выражение ложно, тест паникует и считается проваленным.

---

## `assert_eq!` и `assert_ne!`

Для сравнения значений удобнее:

```rust
assert_eq!(actual, expected);
```

и:

```rust
assert_ne!(a, b);
```

При ошибке `assert_eq!` и `assert_ne!` выводят сравниваемые значения, поэтому обычно дают больше информации, чем:

```rust
assert!(a == b);
```

Для работы этих макросов сравниваемые типы должны поддерживать `PartialEq`, а для диагностического вывода — `Debug`. Для собственных типов это часто можно получить через:

```rust
#[derive(PartialEq, Debug)]
```

Язык программирования Rust(2)

---

## Сообщение при ошибке

К assertions можно добавлять пояснение:

```rust
assert!(
    result.contains(name),
    "Greeting did not contain name: {result}"
);
```

То же возможно для:

```text
assert!
assert_eq!
assert_ne!
```

Дополнительные аргументы форматируются аналогично `format!`.

Практический смысл:

```text
assertion failed
+
контекст причины
→ быстрее понять, что именно нарушилось
```

---

# Проверка `panic!`

Иногда правильное поведение функции — вызвать panic при нарушении контракта.

Для этого:

```rust
#[test]
#[should_panic]
fn greater_than_100() {
    Guess::new(200);
}
```

Тест считается успешным, если код действительно паникует.

Но простой `should_panic` слишком широк:

```text
произошла любая panic
→ тест прошёл
```

Даже если паника возникла не по той причине.

Поэтому точнее:

```rust
#[test]
#[should_panic(expected = "less than or equal to 100")]
fn greater_than_100() {
    Guess::new(200);
}
```

Теперь сообщение panic должно содержать указанную подстроку. Язык программирования Rust(2)

---

# Тесты с `Result`

Тест не обязан завершаться через panic.

Он может вернуть:

```rust
Result<(), String>
```

Концептуально:

```rust
#[test]
fn it_works() -> Result<(), String> {
    if 2 + 2 == 4 {
        Ok(())
    } else {
        Err(String::from("two plus two does not equal four"))
    }
}
```

Модель:

```text
Ok(())
→ test passed

Err(...)
→ test failed
```

Это удобно, когда внутри теста уже есть операции, возвращающие `Result`, и хочется использовать `?`.

Книга отдельно отмечает, что `#[should_panic]` с таким стилем не используется: если требуется проверить ошибку `Result`, нужно работать с самим `Result`. Язык программирования Rust(2)

---

# Организация unit tests

Типичная структура:

```rust
pub fn add_two(a: u64) -> u64 {
    a + 2
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_adds_two() {
        assert_eq!(add_two(2), 4);
    }
}
```

Здесь:

```text
#[cfg(test)]
→ модуль компилируется только при cargo test

mod tests
→ отдельный модуль тестов

use super::*
→ даёт тестам доступ к содержимому родительского модуля
```

Unit tests обычно размещаются рядом с тестируемым кодом в `src`. Они могут тестировать и приватные функции, потому что являются дочерним модулем тестируемого модуля. Язык программирования Rust(2)

---

# Integration tests

Интеграционные тесты находятся отдельно:

```text
project/
├── src/
│   └── lib.rs
└── tests/
    └── integration_test.rs
```

Например:

```rust
use adder::add_two;

#[test]
fn it_adds_two() {
    assert_eq!(add_two(2), 4);
}
```

Каждый файл внутри `tests/` компилируется как отдельный crate.

Это значит, что integration test смотрит на библиотеку **как внешний пользователь**:

```text
может использовать public API
не может напрямую использовать private API
```

Для файлов в `tests/` отдельный:

```rust
#[cfg(test)]
```

не требуется — Cargo сам знает, что это integration tests. Язык программирования Rust(2)

---

## Unit vs integration

```text
UNIT TEST
→ рядом с кодом
→ небольшой участок
→ может проверять private API

INTEGRATION TEST
→ каталог tests/
→ внешний crate
→ только public API
→ проверяет совместную работу частей
```

Оба вида нужны для разных уровней проверки. Язык программирования Rust(2)

---

# Полезные команды тестов

Основная:

```bash
cargo test
```

Один тест:

```bash
cargo test one_hundred
```

Или фильтр по части имени:

```bash
cargo test add
```

Тесты по умолчанию могут выполняться параллельно, поэтому они не должны без необходимости зависеть от общего изменяемого состояния. Язык программирования Rust(2)

Дорогой тест можно отметить:

```rust
#[test]
#[ignore]
fn expensive_test() {
    ...
}
```

Запустить только игнорируемые:

```bash
cargo test -- --ignored
```

Это уже второстепенная возможность, но её полезно узнавать в реальном проекте. Язык программирования Rust(2)

# Архитектура приложения

## Проблема большого `main`

В начале `minigrep` всё можно было написать внутри:

```rust
fn main() {
    ...
}
```

Но тогда `main` начинает одновременно отвечать за:

```text
чтение CLI-аргументов
разбор аргументов
конфигурацию
чтение файла
поиск
вывод
обработку ошибок
```

Такой код трудно отдельно тестировать и расширять.

Поэтому книга постепенно разделяет обязанности.

---

# CLI-аргументы

Аргументы программы можно получить через:

```rust
use std::env;

let args: Vec<String> = env::args().collect();
```

При запуске:

```bash
cargo run -- needle haystack
```

вектор концептуально содержит:

```text
args[0] → имя/путь запущенной программы
args[1] → "needle"
args[2] → "haystack"
```

`--` здесь отделяет аргументы Cargo от аргументов самой программы. Язык программирования Rust(2)

---

# `Config` вместо отдельных переменных

Вместо того чтобы хранить связанные параметры независимо:

```rust
query
file_path
ignore_case
```

книга объединяет их в структуру:

```rust
pub struct Config {
    pub query: String,
    pub file_path: String,
    pub ignore_case: bool,
}
```

Причина:

```text
эти значения вместе описывают
конфигурацию одного запуска
```

Структура делает эту связь явной.

Ранний вариант с кортежем был заменён `Config`, потому что именованные поля лучше выражают смысл данных и облегчают поддержку. Язык программирования Rust(2)

---

# `Config::build`

Разбор аргументов выносится из `main`:

```rust
impl Config {
    fn build(args: &[String])
        -> Result<Config, &'static str>
    {
        if args.len() < 3 {
            return Err("not enough arguments");
        }

        let query = args[1].clone();
        let file_path = args[2].clone();

        Ok(Config {
            query,
            file_path,
            ignore_case: false,
        })
    }
}
```

Главная архитектурная идея здесь важнее конкретной реализации:

```text
main
не должен знать детали:
"какой индекс означает query?"

Config::build
берёт сырые входные данные
и превращает их в осмысленную конфигурацию
```

Кроме того, `build` возвращает `Result`, а не вызывает `panic!`, потому что отсутствие аргументов — ожидаемая ошибка пользовательского ввода. Язык программирования Rust(2)

---

# `main` обрабатывает ошибку конфигурации

Примерная модель:

```rust
let config = Config::build(&args)
    .unwrap_or_else(|err| {
        eprintln!(
            "Problem parsing arguments: {err}"
        );

        process::exit(1);
    });
```

Ответственность разделена:

```text
Config::build
→ обнаруживает проблему
→ возвращает Err

main
→ решает, как показать ошибку пользователю
→ завершает процесс
```

То есть библиотечная логика сообщает об ошибке, а верхний уровень определяет пользовательское поведение.

---

# `run` — основное выполнение приложения

После создания `Config` сама работа программы выносится в:

```rust
fn run(config: Config)
    -> Result<(), Box<dyn Error>>
{
    let contents =
        fs::read_to_string(config.file_path)?;

    // основная работа

    Ok(())
}
```

Сигнатура:

```text
Result<(), Box<dyn Error>>
```

означает:

```text
успех
→ Ok(())
→ полезного возвращаемого значения нет

ошибка
→ Err(...)
```

`()` показывает, что функция выполняется ради своих действий, а не ради возвращения некоторого результата.

`?` передаёт ошибку чтения файла вверх вызывающему коду. Язык программирования Rust(2)

---

# Чтение файла

Основная операция:

```rust
let contents =
    fs::read_to_string(file_path)?;
```

`fs::read_to_string`:

```text
принимает путь
→ пытается открыть файл
→ читает содержимое
→ возвращает Result<String, ...>
```

То есть работа с файлами естественно встраивается в уже изученный `Result` + `?`. Язык программирования Rust(2)

# Разделение `main.rs` и `lib.rs`

После рефакторинга структура становится примерно такой:

```text
src/
├── main.rs
└── lib.rs
```

`main.rs`:

```text
получить внешние входные данные
        ↓
создать Config
        ↓
вызвать run
        ↓
вывести ошибку
        ↓
установить код завершения
```

`lib.rs`:

```text
Config
run
search
search_case_insensitive
основная логика
```

В результате большая часть функциональности становится библиотечным API и может тестироваться напрямую. Язык программирования Rust(2)

Это одна из ключевых архитектурных идей главы.

# Переменные окружения

Конфигурация может поступать не только через CLI.

Например, книга использует:

```text
IGNORE_CASE
```

и проверяет её через `std::env`.

Модель:

```text
CLI arguments
        ┐
        ├──→ Config
environment variables
        ┘
```

В `Config` затем появляется:

```rust
ignore_case: bool
```

а `run` выбирает нужное поведение:

```text
ignore_case == false
→ search(...)

ignore_case == true
→ search_case_insensitive(...)
```

Книга также отмечает, что если одна настройка может задаваться несколькими источниками, программе нужно определить, какой источник имеет приоритет. Язык программирования Rust(2)

---

# `stdout` и `stderr`

Результаты программы и ошибки следует разделять.

Обычный вывод:

```rust
println!("...");
```

идёт в:

```text
stdout
```

Ошибки:

```rust
eprintln!("...");
```

идут в:

```text
stderr
```

Почему это важно?

Например:

```bash
cargo run -- to poem.txt > output.txt
```

перенаправляет `stdout` в файл.

Если сообщения об ошибках тоже печатать через `println!`, они попадут в `output.txt` вместе с нормальными результатами.

Поэтому:

```text
stdout
→ данные успешной работы

stderr
→ диагностические сообщения и ошибки
```

Книга заменяет вывод ошибок в `main` на `eprintln!`, чтобы перенаправление нормального вывода не поглощало ошибки. Язык программирования Rust(2)

# 3. Важные детали

## Тесты и архитектура напрямую связаны

Если вся логика находится в:

```text
src/main.rs
```

интеграционным тестам трудно использовать её напрямую.

Binary crate предназначен для запуска, а library crate может предоставлять функции другим crates.

Поэтому книга рекомендует модель:

```text
main.rs
→ тонкая оболочка

lib.rs
→ реальная логика
```

Это одновременно улучшает:

```text
тестируемость
модульность
обработку ошибок
повторное использование
```

Язык программирования Rust(2)

---

## `main` должен быть небольшим

Хорошая итоговая модель `main`:

```text
1. получить вход
2. собрать Config
3. вызвать run
4. обработать верхнеуровневую ошибку
```

А не:

```text
main
→ содержит всю бизнес-логику приложения
```

---

## Не использовать `panic!` для обычного плохого CLI-ввода

Например:

```text
пользователь забыл аргумент
```

— это ожидаемая ситуация.

Поэтому:

```text
Config::build
→ Result
```

лучше, чем безусловный:

```rust
panic!("not enough arguments");
```

Пользователь получает нормальное сообщение, а не технический panic/backtrace.

---

## Не игнорировать `Result`

Если:

```rust
run(config);
```

возвращает `Result`, а его никак не обработать, Rust выдаёт предупреждение.

Нужно:

```text
обработать Err
или
явно пробросить его
```

В `minigrep` ошибку `run` обрабатывает `main`. Язык программирования Rust(2)

---

## TDD как рабочий цикл

Глава 12 показывает простой цикл test-driven development:

```text
1. написать тест
2. убедиться, что он падает
3. написать минимум кода для прохождения
4. выполнить рефакторинг
5. повторить
```

Например, сначала создаётся тест для `search`, затем минимальная пустая реализация, затем рабочий поиск.

Книга не объявляет TDD единственным способом разработки, но использует его как способ постепенно развивать `minigrep`. Язык программирования Rust(2)

# 4. Что запомнить

Минимальная структура теста:

```rust
#[test]
fn something_works() {
    let result = operation();

    assert_eq!(result, expected);
}
```

Основные assertions:

```text
assert!(condition)
→ условие должно быть true

assert_eq!(a, b)
→ a == b

assert_ne!(a, b)
→ a != b
```

Проверка panic:

```rust
#[test]
#[should_panic(expected = "text")]
fn invalid_value_panics() {
    ...
}
```

---

Unit tests:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_name() {
        ...
    }
}
```

```text
→ находятся рядом с кодом
→ могут тестировать private части
```

Integration tests:

```text
tests/
└── integration_test.rs
```

```text
→ отдельный crate
→ использует библиотеку снаружи
→ видит только public API
```

---

Главная архитектура приложения:

```text
main.rs
│
├─ получить args
├─ создать Config
├─ вызвать run
├─ вывести ошибки
└─ завершить процесс

lib.rs
│
├─ Config
├─ Config::build
├─ run
├─ search
└─ основная логика
```

---

CLI:

```rust
env::args()
```

Файл:

```rust
fs::read_to_string(path)?
```

Переменные окружения:

```text
std::env
→ дополнительный источник Config
```

Вывод:

```text
println!
→ stdout
→ нормальный результат

eprintln!
→ stderr
→ ошибки
```

---

Обработка ошибок приложения:

```text
Config::build(...)
       ↓
Result<Config, ...>
       ↓
main

run(config)
       ↓
Result<(), ...>
       ↓
main
```

То есть:

```text
нижний уровень
→ возвращает ошибку

верхний уровень
→ решает, как показать её пользователю
```

---

Самая важная связь этого шага:

```text
ХОРОШО РАЗДЕЛЁННЫЙ КОД
        ↓
легче тестировать
        ↓
ошибки проще обрабатывать
        ↓
main становится маленьким
        ↓
основная логика живёт в library crate
```

Итоговая модель:

```text
compiler checks
→ безопасность типов и памяти

tests check
→ ожидаемое поведение программы

architecture
→ делает это поведение
  удобным для тестирования
```

Поэтому тестирование и архитектура здесь рассматриваются вместе: **чем меньше логики спрятано внутри `main`, тем проще вызывать её напрямую, проверять результат и отдельно обрабатывать ввод-вывод и ошибки.**

**Объём конспекта:** примерно **10–12 тыс. символов** с кодом.

**Время переноса в тетрадь:** примерно **55–70 минут**. При сокращении можно убрать `#[ignore]` и часть команд фильтрации тестов; обязательно оставить `#[test]`, assertions, `should_panic`, unit/integration tests и модель `main.rs → Config → run → lib.rs`.
