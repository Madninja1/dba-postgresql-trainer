# Шаг 10. Lifetimes

## 1. Тема

**Lifetime — время жизни ссылки**, то есть область программы, в которой ссылка остаётся действительной.

У каждой ссылки в Rust есть lifetime, даже если он нигде явно не написан. В большинстве ситуаций компилятор выводит его самостоятельно. Явная аннотация требуется тогда, когда Rust не может однозначно определить взаимосвязь нескольких ссылок. Язык программирования Rust(2)

Главная задача lifetimes:

```text
не продлить существование данных

а доказать компилятору:

ссылка никогда не переживёт
данные, на которые она указывает
```

Иными словами:

```text
data lifetime
    ≥
reference lifetime
```

Если данные уничтожаются раньше ссылки:

```text
dangling reference
→ компиляция запрещена
```

---

# 2. Механизм

## Почему lifetimes вообще нужны

Рассмотрим:

```rust
fn main() {
    let r;

    {
        let x = 5;
        r = &x;
    }

    println!("{r}");
}
```

С точки зрения областей видимости:

```text
r  ──────────────────────────────┐
                                 │
       x ───────────┐             │
                    │             │
                    ↓             │
                 x уничтожен      │
                                  │
                       r используется
```

`r` живёт дольше, чем `x`.

После окончания внутреннего блока:

```text
x
→ уничтожен

r
→ всё ещё существует
→ но указывал бы на уничтоженное значение
```

Rust запрещает такой код.

Borrow checker сравнивает области жизни данных и ссылок и проверяет, что каждая ссылка остаётся действительной всё время своего использования. Язык программирования Rust(2)

---

## Безопасный вариант

```rust
fn main() {
    let x = 5;

    let r = &x;

    println!("{r}");
}
```

Теперь:

```text
x  ────────────────────────┐
                           │
     r ───────────────┐     │
                      │     │
                  use r     │
```

Данные `x` существуют дольше ссылки `r`.

Поэтому:

```text
reference lifetime
<
data lifetime

✓ безопасно
```

---

# Lifetime-аннотации

## `'a`

Обычная ссылка:

```rust
&i32
```

С явно указанным lifetime:

```rust
&'a i32
```

Изменяемая:

```rust
&'a mut i32
```

Синтаксис:

```text
&
'a
Type

↓
&'a Type
```

Имена lifetime начинаются с:

```text
'
```

и обычно короткие:

```text
'a
'b
```

Чаще всего первым используют `'a`. Язык программирования Rust(2)

---

## Главное: аннотация не продлевает lifetime

Это критически важно.

Запись:

```rust
&'a str
```

не означает:

```text
"сделай эту строку жить дольше"
```

Она означает:

```text
"эта ссылка участвует
в отношении времени жизни 'a"
```

Lifetime-аннотации **описывают отношения**, а не управляют временем существования данных.

```text
annotation
≠ изменение lifetime

annotation
= описание связи lifetimes
```

Язык программирования Rust(2)

---

# Lifetimes в функциях

## Проблема с двумя входными ссылками

Рассмотрим функцию:

```rust
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

Она возвращает ссылку.

Но какую?

```text
иногда → x
иногда → y
```

Компилятор не знает заранее:

```text
какая ветка выполнится
какой аргумент будет возвращён
как lifetime x связан с lifetime y
```

Поэтому сигнатуры недостаточно.

---

## Связываем ссылки через `'a`

```rust
fn longest<'a>(
    x: &'a str,
    y: &'a str,
) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

Теперь контракт сообщает Rust:

```text
x      → живёт как минимум 'a
y      → живёт как минимум 'a
result → живёт как минимум 'a
```

Важно понимать это правильно.

Это **не означает**, что реальные lifetimes `x` и `y` обязаны быть полностью одинаковыми.

При конкретном вызове `'a` становится той областью, где времена жизни обеих ссылок пересекаются.

Практически для `longest`:

```text
lifetime(result)
=
меньший из lifetime(x) и lifetime(y)
```

Язык программирования Rust(2)

---

## Почему берётся меньший lifetime

Например:

```rust
let string1 = String::from("long string is long");

{
    let string2 = String::from("xyz");

    let result =
        longest(string1.as_str(), string2.as_str());

    println!("{result}");
}
```

Схема:

```text
string1 ────────────────────────────┐
                                   │
      string2 ────────────┐         │
                          │         │
      result  ────────────┘         │
```

Результат используется только там, где действительны **обе** входные ссылки.

Такой код безопасен.

---

## Когда использование результата запрещается

```rust
let string1 = String::from("long string is long");

let result;

{
    let string2 = String::from("xyz");

    result =
        longest(string1.as_str(), string2.as_str());
}

println!("{result}");
```

Проблема:

```text
string1 ────────────────────────────────┐
                                       │
     string2 ────────┐                  │
                     ↓                  │
                  уничтожен             │
                                       │
                         result используется
```

Даже если человек видит, что в конкретных данных функция вернула бы `string1`, контракт `longest` допускает возврат любой из двух ссылок.

Поэтому Rust использует более короткий lifetime и запрещает использование `result` после уничтожения `string2`.

---

# Lifetime — часть контракта функции

Аннотации находятся в **сигнатуре**, а не в теле:

```rust
fn longest<'a>(
    x: &'a str,
    y: &'a str,
) -> &'a str
```

Подобно:

```rust
fn f<T>(...)
```

где `T` — обобщение типа,

```rust
fn f<'a>(...)
```

обобщает время жизни ссылки.

Сигнатура сообщает отношения, на которые может рассчитывать borrow checker.

```text
types
→ контракт типов

lifetimes
→ контракт ссылок
```

---

# Не все ссылки должны иметь один lifetime

Предположим, функция всегда возвращает только `x`:

```rust
fn longest<'a>(
    x: &'a str,
    y: &str,
) -> &'a str {
    x
}
```

Здесь:

```text
result связан с x

result не связан с y
```

Поэтому lifetime нужно связать только:

```text
x ↔ result
```

а lifetime `y` не требуется включать в это отношение.

Главный принцип:

> Lifetime-аннотации должны описывать реальные отношения ссылок, создаваемые функцией.

---

# Нельзя исправить dangling reference аннотацией

Рассмотрим:

```rust
fn longest<'a>(
    x: &str,
    y: &str,
) -> &'a str {
    let result =
        String::from("really long string");

    result.as_str()
}
```

Это не работает.

Причина:

```text
result
→ создаётся внутри функции
→ владеет String
→ уничтожается при выходе из функции

result.as_str()
→ ссылка на этот String
```

Функция попыталась бы вернуть:

```text
ссылку
↓
на уже уничтоженные данные
```

Никакая запись:

```rust
'a
```

не способна продлить существование `result`.

В такой ситуации книга указывает другое решение: **вернуть владеющее значение**, а не ссылку.

Например концептуально:

```rust
fn make_string() -> String {
    String::from("...")
}
```

Тогда ownership передаётся вызывающему коду.

Это важнейшее правило:

```text
lifetime annotation
может описать безопасную ссылку

но

lifetime annotation
не может сделать небезопасную ссылку безопасной
```

# Lifetimes в структурах

Структура может хранить ссылку:

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}
```

Здесь `'a` является частью типа структуры.

Смысл:

```text
ImportantExcerpt<'a>
не может жить дольше,
чем данные,
на которые ссылается part
```

Язык программирования Rust(2)

---

Пример:

```rust
let novel =
    String::from("Call me Ishmael. Some years ago...");

let first_sentence =
    novel.split('.').next().unwrap();

let i = ImportantExcerpt {
    part: first_sentence,
};
```

Схема:

```text
novel
  │
  └────→ строковые данные
             ▲
             │
        first_sentence
             ▲
             │
     ImportantExcerpt.part
```

Пока существует структура с такой ссылкой, исходные данные должны оставаться действительными.

---

## Почему lifetime нужен структуре

Если написать концептуально:

```rust
struct Something {
    value: &str,
}
```

возникает вопрос:

```text
как долго должны жить данные,
на которые указывает value?
```

Поэтому структура с ссылочным полем должна выразить эту связь:

```rust
struct Something<'a> {
    value: &'a str,
}
```

Снова:

```text
структура не владеет данными

она заимствует их
```

и lifetime описывает это заимствование.

---

# 3. Важные детали

# Lifetime elision

## Почему lifetimes не пишутся постоянно

Например, эта уже знакомая функция компилируется:

```rust
fn first_word(s: &str) -> &str {
    ...
}
```

Хотя формально связь выглядит примерно так:

```rust
fn first_word<'a>(
    s: &'a str,
) -> &'a str {
    ...
}
```

Причина — **правила неявного выведения lifetimes**.

Rust может автоматически восстановить некоторые распространённые отношения, поэтому программисту не приходится писать `'a` в каждой функции. Язык программирования Rust(2)

---

# Три правила lifetime elision

Компилятор последовательно применяет три правила.

## Правило 1

Каждый ссылочный входной параметр получает собственный lifetime.

Было:

```rust
fn foo(x: &i32)
```

Компилятор рассматривает как:

```rust
fn foo<'a>(x: &'a i32)
```

Для двух ссылок:

```rust
fn foo(x: &i32, y: &i32)
```

получается:

```rust
fn foo<'a, 'b>(
    x: &'a i32,
    y: &'b i32,
)
```

То есть по умолчанию:

```text
каждый input reference
→ свой lifetime
```

---

## Правило 2

Если имеется **ровно один входной lifetime**, он назначается всем выходным ссылкам.

```rust
fn first_word(s: &str) -> &str
```

после первого правила:

```rust
fn first_word<'a>(
    s: &'a str,
) -> &str
```

после второго:

```rust
fn first_word<'a>(
    s: &'a str,
) -> &'a str
```

Поэтому писать `'a` вручную здесь не нужно.

---

## Правило 3

Если входных lifetime несколько, но один параметр:

```rust
&self
```

или:

```rust
&mut self
```

то lifetime `self` назначается выходным ссылкам.

Именно поэтому сигнатуры методов обычно не перегружены lifetime-аннотациями.

Язык программирования Rust(2)

---

# Почему `longest` нельзя вывести автоматически

Исходная сигнатура:

```rust
fn longest(
    x: &str,
    y: &str,
) -> &str
```

После правила №1:

```rust
fn longest<'a, 'b>(
    x: &'a str,
    y: &'b str,
) -> &str
```

Правило №2:

```text
не подходит
→ входных lifetime два
```

Правило №3:

```text
не подходит
→ это функция, а не метод
→ нет self
```

Выходной lifetime остаётся неизвестным.

Поэтому Rust требует написать связь вручную:

```rust
fn longest<'a>(
    x: &'a str,
    y: &'a str,
) -> &'a str
```

---

# Lifetimes в методах

Для структуры:

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}
```

реализация выглядит:

```rust
impl<'a> ImportantExcerpt<'a> {
    fn level(&self) -> i32 {
        3
    }
}
```

Здесь:

```text
impl<'a>
→ объявляем lifetime

ImportantExcerpt<'a>
→ применяем его к типу
```

Для самого `&self` отдельная явная аннотация часто не требуется из-за lifetime elision.

---

## Возврат ссылки из `self`

Например:

```rust
impl<'a> ImportantExcerpt<'a> {
    fn announce_and_return_part(
        &self,
        announcement: &str,
    ) -> &str {
        println!(
            "Attention please: {announcement}"
        );

        self.part
    }
}
```

Есть две входные ссылки:

```text
&self
&str
```

По первому правилу они получают разные lifetimes.

Но поскольку присутствует:

```text
&self
```

третье правило связывает lifetime возвращаемой ссылки с `self`.

Поэтому вручную прописывать возвращаемый lifetime здесь не нужно.

---

# `'static`

Особенный lifetime:

```rust
'static
```

означает, что ссылка может существовать **на протяжении всей работы программы**.

Главный пример:

```rust
let s: &'static str =
    "I have a static lifetime.";
```

Строковые литералы хранятся в бинарном файле программы и доступны на протяжении работы программы, поэтому имеют `'static` lifetime. Язык программирования Rust(2)

---

## Не лечить ошибки через `'static`

Компилятор иногда может предложить:

```rust
'static
```

при ошибке lifetime.

Но книга специально предупреждает: не следует механически заменять lifetime на `'static`.

Нужно сначала спросить:

```text
Эти данные действительно существуют
всю работу программы?
```

Если нет, проблема обычно в:

```text
dangling reference
или
неправильной связи lifetimes
```

а не в отсутствии `'static`.

То есть:

```text
compiler suggests 'static
        ↓
не значит:
"всегда добавляй 'static"
```

---

# Lifetimes + Generics + Traits

Все три механизма могут использоваться одновременно.

Пример книги:

```rust
use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(
    x: &'a str,
    y: &'a str,
    ann: T,
) -> &'a str
where
    T: Display,
{
    println!("Announcement! {ann}");

    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```

Здесь:

```text
'a
→ generic lifetime

T
→ generic type

T: Display
→ trait bound
```

Объявляются вместе:

```rust
<'a, T>
```

а ограничения поведения типа можно вынести в:

```rust
where
```

# 4. Что запомнить

Главное определение:

```text
lifetime
→ область, в которой ссылка действительна
```

Главная задача:

```text
не допустить:

reference
↓
данные уже уничтожены
```

То есть:

```text
reference lifetime
не должен превышать
lifetime данных
```

---

Синтаксис:

```rust
&i32
```

обычная ссылка.

```rust
&'a i32
```

ссылка с lifetime `'a`.

```rust
&'a mut i32
```

изменяемая ссылка с lifetime `'a`.

---

Самое важное правило:

```text
LIFETIME ANNOTATION
НЕ продлевает жизнь значения

она только описывает
отношения между ссылками
```

---

Основная функция:

```rust
fn longest<'a>(
    x: &'a str,
    y: &'a str,
) -> &'a str
```

читать так:

```text
функция принимает две ссылки,
действительные как минимум 'a,

и возвращает ссылку,
действительную как минимум 'a
```

При вызове:

```text
'a
≈ общая допустимая область
для обеих входных ссылок

практически
→ меньший lifetime
```

---

Если результат связан только с одним аргументом:

```rust
fn f<'a>(
    x: &'a str,
    y: &str,
) -> &'a str {
    x
}
```

не нужно искусственно связывать `y` с `'a`.

---

Нельзя:

```rust
fn f<'a>() -> &'a str {
    let s = String::from("hello");

    s.as_str()
}
```

Потому что:

```text
s уничтожается
при выходе из функции

↓
возвращённая ссылка стала бы dangling
```

Решение в такой ситуации:

```text
вернуть owned value
```

а не пытаться исправлять ссылку аннотацией lifetime.

---

Структура со ссылкой:

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}
```

означает:

```text
ImportantExcerpt
не может пережить данные,
на которые указывает part
```

---

Три правила elision:

```text
1. Каждая входная ссылка
   получает собственный lifetime.

2. Если входной lifetime один,
   он назначается выходным ссылкам.

3. Для метода с &self / &mut self
   lifetime self назначается
   выходным ссылкам.
```

Если после этих правил связь всё ещё неясна:

```text
Rust не угадывает

↓
нужна явная lifetime-аннотация
```

---

Особый lifetime:

```rust
'static
```

означает:

```text
ссылка может жить
всю работу программы
```

Классический пример:

```rust
let text: &'static str = "hello";
```

Но `'static` не следует использовать как универсальное исправление ошибок borrow checker.

---

Итоговая связь главы 10:

```text
GENERICS
→ какие типы можно подставлять?

TRAITS
→ какое поведение обязан иметь тип?

LIFETIMES
→ как связаны времена жизни ссылок?
```

Все три — формы описания ограничений на абстрактный код:

```text
T
→ неизвестный тип

T: Trait
→ неизвестный тип
  с известным поведением

'a
→ неизвестное конкретное время жизни
  с известным отношением к другим ссылкам
```

И самая важная мысль lifetimes:

> **Lifetime не говорит данным, сколько жить. Он сообщает компилятору, как времена жизни ссылок связаны с данными, чтобы Rust мог доказать отсутствие висячих ссылок.**

**Объём конспекта:** примерно **10–12 тыс. символов** с кодом и схемами.

**Время переноса в тетрадь:** примерно **60–75 минут**. Если сокращать, можно уменьшить количество примеров, но обязательно оставить `longest<'a>`, связь результата с меньшим lifetime, структуры со ссылками, три правила elision и смысл `'static`.
