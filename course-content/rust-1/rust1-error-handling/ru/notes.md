# Шаг 8. Ошибки

## 1. Тема

Rust разделяет ошибки на две основные категории:

```text
recoverable
→ ошибку можно обработать и продолжить работу

unrecoverable
→ продолжение работы считается неправильным
```

Для них используются разные механизмы:

```text
исправимая ошибка
→ Result<T, E>

неисправимая ошибка
→ panic!
```

В Rust нет механизма исключений в том виде, как он используется во многих других языках: ожидаемые сбои представляются обычными значениями `Result`, которые вызывающий код должен обработать. Язык программирования Rust(2)

Главная модель:

```text
операция может завершиться неудачей
            ↓
       это ожидаемо?
        ┌───┴───┐
       да      нет
       ↓        ↓
    Result    panic!
```

---

# 2. Механизм

## `panic!` — остановка программы

Явная паника:

```rust
panic!("crash and burn");
```

Паника может возникнуть и автоматически, например при выходе за границы вектора:

```rust
let v = vec![1, 2, 3];

v[99];
```

В таком случае Rust не пытается вернуть данные из памяти за пределами структуры, а прекращает выполнение.

По умолчанию при panic Rust:

```text
выводит сообщение
       ↓
раскручивает стек вызовов
       ↓
очищает данные
       ↓
завершает программу
```

Книга также описывает альтернативный режим — немедленное завершение без раскрутки стека:

```toml
[profile.release]
panic = 'abort'
```

Он уменьшает объём работы при panic и может уменьшить размер итогового бинарного файла.

---

## Backtrace

Для поиска источника паники можно использовать:

```bash
RUST_BACKTRACE=1 cargo run
```

Backtrace показывает цепочку вызовов функций, которая привела к panic.

При поиске причины книга рекомендует двигаться по трассировке до первого места, относящегося к вашему исходному коду.

Для получения информативного backtrace необходимы debug symbols; при обычных `cargo build` и `cargo run` без `--release` они включены по умолчанию.

Модель:

```text
panic
 ↓
stack backtrace
 ↓
цепочка вызовов
 ↓
первое релевантное место вашего кода
```

---

# `Result<T, E>`

Для ошибки, которую вызывающий код способен обработать, используется:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

Где:

```text
T
→ тип успешного результата

E
→ тип ошибки
```

Например:

```rust
use std::fs::File;

let result = File::open("hello.txt");
```

`File::open` может вернуть:

```text
Ok(File)
→ файл успешно открыт

Err(io::Error)
→ произошла ошибка
```

Таким образом ошибка является частью типа результата, а не скрытым побочным событием.

---

## Обработка через `match`

Полная обработка:

```rust
use std::fs::File;

let result = File::open("hello.txt");

let file = match result {
    Ok(file) => file,
    Err(error) => panic!("Problem opening the file: {error:?}"),
};
```

Механизм:

```text
Result<T, E>
     ↓
   match
 ┌────┴────┐
Ok(T)     Err(E)
 ↓          ↓
T       обработка
```

`Ok` и `Err`, как и `Result`, находятся в prelude, поэтому обычно не требуется писать:

```rust
Result::Ok(...)
Result::Err(...)
```

---

## Разные ошибки — разная обработка

Причина ошибки тоже может влиять на поведение программы.

В примере книги:

```text
File::open
    ↓
ошибка?
    ↓
файл не найден?
 ┌──────┴──────┐
да             нет
↓               ↓
создать файл   panic
```

Для `io::Error` используется:

```rust
error.kind()
```

и проверяется:

```rust
ErrorKind::NotFound
```

Упрощённо:

```rust
match File::open("hello.txt") {
    Ok(file) => file,

    Err(error) => match error.kind() {
        ErrorKind::NotFound => {
            // попытаться создать файл
        }

        _ => {
            panic!("Problem opening file");
        }
    },
}
```

Важно не само количество вложенных `match`, а принцип:

> `Err` содержит данные, позволяющие определить причину сбоя и принять соответствующее решение.

---

# `unwrap()`

Для `Result` есть сокращение:

```rust
let file = File::open("hello.txt").unwrap();
```

Поведение:

```text
Ok(value)
→ вернуть value

Err(error)
→ panic!
```

То есть концептуально:

```rust
result.unwrap()
```

примерно заменяет простейший:

```rust
match result {
    Ok(value) => value,
    Err(error) => panic!(...),
}
```

`unwrap` не является полноценной обработкой ошибки: при `Err` программа просто паникует.

---

# `expect()`

Похож на `unwrap`, но позволяет указать собственное сообщение:

```rust
let file = File::open("hello.txt")
    .expect("hello.txt should be included in this project");
```

Поведение:

```text
Ok(value)
→ value

Err(error)
→ panic + наше сообщение
```

Книга предпочитает `expect` перед `unwrap`, когда паника действительно допустима, потому что сообщение объясняет **почему операция предполагалась успешной**.

```text
unwrap
→ "здесь ожидаю успех"

expect("причина")
→ "ожидаю успех вот по этой причине"
```

---

# `unwrap_or_else`

В главе также показывается метод:

```rust
result.unwrap_or_else(...)
```

Его идея:

```text
Ok(value)
→ вернуть value

Err(error)
→ выполнить переданный код обработки
```

Он позволяет заменить некоторые вложенные `match` более коротким кодом.

Подробно замыкания, которые используются с этим методом, книга разбирает позже, поэтому здесь достаточно помнить сам принцип.

---

# Проброс ошибки

Функция не обязана сама решать, что делать с ошибкой.

Она может вернуть её вызывающему коду:

```rust
fn read_username_from_file()
    -> Result<String, std::io::Error>
{
    ...
}
```

При успехе:

```text
Ok(String)
```

при ошибке:

```text
Err(io::Error)
```

Например вручную:

```rust
let file = match File::open("hello.txt") {
    Ok(file) => file,
    Err(e) => return Err(e),
};
```

Здесь функция говорит:

```text
"Я не решаю, что делать с этой ошибкой.
Передаю решение вызывающему коду."
```

Это называется **распространением / пробросом ошибки**.

---

# Оператор `?`

Такой код:

```rust
let file = match File::open("hello.txt") {
    Ok(file) => file,
    Err(e) => return Err(e),
};
```

в типичном случае можно заменить:

```rust
let file = File::open("hello.txt")?;
```

Механизм `?` для `Result`:

```text
Result
   ↓
   ?
 ┌─┴──────────────┐
Ok(value)        Err(error)
   ↓                 ↓
получить value    досрочно вернуть Err
   ↓
продолжить функцию
```

То есть:

```rust
operation()?
```

означает примерно:

```text
если Ok
→ распаковать значение

если Err
→ return Err(...)
```

Эта схема настолько распространена, что Rust предоставляет для неё отдельный оператор. Язык программирования Rust(2)

---

## `?` и преобразование ошибок

Есть отличие от ручного:

```rust
return Err(e);
```

При использовании `?` ошибка может быть преобразована в тип ошибки, который возвращает текущая функция.

Для этого используется механизм `From`.

Упрощённо:

```text
ошибка операции
      ↓
      ?
      ↓
From::from(...)
      ↓
тип ошибки текущей функции
```

Это позволяет функции иметь один итоговый тип ошибки, даже если внутри выполняются операции, способные возвращать разные совместимые типы ошибок.

Подробности `From` и traits будут позже.

---

## Несколько `?`

Пример из книги:

```rust
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file()
    -> Result<String, io::Error>
{
    let mut username = String::new();

    File::open("hello.txt")?
        .read_to_string(&mut username)?;

    Ok(username)
}
```

Логика:

```text
открыть файл
   ↓ Err → вернуть ошибку
   ↓ Ok
читать файл
   ↓ Err → вернуть ошибку
   ↓ Ok
Ok(username)
```

То есть `?` хорошо подходит для цепочки операций, где любая может завершиться ошибкой, а решение должен принимать вызывающий код.

---

## Не писать вручную то, что уже есть в библиотеке

Для распространённой задачи чтения файла книга показывает ещё более короткий вариант:

```rust
use std::fs;
use std::io;

fn read_username_from_file()
    -> Result<String, io::Error>
{
    fs::read_to_string("hello.txt")
}
```

Это важный общий принцип главы: если стандартная библиотека уже предоставляет операцию с подходящим `Result`, нет необходимости вручную воспроизводить её внутренние шаги.

---

# Где работает `?`

`?` нельзя поставить в произвольной функции.

Например:

```rust
fn main() {
    let file = File::open("hello.txt")?;
}
```

не компилируется, потому что обычный `main` здесь возвращает:

```rust
()
```

а `?` должен иметь возможность выполнить ранний возврат совместимой ошибки.

Книга указывает, что `?` используется в функциях, возвращающих совместимые типы, в частности:

```text
Result
Option
```

---

# `?` с `Option<T>`

Для:

```rust
Option<T>
```

оператор работает аналогично.

```text
Some(value)?
→ получить value
→ продолжить

None?
→ досрочно вернуть None
```

Пример из книги:

```rust
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}
```

Если:

```rust
text.lines().next()
```

возвращает `None`, вся функция сразу возвращает `None`.

Если возвращается:

```rust
Some(line)
```

`?` извлекает `line`, и выполнение продолжается.

Важно:

```text
Result + ?
→ обычно функция возвращает Result

Option + ?
→ обычно функция возвращает Option
```

`?` не преобразует автоматически `Result` в `Option` и наоборот; книга упоминает для явного преобразования методы вроде `ok` и `ok_or`.

---

# `main` тоже может вернуть `Result`

Можно написать:

```rust
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let file = File::open("hello.txt")?;

    Ok(())
}
```

В этой главе `Box<dyn Error>` предлагается пока понимать как:

```text
"любой вид ошибки"
```

Сам механизм trait objects разбирается позже.

Если `main` возвращает:

```rust
Ok(())
```

программа завершается с успешным кодом.

Если:

```rust
Err(...)
```

— с ненулевым кодом завершения. Язык программирования Rust(2)

---

# 3. Важные детали

## `panic!` или `Result`?

Это ключевой архитектурный выбор.

При:

```rust
panic!()
```

функция сама решает:

```text
"восстановление невозможно"
```

Вызывающий код уже не получает возможности решить, что делать.

При:

```rust
Result<T, E>
```

решение передаётся выше:

```text
функция обнаружила ошибку
        ↓
вернула Err
        ↓
вызывающий код решает:
повторить?
использовать другое значение?
показать сообщение?
panic?
```

Поэтому книга называет `Result` хорошим выбором по умолчанию для функции, которая может завершиться неудачей. Язык программирования Rust(2)

---

## Когда `unwrap` / `expect` допустимы

Книга отдельно выделяет случаи, где паника удобна:

```text
примеры
прототипы
тесты
```

В прототипе это позволяет сначала написать основную логику, оставив `unwrap` или `expect` как место, которое позже можно заменить нормальной обработкой ошибок.

В тесте panic означает провал теста, поэтому `unwrap` и `expect` естественно подходят.

---

## Когда программист знает больше компилятора

Иногда тип возвращается как `Result`, хотя из логики конкретной программы известно, что операция должна быть успешной.

Пример книги:

```rust
use std::net::IpAddr;

let home: IpAddr = "127.0.0.1"
    .parse()
    .expect("Hardcoded IP address should be valid");
```

`parse` в общем случае может завершиться ошибкой.

Но здесь строка жёстко задана и заведомо соответствует ожидаемой форме.

Поэтому `expect` одновременно:

```text
распаковывает Result
+
документирует предположение программы
```

Если же строка пришла от пользователя, такое предположение уже не действует и ошибку следует обрабатывать.

---

## Ошибка пользователя ≠ ошибка программы

Если сбой ожидаем:

```text
неправильный пользовательский ввод
неверные входные данные
операция может нормально не выполниться
```

обычно это кандидат на:

```rust
Result
```

Если нарушен контракт или инвариант программы:

```text
"это состояние вообще не должно существовать"
```

может быть оправдан:

```rust
panic!
```

Книга приводит выход за границы массива как пример, где продолжение с некорректным доступом к памяти недопустимо.

Если библиотека паникует при нарушении контракта функции, такое условие следует описать в документации API.

---

# Типы как способ уменьшить количество ошибок

Rust позволяет часть проверок перенести из runtime в систему типов.

Например:

```rust
fn f(value: u32)
```

уже гарантирует, что `value` не отрицателен.

А если функция принимает обычный тип вместо:

```rust
Option<T>
```

она может рассчитывать, что значение присутствует.

То есть вместо:

```text
постоянно проверять невозможные состояния
```

можно по возможности сделать эти состояния непредставимыми соответствующим типом.

---

## Пользовательский тип с проверкой инварианта

Книга показывает идею на числе от `1` до `100`.

Вместо передачи повсюду:

```rust
i32
```

и постоянной проверки:

```rust
if value < 1 || value > 100
```

можно создать:

```rust
struct Guess {
    value: i32,
}
```

а создание контролировать через:

```rust
impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            panic!("...");
        }

        Guess { value }
    }

    pub fn value(&self) -> i32 {
        self.value
    }
}
```

Поле:

```rust
value
```

остаётся приватным.

Значит внешний код не может создать произвольное некорректное состояние, обходя проверку.

После успешного создания:

```text
Guess
→ значение уже проверено
→ остальной код может полагаться на инвариант
```

Так система типов помогает сосредоточить проверку в одном месте вместо её повторения во множестве функций.

# 4. Что запомнить

Главная карта ошибок Rust:

```text
ERROR
 │
 ├── ожидаемая / исправимая
 │       ↓
 │   Result<T, E>
 │
 └── нарушение инварианта /
     продолжение невозможно
         ↓
       panic!
```

`Result`:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

Запомнить:

```text
Ok(T)
→ успешное значение

Err(E)
→ описание ошибки
```

Обработка:

```rust
match result {
    Ok(value) => ...,
    Err(error) => ...,
}
```

---

Сокращения:

```text
unwrap()
→ Ok: вернуть value
→ Err: panic

expect("reason")
→ то же,
  но со своим объяснением паники
```

Для кода, где ошибка должна быть обработана вызывающей стороной:

```rust
operation()?
```

читать так:

```text
Ok(value)
→ value

Err(error)
→ return Err(error)
```

---

Главная сигнатура функции, которая может завершиться ошибкой:

```rust
fn operation() -> Result<T, E>
```

Например:

```rust
fn read() -> Result<String, io::Error>
```

Она сразу сообщает пользователю функции:

```text
"успех не гарантирован"
```

---

Оператор `?`:

```text
Result + ?
→ проброс Err

Option + ?
→ проброс None
```

Но:

```text
Result ↔ Option
```

автоматически не смешиваются.

---

Выбор:

```text
Ошибка ожидаема?
→ Result

Вызывающий код способен принять решение?
→ Result

Нарушен контракт или инвариант?
→ panic! может быть уместен

Пример / прототип / тест?
→ unwrap / expect могут быть удобны
```

И самое важное архитектурное различие:

```text
panic!
→ текущий код принимает решение
  прекратить выполнение

Result
→ текущий код сообщает о проблеме,
  а решение принимает вызывающий код
```

Это одна из основных идей обработки ошибок в Rust.

**Объём конспекта:** примерно **9–11 тыс. символов** с кодом.

**Время переноса в тетрадь:** примерно **50–65 минут**. При сокращении в первую очередь можно убрать подробности backtrace и `panic = 'abort'`, но обязательно оставить модель `panic! / Result`, `Ok/Err`, `unwrap/expect`, проброс через `?` и правило выбора между паникой и возвращением ошибки.
