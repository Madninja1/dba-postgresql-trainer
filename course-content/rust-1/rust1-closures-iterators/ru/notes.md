# Шаг 12. Замыкания и итераторы

## 1. Тема

Глава объединяет две возможности Rust, связанные с функциональным стилем:

```text
closures
→ анонимные функции,
  которые могут захватывать окружение

iterators
→ последовательная обработка элементов
  без ручного управления перебором
```

Замыкания можно сохранять в переменные и передавать другим функциям. Главное отличие от обычной `fn`: замыкание может использовать значения из области, где оно было создано. Итераторы, в свою очередь, предоставляют общий способ последовательной обработки элементов. Язык программирования Rust(2)

Основная связь:

```text
iterator
   ↓
выдаёт элементы
   ↓
closure
   ↓
задаёт, что делать с каждым элементом
```

Например:

```rust
values
    .iter()
    .map(|x| x + 1)
    .collect()
```

Здесь итератор отвечает за перебор, а замыкание:

```rust
|x| x + 1
```

— за конкретную операцию.

---

# 2. Механизм

## Замыкание

Простейшее замыкание:

```rust
let add_one = |x| x + 1;
```

Вызов:

```rust
let result = add_one(5);
```

Параметры записываются между:

```text
| |
```

Например:

```rust
|x| x + 1
```

Несколько параметров:

```rust
|x, y| x + y
```

Без параметров:

```rust
|| something()
```

---

## Замыкание и обычная функция

Одинаковое поведение можно записать так:

```rust
fn add_one(x: u32) -> u32 {
    x + 1
}
```

или:

```rust
let add_one = |x: u32| -> u32 {
    x + 1
};
```

Но для замыканий типы обычно выводятся:

```rust
let add_one = |x| x + 1;
```

Если тело состоит из одного выражения, фигурные скобки тоже можно убрать. Язык программирования Rust(2)

---

## Тип замыкания фиксируется

Отсутствие явной аннотации не означает, что одно замыкание становится generic.

Например:

```rust
let identity = |x| x;

let s = identity(String::from("hello"));
let n = identity(5);
```

не скомпилируется.

После первого вызова:

```text
identity(String)
        ↓
параметр = String
return   = String
```

эти конкретные типы фиксируются для данного замыкания.

```text
closure без аннотаций
≠ generic function
```

Язык программирования Rust(2)

---

# Захват окружения

Главное отличие замыкания от обычной функции:

```rust
let x = 10;

let f = || println!("{x}");
```

`x` не является параметром `f`, но замыкание может его использовать.

Замыкание автоматически выбирает минимально необходимый способ захвата окружающего значения:

```text
&T
→ неизменяемое заимствование

&mut T
→ изменяемое заимствование

T
→ получение владения
```

Эти способы соответствуют уже изученным правилам ownership и borrowing. Язык программирования Rust(2)

---

## Неизменяемый захват

```rust
let list = vec![1, 2, 3];

let only_borrows =
    || println!("{list:?}");

only_borrows();
```

Замыканию достаточно прочитать `list`, поэтому оно захватывает неизменяемую ссылку.

Концептуально:

```text
closure
   │
   └── &list
```

Сам `list` остаётся доступен в местах, где правила обычного неизменяемого borrowing это позволяют.

---

## Изменяемый захват

```rust
let mut list = vec![1, 2, 3];

let mut add =
    || list.push(7);

add();
```

Теперь замыкание изменяет `list`, поэтому захватывает:

```text
&mut list
```

Пока такое изменяемое заимствование активно, действуют обычные правила `&mut`: нельзя одновременно пользоваться конфликтующей ссылкой на `list`. Язык программирования Rust(2)

---

# `move`

Можно принудительно передать захваченные значения замыканию во владение:

```rust
move || {
    ...
}
```

Например:

```rust
let list = vec![1, 2, 3];

let closure =
    move || println!("{list:?}");
```

Смысл:

```text
до:

scope owns list


move closure
     ↓


closure owns list
```

Книга особенно связывает это с передачей замыкания в другой поток:

```rust
thread::spawn(
    move || println!("{list:?}")
);
```

Так данные принадлежат самому замыканию и не зависят от того, закончилась ли область видимости, где оно было создано. Язык программирования Rust(2)

Важно:

```text
move
→ определяет, как значение попадает в closure
```

А то, какой `Fn`-trait реализует замыкание, зависит ещё и от того, **что тело затем делает с захваченным значением**.

---

# `Fn`, `FnMut`, `FnOnce`

Rust автоматически определяет для замыкания один или несколько специальных traits.

## `FnOnce`

Все замыкания реализуют как минимум:

```rust
FnOnce
```

Если тело перемещает захваченное значение **из самого замыкания**, его можно вызвать только один раз.

```text
closure owns value
      ↓
call
      ↓
value moved out
      ↓
второй call невозможен
```

Такое замыкание может реализовывать только `FnOnce`.

---

## `FnMut`

```rust
FnMut
```

подходит замыканиям, которые:

```text
не перемещают захваченные данные наружу
+
могут изменять окружение
```

Например:

```rust
let mut count = 0;

let mut f = || {
    count += 1;
};
```

Замыкание можно вызывать несколько раз, но оно изменяет захваченное состояние.

---

## `Fn`

```rust
Fn
```

подходит замыканиям, которые:

```text
не перемещают захваченные значения
не изменяют их
```

или вообще ничего не захватывают.

Например:

```rust
|x| x + 1
```

Такое замыкание может вызываться многократно без изменения своего окружения. Язык программирования Rust(2)

Главная модель:

```text
FnOnce
→ можно вызвать хотя бы один раз

FnMut
→ можно вызывать много раз
→ можно менять окружение

Fn
→ можно вызывать много раз
→ окружение не изменяется
```

При этом реализация аддитивна:

```text
Fn
→ также подходит как FnMut
→ также подходит как FnOnce
```

---

## Traits замыканий как bounds

Функция может принимать замыкание через generic + trait bound.

Упрощённый пример из `Option::unwrap_or_else`:

```rust
F: FnOnce() -> T
```

Это означает:

```text
F
→ замыкание

()
→ без аргументов

-> T
→ возвращает T

FnOnce
→ будет вызвано не более одного раза
```

`unwrap_or_else` вызывает замыкание только если `Option` содержит `None`, поэтому требования `FnOnce` достаточно. Язык программирования Rust(2)

Другой пример:

```text
sort_by_key
→ вызывает замыкание много раз
→ требуется FnMut
```

Отсюда важный принцип:

> `Fn` / `FnMut` / `FnOnce` в сигнатуре описывают, как вызывающий код собирается использовать переданное замыкание.

# Итераторы

Итератор позволяет последовательно получать элементы, не реализуя вручную:

```text
индекс
проверку конца
увеличение счётчика
доступ к следующему элементу
```

Простейший пример:

```rust
let v = vec![1, 2, 3];

let iter = v.iter();
```

Само создание:

```rust
v.iter()
```

ещё не выполняет обработку элементов.

Rust-итераторы **ленивые**. Язык программирования Rust(2)

---

# Trait `Iterator`

Упрощённое определение:

```rust
pub trait Iterator {
    type Item;

    fn next(
        &mut self
    ) -> Option<Self::Item>;
}
```

Главное, что нужно реализовать для собственного итератора:

```rust
next()
```

Каждый вызов:

```text
ещё есть элемент
→ Some(item)

элементы закончились
→ None
```

Язык программирования Rust(2)

---

## `next()`

```rust
let v = vec![1, 2, 3];

let mut iter = v.iter();

assert_eq!(
    iter.next(),
    Some(&1)
);

assert_eq!(
    iter.next(),
    Some(&2)
);

assert_eq!(
    iter.next(),
    Some(&3)
);

assert_eq!(
    iter.next(),
    None
);
```

Итератор должен быть `mut`, потому что каждый `next()` изменяет его внутреннее состояние:

```text
position 0
   ↓ next
position 1
   ↓ next
position 2
...
```

Язык программирования Rust(2)

---

# `iter`, `iter_mut`, `into_iter`

Способ создания итератора определяет отношение к исходным значениям.

```rust
collection.iter()
```

возвращает итерацию по:

```text
&T
```

То есть значения только заимствуются.

---

```rust
collection.iter_mut()
```

даёт:

```text
&mut T
```

и позволяет изменять элементы.

---

```rust
collection.into_iter()
```

создаёт итератор, который принимает коллекцию во владение и выдаёт принадлежащие ему значения.

Модель:

```text
iter()
→ &T
→ читать

iter_mut()
→ &mut T
→ изменять

into_iter()
→ T
→ забрать ownership элементов
```

Язык программирования Rust(2)

Это одно из самых важных различий при практической работе с итераторами.

---

# Потребляющие методы

Некоторые методы проходят итератор до конца и **потребляют его**.

Пример:

```rust
let v = vec![1, 2, 3];

let total: i32 =
    v.iter().sum();
```

Результат:

```text
6
```

`sum` многократно вызывает `next`, пока последовательность не закончится.

После потребления соответствующий итератор использовать снова нельзя, потому что `sum` получает его во владение. Язык программирования Rust(2)

Главная модель:

```text
iterator
   ↓
consumer
   ↓
готовый результат
```

Примеры из главы:

```text
sum()
collect()
```

---

# Адаптеры итераторов

Другие методы не вычисляют окончательный результат, а создают **новый итератор**.

Например:

```rust
map
filter
```

Их называют iterator adapters.

```text
iterator
    ↓
adapter
    ↓
новый iterator
```

---

## `map`

`map` преобразует каждый элемент:

```rust
let v = vec![1, 2, 3];

let result: Vec<_> =
    v.iter()
        .map(|x| x + 1)
        .collect();
```

Получаем:

```text
[2, 3, 4]
```

Логика:

```text
1 → closure → 2
2 → closure → 3
3 → closure → 4
```

Но:

```rust
v.iter().map(|x| x + 1);
```

сам по себе практически ничего не делает.

Почему?

```text
map
→ создаёт новый iterator

iterator
→ lazy
```

Для реального вычисления его нужно потребить, например через `collect`. Язык программирования Rust(2)

---

## `filter`

`filter` оставляет только элементы, для которых замыкание возвращает:

```text
true
```

Например:

```rust
shoes
    .into_iter()
    .filter(|s| {
        s.size == shoe_size
    })
    .collect()
```

Логика:

```text
element
   ↓
closure
   ↓
 bool
 ┌─┴────┐
true   false
 ↓       ↓
keep    skip
```

Замыкание здесь может использовать `shoe_size`, который находится в окружении — это как раз связь итераторов с closures. Язык программирования Rust(2)

---

# `collect`

`collect()` потребляет итератор и собирает его элементы в коллекцию.

Например:

```rust
let result: Vec<_> =
    v.iter()
        .map(|x| x + 1)
        .collect();
```

Почему часто требуется указать тип?

Потому что `collect` способен собирать данные в разные виды коллекций, и Rust должен понимать, какой именно результат требуется.

В примере:

```rust
Vec<_>
```

сообщает:

```text
собрать в Vec
```

---

# Цепочки итераторов

Сила итераторов проявляется при композиции:

```rust
collection
    .into_iter()
    .filter(|x| ...)
    .map(|x| ...)
    .collect()
```

Можно читать сверху вниз:

```text
получить элементы
       ↓
отфильтровать
       ↓
преобразовать
       ↓
собрать результат
```

Промежуточные адаптеры:

```text
filter
map
...
```

ленивы.

Выполнение начинается, когда появляется потребляющая операция:

```text
collect
sum
for
...
```

# 3. Важные детали

## Iterator laziness

Это центральное свойство.

```rust
let iter =
    v.iter()
        .map(|x| x + 1);
```

не означает:

```text
"сейчас пройти весь v
и создать все результаты"
```

Пока итератор не потреблён, работа не выполняется.

```text
создание pipeline
→ описание вычисления

consuming operation
→ запуск вычисления
```

Поэтому Rust даже предупреждает, если создать `map(...)` и больше его никак не использовать. Язык программирования Rust(2)

---

## Замыкания подчиняются ownership

Closure не является обходным путём вокруг borrow checker.

Если оно захватило:

```text
&T
```

действуют правила неизменяемого borrowing.

Если:

```text
&mut T
```

действуют правила изменяемого borrowing.

Если:

```text
T
```

действуют правила move.

Поэтому ошибки вокруг closures часто являются уже знакомыми ошибками ownership, только значение находится внутри замыкания.

---

## `move` и `FnOnce` — не одно и то же

Не путать:

```text
move
→ заставляет closure получить ownership
  захватываемых значений
```

и:

```text
FnOnce
→ описывает,
  перемещает ли тело значение
  ИЗ closure при вызове
```

Само наличие `move` не означает автоматически, что замыкание можно вызвать только один раз. Классификация зависит от того, что тело делает с захваченными значениями. Это следует из разделения в книге между способом захвата и последующим поведением тела замыкания. Язык программирования Rust(2)

---

## Итераторы и ownership

Очень полезно смотреть на начало pipeline:

```rust
v.iter()
```

→ элементы заимствуются.

```rust
v.iter_mut()
```

→ элементы изменяемо заимствуются.

```rust
v.into_iter()
```

→ ownership передаётся итератору.

Поэтому ещё до чтения `map/filter` можно понять, что произойдёт с исходной коллекцией.

---

## Итераторы вместо ручного временного состояния

Старая реализация поиска:

```rust
let mut results = Vec::new();

for line in contents.lines() {
    if line.contains(query) {
        results.push(line);
    }
}

results
```

после перехода к итераторам:

```rust
contents
    .lines()
    .filter(|line| {
        line.contains(query)
    })
    .collect()
```

Смысл тот же:

```text
строки
→ оставить совпадающие
→ собрать
```

но исчезает:

```text
mutable results
ручной push
явное управление циклом
```

Книга отмечает, что Rust-разработчики обычно предпочитают iterator-style после освоения его адаптеров, поскольку он фокусируется на цели преобразования, а не на механике перебора. Язык программирования Rust(2)

---

## Практическое улучшение `Config::build`

Раньше аргументы командной строки сначала собирались:

```rust
let args: Vec<String> =
    env::args().collect();
```

а затем из них клонировались значения в `Config`.

После освоения итераторов книга передаёт `env::args()` непосредственно:

```rust
Config::build(env::args())
```

а `build` принимает:

```rust
impl Iterator<Item = String>
```

Это позволяет получать аргументы через `next()` и **перемещать `String` непосредственно в `Config`**, вместо заимствования элементов среза и последующего `clone`. Язык программирования Rust(2)

Это хороший пример того, что iterator — не только красивый синтаксис:

```text
ownership iterator
→ может убрать ненужное clone
```

---

## Производительность

Книга сравнивает реализацию поиска через обычный цикл и через iterator pipeline и показывает близкую производительность. Итераторы описываются как одна из **zero-cost abstractions** Rust: высокоуровневый код компилируется примерно в такой же эффективный низкоуровневый код, который можно было бы написать вручную. Язык программирования Rust(2)

Главная мысль:

```text
iterator abstraction
≠ обязательная runtime-плата
```

Компилятор может оптимизировать цепочки итераторов, включая устранение части служебной логики циклов. Язык программирования Rust(2)

# 4. Что запомнить

Минимум по closures:

```rust
let f = |x| x + 1;
```

```text
|x|
→ параметры

x + 1
→ тело
```

Замыкание:

```text
→ можно сохранить в переменной
→ можно передать функции
→ может захватывать окружение
```

---

Три способа захвата:

```text
&T
→ read

&mut T
→ modify

T
→ ownership
```

Принудительное владение:

```rust
move || ...
```

---

Три `Fn` traits:

```text
FnOnce
→ может потребить захваченное значение
→ гарантирован максимум одного подходящего вызова

FnMut
→ не потребляет захваченное значение
→ может менять окружение
→ многократные вызовы

Fn
→ не потребляет
→ не изменяет окружение
→ многократные вызовы
```

Практически:

```text
Fn
⊂ FnMut
⊂ FnOnce
```

в смысле того, что более ограниченное по поведению замыкание удовлетворяет и более общим требованиям вызова.

---

Минимум по iterator:

```rust
let iter = v.iter();
```

Главный trait:

```rust
trait Iterator {
    type Item;

    fn next(
        &mut self
    ) -> Option<Self::Item>;
}
```

`next`:

```text
Some(item)
Some(item)
...
None
```

---

Выбор ownership:

```text
iter()
→ &T

iter_mut()
→ &mut T

into_iter()
→ T
```

---

Главные методы:

```text
map
→ преобразовать каждый элемент
→ возвращает iterator

filter
→ оставить подходящие элементы
→ возвращает iterator

collect
→ собрать iterator в коллекцию
→ потребляет iterator

sum
→ получить сумму
→ потребляет iterator
```

---

Типичный pipeline:

```rust
items
    .into_iter()
    .filter(|x| condition(x))
    .map(|x| transform(x))
    .collect()
```

Читать:

```text
получить элементы
→ отфильтровать
→ преобразовать
→ собрать
```

---

Самое важное свойство:

```text
iterator adapters
→ lazy
```

Поэтому:

```rust
v.iter().map(|x| x + 1);
```

само по себе не выполняет всю работу.

Нужен consumer:

```rust
.collect()
```

или другой способ потребить итератор.

---

Итоговая модель темы:

```text
CLOSURE
→ описывает действие

ITERATOR
→ предоставляет последовательность

ADAPTER
→ преобразует последовательность

CONSUMER
→ запускает обработку
  и получает результат
```

Связь с предыдущими главами:

```text
closures
→ ownership + borrowing + traits

iterators
→ traits + Option + closures

iterator pipelines
→ компактное описание обработки
  без ручного mutable-state
```

Главное практическое правило при чтении iterator-кода:

```text
1. Откуда элементы?
   iter / iter_mut / into_iter

2. Что делают адаптеры?
   map / filter / ...

3. Где iterator потребляется?
   collect / sum / for / ...
```

Если ответить на эти три вопроса, большинство цепочек итераторов становится существенно проще читать.

**Объём конспекта:** примерно **10–12 тыс. символов** с кодом и схемами.

**Время переноса в тетрадь:** примерно **55–70 минут**. При сокращении можно убрать примеры `sort_by_key` и `Config::build`, но обязательно оставить захват окружения, `move`, `Fn/FnMut/FnOnce`, `Iterator::next`, `iter/iter_mut/into_iter`, ленивость и связку `map/filter/collect`.
