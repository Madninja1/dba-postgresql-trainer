# Шаг 3. Владение и память

## 1. Тема

**Владение (ownership)** — система правил, по которой Rust управляет памятью.

В языках со сборщиком мусора неиспользуемая память отслеживается во время работы программы. В других языках программист может освобождать её вручную. Rust использует другой подход: **правила владения проверяются компилятором**, а память освобождается автоматически, когда владелец данных больше не существует.

Система владения не требует сборщика мусора и сама по себе не добавляет проверок владения во время выполнения.

Три главных правила:

```text
1. У каждого значения есть владелец.

2. В каждый момент времени у значения
   может быть только один владелец.

3. Когда владелец выходит из области видимости,
   значение удаляется.
```

Это основа, из которой далее вытекают `move`, borrowing, ссылки, lifetimes и часть правил многопоточности.

---

# 2. Механизм

## Стек и куча

Для понимания ownership книга сначала разделяет память на **stack** и **heap**.

### Stack

Стек работает по принципу:

```text
последним вошёл → первым вышел
LIFO
```

Данные добавляются на вершину стека и оттуда же удаляются.

Для хранения в стеке размер данных должен быть известен во время компиляции.

Условно:

```text
Stack

┌─────────┐
│ value C │ ← вершина
├─────────┤
│ value B │
├─────────┤
│ value A │
└─────────┘
```

Добавление и удаление из стека происходит быстро, потому что место искать не требуется.

Когда вызывается функция, её параметры и локальные переменные помещаются в стек. После завершения функции они извлекаются.

---

### Heap

Если размер данных заранее неизвестен или может изменяться, данные могут размещаться в куче.

При размещении:

```text
запрос памяти
    ↓
поиск свободного участка
    ↓
выделение участка
    ↓
возврат указателя на него
```

Сам указатель имеет фиксированный размер и может находиться в стеке.

Получается модель:

```text
STACK                         HEAP

┌───────────────┐             ┌───────────────┐
│ ptr ──────────┼────────────→│ данные         │
│ length        │             │ ...           │
│ capacity      │             │ ...           │
└───────────────┘             └───────────────┘
```

Выделение памяти в куче дороже помещения значения в стек: сначала нужно найти подходящий участок.

Доступ к данным кучи также требует перехода по указателю.

Главное для этой главы:

> ownership в первую очередь решает вопрос: **кто отвечает за данные и кто должен освободить память, когда она больше не нужна**.

---

## Область видимости и владелец

Переменная действительна после объявления и до конца своей области видимости:

```rust
{
    let s = "hello";

    // s доступна здесь
}

// s больше не доступна
```

Для простых значений это выглядит привычно.

Но с данными в куче окончание области видимости имеет дополнительное значение: Rust должен освободить выделенную память.

---

## `String` как пример владения

Книга использует `String`, потому что его содержимое находится в куче.

Строковый литерал:

```rust
let s = "hello";
```

известен уже во время компиляции.

А `String` может содержать данные, размер которых во время компиляции неизвестен:

```rust
let mut s = String::from("hello");

s.push_str(", world!");
```

Чтобы такой текст мог увеличиваться, `String` использует память в куче.

При:

```rust
String::from("hello")
```

во время выполнения выделяется необходимая память.

Здесь возникает важная проблема управления памятью:

```text
кто выделил память?
когда она больше не нужна?
кто должен её освободить?
```

Rust связывает эту обязанность с владельцем.

---

## Автоматическое освобождение: `drop`

Когда владелец выходит из области видимости, Rust автоматически вызывает специальную функцию:

```text
drop
```

Упрощённо:

```rust
{
    let s = String::from("hello");

    // s владеет String
}

// конец scope
// автоматически освобождается память String
```

Модель:

```text
String::from(...)
      ↓
выделение памяти
      ↓
переменная становится владельцем
      ↓
...
      ↓
владелец покидает scope
      ↓
drop
      ↓
память возвращается
```

Таким образом Rust стремится обеспечить соответствие:

```text
одно выделение памяти
        ↕
одно освобождение
```

Не нужно вручную решать, где вызывать `free`, и не нужен сборщик мусора, который позднее ищет неиспользуемые объекты.

# 3. Важные детали

## Как устроен `String`

У `String` есть три части:

```text
ptr       → указатель на данные
len       → текущая длина
capacity  → выделенная ёмкость
```

Эта информация хранится в стеке.

Сами символы находятся в куче.

Условно:

```text
s
STACK                    HEAP

ptr ───────────────────→ h e l l o
len      5
capacity 5
```

`len` — сколько байтов содержимое сейчас использует.

`capacity` — сколько байтов памяти было выделено для `String`.

Для понимания ownership сейчас достаточно знать, что `String` содержит данные стека, которые указывают на данные в куче.

---

## Move — перемещение владения

Рассмотрим:

```rust
let s1 = String::from("hello");
let s2 = s1;
```

Rust **не создаёт автоматически полную независимую копию данных `hello`**.

Копируются стековые части `String`:

```text
ptr
len
capacity
```

Но данные кучи остаются одни.

После операции могло бы получиться:

```text
s1 ─┐
    ├────→ "hello"
s2 ─┘
```

Если обе переменные считались бы владельцами, при завершении области видимости обе попытались бы освободить одну память.

Это привело бы к:

```text
double free
```

— повторному освобождению одного участка памяти.

Rust предотвращает это иначе:

```rust
let s2 = s1;
```

после этой операции:

```text
s1 → больше нельзя использовать
s2 → новый владелец
```

То есть произошло **перемещение (move)**:

```text
до:

s1 ─────→ heap data


let s2 = s1;


после:

s1   недействителен

s2 ─────→ heap data
```

Попытка:

```rust
let s1 = String::from("hello");
let s2 = s1;

println!("{s1}");
```

не компилируется.

Причина не в том, что данные исчезли. Данные теперь принадлежат `s2`.

---

## Почему Rust не делает глубокую копию автоматически

Rust мог бы при:

```rust
let s2 = s1;
```

создать вторую копию данных в куче.

Но тогда простое присваивание потенциально могло бы выполнять дорогую операцию:

```text
огромные данные
      ↓
полное копирование всей памяти
```

Вместо этого Rust использует `move`.

Из этого получается важное свойство:

> Rust не выполняет автоматически дорогие глубокие копии данных.

Если в коде явно не видно копирования сложных данных, такое дорогое копирование не должно неожиданно происходить из-за обычного присваивания.

---

## `clone()` — явная глубокая копия

Если действительно нужны две независимые копии:

```rust
let s1 = String::from("hello");
let s2 = s1.clone();
```

Теперь:

```text
s1 ─────→ "hello"

s2 ─────→ "hello"
```

В куче находятся независимые данные.

Обе переменные остаются действительными:

```rust
println!("{s1}");
println!("{s2}");
```

`clone()` важен ещё и как визуальный сигнал:

```text
clone()
   ↓
здесь действительно копируются данные
   ↓
операция потенциально может быть дорогой
```

Поэтому:

```rust
let s2 = s1;
```

и:

```rust
let s2 = s1.clone();
```

имеют принципиально разный смысл.

---

## `Copy` — дешёвое копирование

Теперь:

```rust
let x = 5;
let y = x;

println!("{x}");
println!("{y}");
```

работает.

Почему `x` не стал недействительным?

Потому что такие простые типы реализуют специальный trait:

```text
Copy
```

Для `Copy`-типов присваивание означает обычное дешёвое копирование значения.

```text
let y = x;

Copy type:
x → 5
y → 5
```

А не:

```text
x → invalid
y → 5
```

Примеры типов, реализующих `Copy`:

```text
целые числа: i32, u32, ...
bool
f32, f64
char
```

Кортеж тоже является `Copy`, только если **все его элементы** являются `Copy`.

Например:

```text
(i32, i32)    → Copy

(i32, String) → не Copy
```

---

## `Copy` и `Drop`

Если тип требует специальной логики при уничтожении через `Drop`, Rust не позволяет одновременно сделать его `Copy`.

Идея проста:

```text
Copy
→ значение можно просто дублировать

Drop
→ уничтожение значения требует специального действия
```

Эти две модели конфликтовали бы друг с другом.

---

## Move и Copy — главное различие

Полезно мыслить так:

```text
Присваивание:

let b = a;

        │
        ▼
Тип реализует Copy?
        │
   ┌────┴─────┐
   │          │
  да         нет
   │          │
   ▼          ▼
COPY         MOVE

a valid      a invalid
b valid      b owner
```

Для `String`:

```rust
let s2 = s1;
```

→ `move`.

Для `i32`:

```rust
let y = x;
```

→ `copy`.

---

## Владение при передаче в функцию

Передача значения функции работает по тем же правилам, что и присваивание.

### Тип без `Copy`

```rust
fn takes_ownership(s: String) {
    println!("{s}");
}

let s = String::from("hello");

takes_ownership(s);
```

Происходит:

```text
main владеет s
     ↓
вызов функции
     ↓
ownership перемещается параметру функции
     ↓
s в main больше использовать нельзя
```

Когда функция закончится, её параметр выйдет из области видимости и данные будут освобождены.

---

### `Copy`-тип

```rust
fn makes_copy(x: i32) {
    println!("{x}");
}

let x = 5;

makes_copy(x);

println!("{x}");
```

Работает.

Поскольку `i32` реализует `Copy`:

```text
x в main
  ↓
копируется
  ↓
параметр функции
```

Исходный `x` остаётся доступным.

---

## Функции могут возвращать владение

Возвращаемое значение тоже способно передавать ownership.

```rust
fn create_string() -> String {
    let s = String::from("hello");
    s
}
```

При:

```rust
let s1 = create_string();
```

происходит:

```text
s внутри функции
       ↓
return
       ↓
владение перемещается наружу
       ↓
s1 становится владельцем
```

То есть значение не уничтожается при окончании функции, потому что владение было передано вызывающему коду.

---

## Функция может принять и вернуть то же владение

```rust
fn take_and_return(s: String) -> String {
    s
}

let s1 = String::from("hello");
let s2 = take_and_return(s1);
```

Последовательность:

```text
s1
 ↓ move
параметр s
 ↓ move при return
s2
```

После этого:

```text
s1 → недействителен
s2 → владелец
```

---

## Общая модель движения значения

Для типа вроде `String` ownership следует за значением:

```text
создание
  ↓
owner A
  ↓ assignment / аргумент функции
owner B
  ↓ return
owner C
  ↓
конец scope
  ↓
drop
```

В каждый момент память освобождает только текущий владелец.

Это и предотвращает ситуацию, когда несколько обычных переменных независимо считают одну память своей.

---

## Почему передавать владение туда-сюда неудобно

Если функция только хочет посмотреть на `String`, схема:

```rust
String → функция → вернуть String назад
```

была бы крайне неудобной.

Например, технически можно вернуть одновременно исходную строку и результат:

```rust
fn calculate_length(s: String) -> (String, usize) {
    let length = s.len();
    (s, length)
}
```

Но постоянно передавать ownership туда и обратно нерационально с точки зрения написания кода.

Именно эту проблему Rust решает **ссылками и заимствованием**.

Это уже следующий шаг.

# 4. Что запомнить

Главная схема всей темы:

```text
VALUE
  ↓
имеет одного владельца
  ↓
владелец может смениться через MOVE
  ↓
текущий владелец покидает scope
  ↓
DROP
  ↓
ресурс освобождается
```

Обязательно помнить три правила:

```text
1. У каждого значения есть владелец.

2. Одновременно обычное значение
   имеет только одного владельца.

3. Владелец вышел из scope
   → значение уничтожается.
```

Модель памяти:

```text
STACK
→ данные фиксированного размера
→ быстрые push/pop
→ здесь могут храниться ptr/len/capacity String

HEAP
→ данные динамического размера
→ память нужно выделять
→ доступ через указатель
→ здесь находится содержимое String
```

Для `String`:

```text
STACK                    HEAP

ptr ───────────────────→ данные
len
capacity
```

Ключевое различие:

```rust
let s2 = s1;
```

для `String`:

```text
MOVE
s1 invalid
s2 owner
```

а:

```rust
let s2 = s1.clone();
```

означает:

```text
глубокая копия
s1 valid
s2 valid
```

Для `Copy`-типов:

```rust
let y = x;
```

означает:

```text
копирование
x valid
y valid
```

Примеры `Copy`:

```text
integers
floats
bool
char
tuple, если все элементы Copy
```

И главное правило функций:

```text
передача аргумента
работает как присваивание

не-Copy → move
Copy     → copy
```

Возврат значения также может передавать владение:

```text
функция
   ↓ return
ownership переходит вызывающему коду
```

### Финальная модель

Когда видишь код:

```rust
let b = a;
```

первый вопрос:

```text
Какой тип у a?
```

Если это `Copy`:

```text
a сохраняется
b получает копию
```

Если это значение наподобие `String`:

```text
ownership переходит b
a становится недействительным
```

Именно поэтому далее нельзя воспринимать переменную просто как «имя, содержащее значение». Для Rust важно ещё и:

```text
кто сейчас владеет этим значением?
```

Следующий шаг — **4. Заимствование, ссылки и срезы**. Там решается главный недостаток чистого перемещения: как дать функции или другой части программы доступ к данным **без передачи владения**.

**Объём:** примерно **9–11 тыс. символов** с кодом и схемами.
**Время переноса в тетрадь:** примерно **55–70 минут**. Для этой темы сокращать сильнее нежелательно: `move`, `Copy`, `clone`, `drop` и передача владения через функции — фундамент дальнейшего Rust.
