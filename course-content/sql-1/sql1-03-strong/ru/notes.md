# Strong — продвинутый SQL

## 1. Тема

На уровне Strong важно понимать не только синтаксис запроса, но и то, **какой набор строк доступен каждой части запроса, как PostgreSQL его вычисляет и какой ценой**.

Основные темы:

```text
коррелированные источники данных
        ↓
рекурсивные и составные группировки
        ↓
точные рамки окон
        ↓
индексы и планы выполнения
        ↓
конкурентные транзакции
```

## 2. LATERAL

Обычный подзапрос в `FROM` вычисляется как самостоятельный источник и не может просто так обращаться к столбцам соседнего элемента `FROM`.

`LATERAL` разрешает зависимость от элементов, расположенных левее.

```sql
SELECT
    u.id,
    x.last_order_at
FROM users AS u
LEFT JOIN LATERAL (
    SELECT max(o.created_at) AS last_order_at
    FROM orders AS o
    WHERE o.user_id = u.id
) AS x ON true;
```

Модель выполнения:

```text
очередная строка users
        ↓
её u.id доступен LATERAL-подзапросу
        ↓
подзапрос вычисляет результат для этой строки
```

`LEFT JOIN LATERAL ... ON true` полезен, когда строку слева нужно сохранить даже при отсутствии результата справа.

`LATERAL` особенно полезен для «найти N лучших связанных строк для каждого объекта», вызовов табличных функций и вычислений, зависящих от текущей строки предыдущего источника.

Для табличных функций ключевое слово `LATERAL` можно не писать: аргументы функции и без него могут ссылаться на столбцы предшествующих элементов `FROM`. Для подзапроса такая зависимость требует явного `LATERAL`.

## 3. Табличные функции и WITH ORDINALITY

Функция может возвращать набор строк и использоваться в `FROM`.

```sql
SELECT *
FROM unnest(ARRAY['a', 'b', 'c']) AS t(value);
```

`WITH ORDINALITY` добавляет порядковый номер строки типа `bigint`, начиная с `1`:

```sql
SELECT *
FROM unnest(ARRAY['a', 'b', 'c'])
     WITH ORDINALITY AS t(value, n);
```

Результат концептуально:

```text
a  1
b  2
c  3
```

Это удобно, когда после разворачивания массива или другого набора нужно сохранить позицию элементов.

## 4. GROUPING SETS, ROLLUP и CUBE

Обычный `GROUP BY` задаёт один вариант группировки.

```sql
GROUP BY region, product
```

`GROUPING SETS` позволяет получить несколько уровней агрегации одним запросом:

```sql
SELECT region, product, sum(amount)
FROM sales
GROUP BY GROUPING SETS (
    (region, product),
    (region),
    ()
);
```

Здесь считаются:

```text
(region, product)  итог по товару внутри региона
(region)           итог по региону
()                 общий итог
```

`ROLLUP` — сокращение для иерархических итогов.

```sql
GROUP BY ROLLUP (region, product)
```

даёт группировки примерно такого вида:

```text
(region, product)
(region)
()
```

`CUBE` строит комбинации измерений и подходит для многомерной аналитики, когда нужны итоги по разным сочетаниям столбцов.

## 5. Рекурсивные CTE

`WITH RECURSIVE` позволяет запросу использовать результат предыдущего шага того же CTE.

Типичная структура:

```sql
WITH RECURSIVE tree AS (
    -- начальная часть
    SELECT id, parent_id, 1 AS depth
    FROM nodes
    WHERE parent_id IS NULL

    UNION ALL

    -- рекурсивная часть
    SELECT n.id, n.parent_id, t.depth + 1
    FROM nodes AS n
    JOIN tree AS t
        ON n.parent_id = t.id
)
SELECT *
FROM tree;
```

Логика:

```text
начальные строки
      ↓
рабочий набор
      ↓
рекурсивная часть строит следующие строки
      ↓
новые строки снова становятся входом
      ↓
повтор до исчерпания результата
```

Частые применения:

- деревья и иерархии;
- графоподобные связи;
- последовательное построение уровней;
- обход зависимостей.

Главная опасность — цикл или условие, которое не приводит вычисление к завершению. PostgreSQL отдельно поддерживает описание порядка поиска и выявление циклов в рекурсивных запросах (`SEARCH` и `CYCLE`). Даже если эти конструкции не нужны, нужно явно продумывать завершение рекурсии и повторное посещение узлов.

`UNION ALL` обычно предпочтителен, если удаление дублей не является частью логики: `UNION` добавляет стоимость поиска дубликатов.

## 6. Материализация CTE

CTE не нужно воспринимать как безусловно созданную временную таблицу.

PostgreSQL в подходящих случаях может встроить CTE в основной запрос, чтобы оптимизировать всё выражение совместно. В других случаях результат материализуется отдельно.

Можно явно управлять намерением:

```sql
WITH x AS MATERIALIZED (
    SELECT ...
)
SELECT ...;
```

или:

```sql
WITH x AS NOT MATERIALIZED (
    SELECT ...
)
SELECT ...;
```

Упрощённо:

```text
MATERIALIZED
    → сначала отдельный промежуточный результат

NOT MATERIALIZED
    → разрешить совместную оптимизацию/встраивание, когда допустимо
```

Материализация может быть полезна, если вычисление нужно выполнить один раз и использовать повторно. Встраивание может быть выгоднее, если внешние условия позволяют отбросить большую часть строк ещё внутри CTE.

Решение нужно принимать по плану запроса, а не по правилу «CTE всегда быстрее» или «CTE всегда медленнее».

## 7. Оконные рамки

У оконной функции есть три разных понятия:

```text
PARTITION BY  какие строки относятся к разделу
ORDER BY      в каком порядке они рассматриваются
frame         какая часть раздела доступна текущему вычислению
```

Например, накопительная сумма:

```sql
SELECT
    account_id,
    ts,
    amount,
    sum(amount) OVER (
        PARTITION BY account_id
        ORDER BY ts
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM operations;
```

Для каждой строки рамка начинается с первой строки раздела и заканчивается текущей.

Рамка может задаваться через `ROWS`, `RANGE` или `GROUPS`. Они по-разному трактуют границы:

```text
ROWS    физические строки относительно текущей
RANGE   значения ключа ORDER BY и равные им строки
GROUPS  группы строк, равных по ORDER BY
```

Важно помнить о рамке по умолчанию. При наличии `ORDER BY` она может включать не весь раздел, а строки от начала раздела до текущей строки вместе с её peers — строками, равными по ключу сортировки.

Поэтому такой запрос:

```sql
sum(amount) OVER (ORDER BY ts)
```

не обязательно означает «сумма по всей таблице». Если нужна конкретная семантика, задавайте рамку явно.

Оконные функции непосредственно разрешены в `SELECT` и `ORDER BY`. Для фильтрации по их результату нужен дополнительный уровень запроса.

## 8. Индексы

Индекс — отдельная структура, которая может ускорить доступ к данным, но требует места и обслуживания при изменениях.

Главный принцип:

```text
индекс ускоряет не таблицу вообще,
а определённые способы доступа к данным
```

Планировщик сам решает, использовать индекс или последовательное чтение.

### Составной индекс

```sql
CREATE INDEX orders_customer_created_idx
ON orders (customer_id, created_at);
```

Индекс содержит несколько ключевых столбцов. Порядок столбцов важен для того, какие условия и сортировки смогут эффективно его использовать.

### Индекс по выражению

```sql
CREATE INDEX users_lower_email_idx
ON users (lower(email));
```

Индексируется результат `lower(email)`, поэтому он полезен для запросов, использующих соответствующее выражение:

```sql
WHERE lower(email) = 'user@example.com'
```

### Частичный индекс

```sql
CREATE INDEX orders_open_customer_idx
ON orders (customer_id)
WHERE status = 'open';
```

Такой индекс содержит только строки, удовлетворяющие предикату `status = 'open'`.

Он полезен, когда запросы часто работают с небольшим важным подмножеством таблицы.

### Покрывающий индекс

Индекс может включать дополнительные столбцы, чтобы некоторые запросы могли получить нужные значения из индекса без обычного чтения строки таблицы, когда остальные условия это позволяют.

При выборе индекса нужно смотреть на реальные запросы и планы, а не создавать индекс на каждый столбец.

## 9. EXPLAIN

`EXPLAIN` показывает план, который PostgreSQL выбрал для запроса.

```sql
EXPLAIN
SELECT *
FROM orders
WHERE customer_id = 42;
```

План содержит узлы выполнения и оценки планировщика.

Частые узлы чтения:

```text
Seq Scan     последовательное чтение таблицы
Index Scan   чтение через индекс
Bitmap Scan  построение bitmap по индексу с последующим чтением таблицы
```

`Filter` показывает условие, применяемое к строкам на данном узле.

Важно: наличие индекса не означает, что будет выбран `Index Scan`. Планировщик сравнивает стоимость вариантов и может выбрать `Seq Scan`, `Index Scan` или bitmap-план. Условие, которое выбранный индекс не обслуживает напрямую, может остаться отдельным `Filter`.

Порядок B-tree-индекса иногда позволяет выполнить `ORDER BY` без отдельного узла `Sort`, если требуемый порядок совпадает с доступным порядком чтения индекса. Сам факт наличия индекса этого не гарантирует.

Стоимость в `EXPLAIN` — **оценка планировщика**, а не миллисекунды выполнения.

## 10. EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE customer_id = 42;
```

В отличие от обычного `EXPLAIN`, `EXPLAIN ANALYZE` **реально выполняет запрос** и добавляет фактические показатели, включая реальные строки и время выполнения узлов.

Сравнение:

```text
EXPLAIN
→ план + оценки

EXPLAIN ANALYZE
→ выполнение запроса + план + фактические показатели
```

Из этого следует важное правило безопасности:

```sql
EXPLAIN ANALYZE DELETE FROM orders ...;
```

реально выполнит `DELETE`.

Если нужно исследовать изменяющий запрос без сохранения результата, можно выполнять его в транзакции и затем откатывать изменения:

```sql
BEGIN;
EXPLAIN ANALYZE
UPDATE ...;
ROLLBACK;
```

При этом всё равно нужно учитывать эффекты самого выполнения во время транзакции: команда действительно выполняется, включая срабатывание применимых триггеров. `EXPLAIN ANALYZE` сам по себе не делает автоматический `ROLLBACK`.

## 11. MVCC, изоляция и блокировки

Одновременная работа транзакций требует определить, какие изменения каждая из них может видеть.

Уровень изоляции PostgreSQL по умолчанию — `READ COMMITTED`.

На этом уровне каждый SQL-оператор получает снимок данных, актуальный на начало **этого оператора**. Поэтому два `SELECT` внутри одной транзакции могут увидеть разные зафиксированные изменения других транзакций.

Более строгие уровни:

```text
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

Чем сильнее гарантия изоляции, тем больше вероятность, что конфликтующую транзакцию придётся повторить.

MVCC позволяет чтениям во многих случаях не блокировать обычные записи и наоборот, но это не означает отсутствия блокировок. PostgreSQL поддерживает блокировки таблиц и строк; изменение одних и тех же строк, DDL и явные блокировки могут заставить транзакции ждать друг друга.

Ожидание блокировки само по себе не является deadlock. Взаимоблокировка возникает, когда транзакции образуют цикл ожидания ресурсов; PostgreSQL обнаруживает такую ситуацию и прерывает одну из транзакций.

Практическая модель:

```text
MVCC       → версии строк и видимость
изоляция   → какие состояния разрешено видеть транзакции
блокировки → координация конфликтующих операций
```

Это связанные, но не взаимозаменяемые понятия.

## 12. ONLY и наследование

PostgreSQL поддерживает наследование таблиц. Запрос к родительской таблице обычно включает строки дочерних таблиц.

Чтобы ограничиться только самой родительской таблицей:

```sql
SELECT *
FROM ONLY cities;
```

В вводном материале `ONLY` также применяется к `UPDATE` и `DELETE` в контексте наследуемых таблиц.

Смысл:

```text
cities       → родитель + потомки
ONLY cities  → только непосредственно cities
```

# Что запомнить

Составные запросы:

```text
LATERAL        правый источник может зависеть от строк слева
WITH ORDINALITY добавляет нумерацию строк с 1
WITH RECURSIVE повторно использует результат предыдущего шага
```

Группировки:

```text
GROUPING SETS  несколько наборов группировки
ROLLUP         иерархические итоги
CUBE           комбинации измерений
```

Окна:

```text
PARTITION BY  раздел
ORDER BY      порядок внутри раздела
frame         строки раздела для текущего вычисления
```

Индексы:

```text
обычный/составной → ключи столбцов
expression index  → результат выражения
partial index     → только строки по предикату
```

Диагностика:

```text
EXPLAIN         оценки без выполнения основного запроса
EXPLAIN ANALYZE реально выполняет запрос и показывает фактические данные
```

Конкурентность:

```text
READ COMMITTED → уровень PostgreSQL по умолчанию
MVCC           → версии и видимость строк
locks          → ожидание и защита конфликтующих операций
```

Главное практическое правило уровня Strong: не угадывать, «быстрый» ли запрос. Проверять план, фактическое выполнение, объём данных и соответствие индексов конкретным условиям запроса.
